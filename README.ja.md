# TanukiTarkovMap

[한국어](README.md) | [English](README.en.md) | **日本語**

<div align="center">
<img src="images/icon.png" alt="TanukiTarkovMap" width="120" />

> **Escape from Tarkov 用のインゲームミニマップオーバーレイツールです。<br>スクリーンショットを撮ると座標を検出し、現在位置をミニマップに表示します。**

ゲームの上に常に表示されるウィンドウで [tarkov-market.com](https://tarkov-market.com/pilot) のインタラクティブマップを開き、ゲーム内のスクリーンショットに記録された座標から現在位置をリアルタイムで表示します。Alt+Tab をしなくても、ショートカットキー一つでマップを確認できます。

## インストール

1. [Releases ページ](https://github.com/siakun/TanukiTarkovMap/releases/latest)から最新の Setup インストーラー（`TanukiTarkovMap-Setup-<バージョン>-x64.exe`）をダウンロードします。
2. 実行してインストールすると、以降のアップデートは自動で適用されます。設定で自動アップデートをオフにしたり、好きなバージョンに戻したりすることもできます。

インストールせずに使いたい場合は、同じページからポータブル版（`TanukiTarkovMap-Portable-<バージョン>-x64.zip`）をダウンロードし、展開して実行します。ポータブル版にはインストールの手順がないため、下記の動作要件にある VC++ 再頒布可能パッケージを自分でインストールする必要があります。

> **動作要件**：Windows 10/11 (x64)、[Microsoft Visual C++ 2015-2022 再頒布可能パッケージ (x64)](https://aka.ms/vs/17/release/vc_redist.x64.exe)
>
> 再頒布可能パッケージは、内蔵ブラウザー（CefSharp）が使うランタイムです。Setup インストーラーは、パッケージがなければインストールの途中で自動的に入れるので、事前の準備は要りません。手動でのインストールが必要なのはポータブル版だけです。パッケージがない状態で実行すると、`CefSharp.Core.Runtime.dll` を読み込めなかったというエラーでアプリが起動しません。
>
> **安全性**：ゲームのメモリを読んだり、ゲームのプロセスに干渉したりしません。このアプリが読むのは、スクリーンショットのファイル名（画像の内容ではなく、名前に含まれる座標だけ）と、入ったマップが記録されたゲームログの二つだけで、ゲームのファイルは変更しません。詳しい仕組みは[プロジェクトの背景](#プロジェクトの背景)を参照してください。

## 使い方

1. TanukiTarkovMap を起動します。ゲームのスクリーンショットフォルダーは自動で検出され、必要なら設定画面で指定することもできます。
2. ゲームを始めると、入ったマップに自動で切り替わります。
3. ゲーム中は、ショートカットキー（初期設定は `F11`、設定で変更可能）でマップウィンドウを表示/非表示にします。
4. ゲーム内のスクリーンショットキー（初期設定は `PrtScn`）を押すと、マップに現在位置が表示されます。スクリーンショットを撮るたびに位置が更新されます。

表示/非表示のショートカットキーは、ミニマップウィンドウ全体をタスクトレイに隠したり再び表示したりするもので、アプリは終了しません。位置の更新にはゲームの Screenshot キーを使います。1台のモニターでゲームの上に表示し続けるには、上部のピン（常に手前に表示）をオンにしてください。

> **Steam ユーザーへの注意**：Steam の `F12` スクリーンショットは Steam オーバーレイの機能なので、座標が記録されません。必ずゲーム本体の設定（Controls）にある Screenshot キーを使ってください。初期設定の `PrtScn` が動作しないという報告もあるため、その場合はほかのキーに割り当て直してください。

設定画面では、ショートカットキー、透明度、UI の表示、マップの自動切り替え、スクリーンショットの自動整理、アップデートの方法を変更できます。マップのタイルが溜まるブラウザーキャッシュの容量を確認して消去するのも同じ画面で行います。問題が起きたときや要望があるときは、[GitHub Issues](https://github.com/siakun/TanukiTarkovMap/issues) に投稿してください。

## プロジェクトの背景

Escape from Tarkov では、ゲーム内でスクリーンショットを撮ると、ファイル名にプレイヤーのワールド座標（X, Y, Z）とカメラの回転値が記録されます。開発元の Battlestate Games がバグ報告用に公式に提供している機能で、このアプリはゲームのメモリやプロセスにアクセスせず、ディスクに保存されたファイルだけを読みます。

```
2025-12-20[02-09]-420.18, 1.00, 319.01-0.00089, -0.99307, -0.00012, -0.11748_15.11 (0).png
└ 日付/時刻 ┘ └ 位置 X, Y, Z ┘ └ カメラの回転（クォータニオン） ┘
```

[tarkov-market.com](https://tarkov-market.com/pilot) の Pilot ページは、この座標を受け取ってマップ上に現在位置を表示します。ただし、ブラウザーで開く Web アプリには構造上の限界があります。ゲームの上に常に固定する（Always-on-Top）、ウィンドウを半透明にする、グローバルショートカットキーで表示を切り替えるといった、OS のウィンドウを直接制御する処理ができません。デスクトップクライアントが必要な理由はここにあります。

このようなツールはすでにいくつかあります。元祖は tarkov-market.com が公式に検出する [ggdiam/TarkovPilot](https://github.com/ggdiam/TarkovPilot)（.NET Framework、トレイ専用のヘルパー）で、韓国のコミュニティの [byeong1/Tarkov-Client](https://github.com/byeong1/Tarkov-Client) はこれを Edge WebView2 で包んでウィンドウ内に表示しました。このプロジェクトは byeong1 版のアイデアから出発しましたが、Web ビューのエンジンを CefSharp に置き換え、ウィンドウ制御、座標の同期、ビルドパイプラインを一から設計し直しました。

## 技術的な実装

このプロジェクトの核心は「Web アプリにできないことを、ネイティブクライアントが代わりに行うこと」です。各機能をどのような問題のために、どのような方法で解決したかをまとめます。

### 1. Edge WebView2 から CefSharp への移植

出発点となったツールは Windows に内蔵されている Edge WebView2 を使っていましたが、このプロジェクトでは Web ビューのエンジンを CefSharp（Chromium Embedded Framework）に置き換えました。WebView2 はランタイムがユーザーの環境に依存するのに対し、CefSharp は Chromium をアプリと一緒に配布するので環境に左右されず、レンダープロセス、スクリプトの注入、ズームといった動作をより直接的に制御できます。ページの読み込み完了時（`FrameLoadEnd`）にカスタマイズ用のスクリプトを注入し、Web からアプリへのメッセージを `JavascriptMessageReceived` で受け取る方式で統合しました。

### 2. P/Invoke（user32.dll）によるネイティブウィンドウ制御

Web アプリにはできない OS のウィンドウ制御を、P/Invoke で直接実装しました。

- **Always-on-Top**：`SetWindowPos` に `HWND_TOPMOST` を適用し、ゲームの上に固定
- **半透明ウィンドウ**：`GetWindowLong`/`SetWindowLong` で `WS_EX_LAYERED` スタイルを有効にし、`SetLayeredWindowAttributes(LWA_ALPHA)` でアルファ値を調整
- **グローバルショートカットキー**：低レベルキーボードフック（`SetWindowsHookEx`）で、ゲームにフォーカスがある状態でも表示を切り替え

すべての Win32 呼び出しは `PInvoke.cs` の一か所にまとめて宣言し、`WindowTopmost` や `WindowTransparency` のような意図単位のラッパーで包んで、呼び出し側がフラグを直接扱わないようにしました。

### 3. リアルタイムの座標同期（FileSystemWatcher + Pilot ブリッジ）

スクリーンショットフォルダーを `FileSystemWatcher` でリアルタイムに監視し、新しいファイルができると、そのファイル名を内蔵ブラウザーの Pilot ブリッジに渡します。ブリッジはファイル名から座標と回転値を読み取り、サイトの地図機能で位置を表示します。ゲームログも一緒に監視（`LogsWatcher`）し、プレイヤーが入ったマップに自動で切り替えます。

`PilotBridge` は、ページに実際にある位置入力の経路を探して座標を渡します。以前の `window.pilot` の経路、Nuxt の Pilot サービス、そしてその二つがなくなった後の「Where am i」入力のハンドラーに対応し、座標が地図に反映されたことを確認してから受け渡しを終えます。読み込み中に取りこぼした最新の入力は送り直し、再読み込みやページ移動で消えた向き表示のスクリプトも復元します。

2026-08-17 までは、アプリ内で ASP.NET Core Kestrel を使ってポート `5123` に WebSocket サーバーを立て、サイトがそのサーバーに接続してファイル名を受け取っていました。同じ日に tarkov-market が Pilot v2 をデプロイし、サイトはローカルのアプリではなく自社のサーバー（`wss://tarkov-market.com/ws/pilot`）にだけ接続するよう変わったため、サーバーを立てても接続してくるクライアントがいなくなりました。サーバー中継の仕組みに合わせるにはアカウント認証まで実装する必要がありますが、`window.pilot` はそれなしで同じことができるため、WebSocket サーバーと ASP.NET Core への依存を取り除き、ブリッジの呼び出しに切り替えました。診断の根拠、採用しなかった代替案、サイトの変更に気づく方法は [Pilot 連携と位置の受け渡し経路](docs/20260817-pilot-bridge.md)（韓国語）にまとめています。

2026-10-07 には、サイトが `window.pilot` の位置関数と Pilot サービスの位置入力をどちらも削除しました。残ったのはユーザーがスクリーンショットのファイル名を貼り付ける「Where am i」入力だけだったため、ブリッジが画面に描画中の Vue コンポーネントからその入力のハンドラーを見つけ、同じファイル名を渡すようにしました。圧縮されたバンドルの関数名はデプロイのたびに変わりますが、テンプレートの prop 名は残るという点を利用しています。

### 4. オフラインマップ（試験的な機能）

設定で「ローカルマップを使用」をオンにすると、上部バーに Online/Local の切り替えが表示されます。Local はサイトに接続せず、アプリに同梱された地図データでマップを開きます。地図と階層、選んだ陣営の脱出地点、現在の位置と向きだけを残すため、サイトが停止していたり、サイトの位置入力が変わったりしても、レイドに必要な表示は動作し続けます。

最初は、サイトが送ってきた応答を丸ごと保存したコピーを、リクエストをインターセプトして返していました。動作はしたものの、コピーは圧縮されたバンドルの塊で中身を読めず、サイトが構造を変えると丸ごとダウンロードし直すしかありませんでした。現在はサイトの地図ドキュメントだけを収集して SVG と JSON（`resources/`）に変換し、アプリに同梱したミニマップ（`viewer/`）がサイトの地図画面と同じ見た目で描画します。変換した SVG は、収集したサイトのレンダラーで描いた結果と階層ごとにピクセル単位で照合し、座標変換はサイトが計算した値と比較して検証します。

Local は独立した一時的な保存領域で開き、オンラインの DB やキャッシュと混ざらないようにします。モードを切り替えると同じマップを開き直して最後の位置を渡し、アプリの陣営、拡大率、「UI 要素を隠す」の設定も適用し直します。設計の根拠と制約は [ローカルマップビューアーの設計](docs/20260821-local-viewer-design.md)（韓国語）にまとめています。

### 5. ゲームログの解析によるマップの自動切り替え

ゲームは起動するたびに、ログフォルダー（公式ランチャー版は `ゲームフォルダー\Logs`、Steam 版は `ゲームフォルダー\build\Logs`）の下に新しいセッションフォルダーを作り、`application.log` などに状態を記録します。ゲームフォルダーはレジストリから自動で検出し（公式ランチャー -> Steam の順）、検出できない場合は設定で指定できます。

- **公式ランチャー**：`HKLM\SOFTWARE\WOW6432Node\Microsoft\Windows\CurrentVersion\Uninstall\EscapeFromTarkov` の `InstallLocation` の値（フォルダーが実際に存在する場合のみ採用）
- **Steam**：`HKLM\SOFTWARE\WOW6432Node\Valve\Steam` の `InstallPath` から `steamapps\libraryfolders.vdf` を解析し、得られたすべてのライブラリフォルダーで `steamapps\common\Escape from Tarkov` を確認

`LogsWatcher` は最も新しいセッションフォルダーを選んで監視し（新しいフォルダーができると自動で乗り換え）、ログファイルが更新されるたびに、最後に読んだ位置から新しく追加された行だけを続けて読みます（`FileShare.ReadWrite` で開くので、ゲームの書き込みと競合しません）。アプリの起動前にすでに溜まっていた過去のログでは画面を切り替えないため、前のレイドのマップに誤って切り替わることを防げます。

マップの判別は、シーン読み込みのログ（`scene preset`）の行から `path:maps/<プリセット>.bundle` のプリセット名を取り出して行います。マッチ作成のログ（`TRACE-NetworkGameCreate profileStatus`）の `Location:` の値にも同じ情報がありますが、シーン読み込みの行が常に先に出力され、シーン読み込みの行しか残らないレイドもあるため、シーン読み込みの行だけを見ます。

取り出したプリセット名は、検出したその場でマップとして解釈します。ログの文字列を解釈するコードを `LogsWatcher` の一か所にまとめておくためで、それ以降の段階は文字列ではなくマップのオブジェクトだけをやり取りします。

```
scene preset の行を検出
  -> LogsWatcher          プリセット名を抽出
  -> MapConfiguration     プリセットをマップとして解釈（登録されていない値ならここで中断）
  -> MapEventService      マップ変更イベントを発行
  -> MainWindowViewModel  SelectedMapInfo に代入（ドロップダウンでの手動選択が合流する地点）
  -> WebBrowserViewModel  CefSharp のアドレスを移動
```

マップとプリセットの関係は 1:N です。Ground Zero はプレイヤーレベル帯ごとに、Factory は時間帯ごとにプリセットが分かれているため、一つのマップがプリセットの一覧を持つ形で `MapConfiguration` に登録します。一覧にないプリセットが出てきた場合は切り替えず、その名前だけをアプリのログに残します。ゲームに新しいマップが追加されたとき、何を登録すればよいかがその行でわかります。

自動切り替えが `SelectedMapInfo` を経由するのも意図したものです。ユーザーがドロップダウンでマップを選ぶときと同じ地点に合流させると、アドレスを変えてスクリプトを注入し直すコードが一つで済みます。自動切り替えをオフにすると、この代入だけを飛ばすので、手動選択はそのまま動作します。

レイドに入った後にアプリを起動すると、入場のログはすでに過ぎているため、リアルタイムの検出では捉えられません。そこで過去のログからもマップ名だけは読んで最後の値を覚えておき、ゲーム内でしか撮れないスクリーンショットを合図にそのマップへ補正します。すでにそのマップを表示していれば何も起きないため、正しく切り替わった後はスクリーンショットを撮っても画面が揺れません。

このほか、BattlEye の初期化ログ（`BEClient inited successfully`）をレイドの区切りの合図にしてスクリーンショットの自動整理を実行し、通知ログのクエスト通知（JSON）を解析してクエストの進行状況もページに渡します。

### 6. CefSharp と JavaScript の双方向通信

位置と向きの連携を修正した後は、サイトに接続できるかどうかに関係なく、同じ失敗条件を自動テストでもう一度確認します。テストはウィンドウのない Chromium で、サイトを模した再現ページを使って実行されます。PR とリリースでも実行され、失敗すると配布が中止されます。現在のサイトとの互換性は、実際のサイトにアプリと同じスクリプトを注入する診断ツールで別途確認します。テストの一覧と実行方法は [TESTING.md](TESTING.md)（韓国語）にあります。

Web の UI をアプリに合わせて整えるロジックは JavaScript で注入します。`.js` ファイルを Embedded Resource としてまとめて `JavaScriptLoader` で読み込み、ページの読み込み後に `EvaluateScriptAsync` で実行します（ヘッダーとフッターの削除、パネルの切り替え、位置マーカーへの向き表示の追加など）。逆に、Web 側で起きた出来事（マップの変更、接続状態）は `postMessage` で送って `JavascriptMessageReceived` で受け取り、CommunityToolkit.Mvvm の `WeakReferenceMessenger` で ViewModel に伝えます。C# と JS の境界をメッセージで緩やかにつないでいます。Local のミニマップには注入せず、ミニマップが公開している `window.tanukiViewer` の関数だけを呼び出します。他人のサイトをアプリの中で手直しして使うときの手法と、実際にはまった落とし穴は [埋め込み Web ページ制御のリファレンス](docs/20260818-embedded-site-control.md)（韓国語）にまとめています。

### 7. MVVM アーキテクチャと DI

コードビハインド（`*.xaml.cs`）にはロジックを置かないという原則を守りました。UI のインタラクションは Microsoft.Xaml.Behaviors ベースの Behavior に分け（ウィンドウのドラッグ、トレイへの最小化、ショートカットキー入力のキャプチャなど）、データとビジネスロジックは ViewModel と Service に置きます。サービスは Microsoft.Extensions.DependencyInjection で登録して `ServiceLocator` からアクセスし、ViewModel 同士の通信は直接の参照ではなく Messenger で行って結合度を下げました。

### 8. リリースの自動化（GitHub Actions + Velopack）

バージョンタグ（`v1.0.0` または `0.1.0` の形式）を push すると、GitHub Actions が self-contained で publish し、Velopack（`vpk`）でインストーラーとポータブル版の zip をパッケージ化して、GitHub Release に自動でアップロードします。ユーザー側では、アプリの起動時に Velopack の `UpdateManager` が新しいバージョンを確認し、バックグラウンドでダウンロードして次回の起動時に適用します。ビルドから配布、自動アップデートまでがタグ一つでつながります。

バージョンを上げるときは `src/TanukiTarkovMap/TanukiTarkovMap.csproj` の `Version` を変更し、[release-notes スキル](.agents/skills/release-notes/SKILL.md)（韓国語）の基準に従って `docs/releases/<Version>.md` にアップデート内容を書きます。このディレクトリのバージョン別ファイルがアップデート履歴で、配布時には同じファイルを GitHub リリースの本文と Velopack パッケージの両方に入れます。タグとプロジェクトのバージョンが異なるか、内容のファイルがない場合は配布を中止します。ローカルでパッケージ化するときは、プロジェクトのバージョンと同じ値を `build.bat <Version>` に渡します。

### 9. バージョンの選択と切り戻し

自動アップデートは最新バージョンにしか進みません。これは、新しいバージョンで問題に遭ったユーザーが自分で抜け出す方法がないということなので、設定で自動アップデートをオフにし、好きなバージョンを直接選べるようにしました。

これには Velopack の標準の経路を使えません。`GithubSource` は「最新のリリース一つにすべてのパッケージが集まっている」ことを前提に、そのリリースの `releases.win.json` だけを読み、ダウンロード先もその中でしか探しません。このリポジトリではフルパッケージが 250MB を超えるため、タグごとに自分のバージョンだけをアップロードしており、標準の経路では最新とその一つ前の二つのバージョンしか見えません。そこでリリースの一覧は GitHub Releases API で直接取得し、選んだタグ一つに固定した `IUpdateSource`（`GitHubReleaseSource`）を作って、Velopack のダウンロード、チェックサム検証、適用の手順に乗せます。このアップデートのコードは、ほかのアプリでも使えるように [Siakun.AutoUpdate](https://github.com/siakun/Siakun.AutoUpdate) パッケージとして分離しました。

パッケージのメタデータを自分で組み立てず、リリースがすでに持っているフィードの JSON を解析するのもこのためです。Velopack はダウンロードしたパッケージの SHA をフィードの値と照合しますが、手で作った値にはそのハッシュがないため、検証を通す方法がありません。

上のバージョンに上がるときは、間にあるバージョンの差分パッケージ（delta）をつなげてダウンロードします。フルパッケージは 242MB ですが、delta は一つあたり数百 KB なので、差は大きくなります。戻すときは常にフルパッケージをダウンロードします。delta は上がる方向にしか作られないためです。間のリリースが削除されている場合、飛ばす段階が多すぎる場合、delta の合計サイズがフルパッケージに比べて大きくなる場合も、フルパッケージをダウンロードします。時間がかかることのある作業なので、進行状況を画面に表示します。ダウンロードが終わってもプロセスを強制終了せず、CefSharp が Cookie と IndexedDB のファイルを手放せるよう正常に終了してから、パッケージを適用します。

最新ではないバージョンを選ぶと、自動アップデートも一緒にオフにします。オンのままだと次回の起動ですぐに最新に戻り、ユーザーが選んだバージョンが消えてしまうためです。

設定の「試験的な機能」で「ベータ版を受け取る」をオンにすると、`v0.1.1-beta` のような正式リリース前のバージョンも一覧と自動アップデートの対象に入ります。オフにしておくと取得の段階で除外されるため、一覧に見えるものと自動アップデートが追う対象は常に一致します。

この防止策は、自動アップデートの設定が入ったバージョンから有効です。それより古いバージョンに下げると、そのバージョンのアップデートのコードが設定を見ずに最新版を取ってくるため、そこに留まることはできません。すでに配布されたコードは変更できず、設計で防ぐ方法がないため、設定画面でそのことを事前に知らせることで代えています。
