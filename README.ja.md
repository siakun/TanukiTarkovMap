> **Escape from Tarkov 用のインゲームミニマップオーバーレイツールです。<br>スクリーンショットを撮ると座標を検出し、現在位置をミニマップに表示します。**

ゲームの上に常に表示されるウィンドウで [tarkov-market.com](https://tarkov-market.com/pilot) のインタラクティブマップを開き、ゲーム内のスクリーンショットに記録された座標から現在位置をリアルタイムで表示します。Online はサイトの地図に現在位置と向きを重ね、Local は同梱の地図に表示します。Alt+Tab をしなくても、ショートカットキー一つでマップを確認できます。

## インストール

1. [Releases ページ](https://github.com/siakun/TanukiTarkovMap/releases/latest)から最新の Setup インストーラー（`TanukiTarkovMap-Setup-<バージョン>-x64.exe`）をダウンロードします。
2. 実行してインストールすると、以降のアップデートは自動で適用されます。設定で自動アップデートをオフにしたり、好きなバージョンに戻したりすることもできます。

インストールせずに使いたい場合は、同じページからポータブル版（`TanukiTarkovMap-Portable-<バージョン>-x64.zip`）をダウンロードし、展開して実行します。ポータブル版にはインストールの手順がないため、下記の動作要件にある VC++ 再頒布可能パッケージを自分でインストールする必要があります。

> **動作要件**：Windows 10/11 (x64)、[Microsoft Visual C++ 2015-2022 再頒布可能パッケージ (x64)](https://aka.ms/vs/17/release/vc_redist.x64.exe)
>
> 再頒布可能パッケージは、内蔵ブラウザー（CefSharp）が使うランタイムです。Setup インストーラーは、パッケージがなければインストールの途中で自動的に入れるので、事前の準備は要りません。手動でのインストールが必要なのはポータブル版だけです。パッケージがない状態で実行すると、`CefSharp.Core.Runtime.dll` を読み込めなかったというエラーでアプリが起動しません。
>
> **安全性**：ゲームのメモリを読んだり、ゲームのプロセスに干渉したりしません。このアプリが読むのは、スクリーンショットのファイル名（画像の内容ではなく、名前に含まれる座標だけ）と、入ったマップが記録されたゲームログの二つだけで、ゲームのファイルは変更しません。詳しい仕組みは[プロジェクトの背景](#プロジェクトの背景)を参照してください。

## 使い方

1. TanukiTarkovMap を起動します。ゲームのスクリーンショットフォルダーは自動で検出され、必要なら設定画面で指定することもできます。
2. ゲームを始めると、入ったマップに自動で切り替わります。
3. ゲーム中は、ショートカットキー（初期設定は `F11`、設定で変更可能）でマップウィンドウを表示/非表示にします。
4. ゲーム内のスクリーンショットキー（初期設定は `PrtScn`）を押すと、Online または Local の現在位置と向きが更新されます。Online に位置表示の案内が出た場合は、上部バーで Local に切り替えてください。

上部バーで表示モードを選びます。`Online` は tarkov-market.com を地図中心に整理し、現在位置と向きを重ねて表示します。`Local` はアプリに同梱された地図で現在の位置と向きを表示し、`Origin` はサイトをアプリによる変更なしでそのまま開きます。`Origin` では `PMC`/`SCAV` と「UI 要素を隠す」は適用されません。選んだモードは次回の起動でも保持されます。

表示/非表示のショートカットキーは、ミニマップウィンドウ全体をタスクトレイに隠したり再び表示したりするもので、アプリは終了しません。位置の更新にはゲームの Screenshot キーを使います。1台のモニターでゲームの上に表示し続けるには、上部のピン（常に手前に表示）をオンにしてください。

> **Steam ユーザーへの注意**：Steam の `F12` スクリーンショットは Steam オーバーレイの機能なので、座標が記録されません。必ずゲーム本体の設定（Controls）にある Screenshot キーを使ってください。初期設定の `PrtScn` が動作しないという報告もあるため、その場合はほかのキーに割り当て直してください。

設定画面では、ショートカットキー、透明度、UI の表示、マップの自動切り替え、スクリーンショットの自動整理、アップデートの方法を変更できます。マップのタイルが溜まるブラウザーキャッシュの容量を確認して消去するのも同じ画面で行います。問題が起きたときや要望があるときは、[GitHub Issues](https://github.com/siakun/TanukiTarkovMap/issues) に投稿してください。

|------|------|
| マップオーバーレイ | ゲームの上に常に表示されるインタラクティブマップ（Always-on-Top） |
| リアルタイムの位置追跡 | ゲーム内のスクリーンショットで Online と Local の位置と向きを更新 |
| 表示モード | 上部バーで Online（サイトと位置および向き）、Local（同梱の地図と位置および向き）、Origin（元のサイト）を切り替え |
| マップの自動切り替え | ゲームログを検出し、入ったマップに自動で切り替え |
| グローバルショートカットキー | ショートカットキー（初期設定は `F11`）一つでマップウィンドウを表示/非表示、修飾キーと特殊キーに対応 |

| UI の整理 | Online で Web ページの不要な要素を取り除き、マップだけを表示 |
| グーンズの最近の目撃情報 | PvE の目撃情報をマップに表示 |
| レイド位置共有 | 同じパーティでレイドに入ったフレンドとスクリーンショットの位置をやり取りし、マップに一緒に表示（自動接続） |
| アップデート管理 | 新しいバージョンの自動適用、自動アップデートのオフ、以前のバージョンへの切り戻し |
| 表示言語 | 初期設定は Windows の表示言語に従い、設定で選ぶと再起動なしですぐに切り替え |

グーンズの最近の目撃情報は初期設定ではオフで、設定でオンにできます。グーンズは確率でスポーンするため、情報と実際の出現場所が異なることがあります。

レイド位置共有は開発者が運用するサーバーに自動接続し、入力する値はありません。同じパーティで同じレイドに入った人同士でスクリーンショットの位置をやり取りし、自分の位置と一緒にゲームのアカウント ID がサーバーに送られます。ひとりで入ったレイドは共有せず、同じレイドの別のパーティは自分の位置を受け取りません。フレンドの名札は自分のゲームのパーティ通知や同じ部屋の仲間から受け取ったニックネームで表示し、見つからなければアカウント ID の末尾 4 桁で表示します。地図の左下には `InRaid: 3p (名前, 名前, 名前)` のように自分を含む共有人数と名前を表示します。スクリーンショット前も表示し、ソロ、ローカルPvE、メニュー、切断中は非表示です。

## プロジェクトの背景

Escape from Tarkov では、ゲーム内でスクリーンショットを撮ると、ファイル名にプレイヤーのワールド座標（X, Y, Z）とカメラの回転値が記録されます。開発元の Battlestate Games がバグ報告用に公式に提供している機能で、このアプリはゲームのメモリやプロセスにアクセスせず、ディスクに保存されたファイルだけを読みます。

```
2026-09-09[14-14]_179.10, 3.29, -717.65_0, 0.70710678, 0, 0.70710678_15.67 (0).png
└ 日付/時刻 ┘     └ 位置 X, Y, Z ┘      └ カメラの回転（クォータニオン） ┘
```

[tarkov-market.com](https://tarkov-market.com/pilot) の Pilot ページは、この座標を受け取ってマップ上に現在位置を表示します。ただし、ブラウザーで開く Web アプリには構造上の限界があります。ゲームの上に常に固定する（Always-on-Top）、ウィンドウを半透明にする、グローバルショートカットキーで表示を切り替えるといった、OS のウィンドウを直接制御する処理ができません。デスクトップクライアントが必要な理由はここにあります。

このようなツールはすでにいくつかあります。元祖は tarkov-market.com が公式に検出する [ggdiam/TarkovPilot](https://github.com/ggdiam/TarkovPilot)（.NET Framework、トレイ専用のヘルパー）で、韓国のコミュニティの [byeong1/Tarkov-Client](https://github.com/byeong1/Tarkov-Client) はこれを Edge WebView2 で包んでウィンドウ内に表示しました。このプロジェクトは byeong1 版のアイデアから出発しましたが、Web ビューのエンジンを CefSharp に置き換え、ウィンドウ制御、座標の同期、ビルドパイプラインを一から設計し直しました。

## 技術的な実装

このプロジェクトの核心は「Web アプリにできないことを、ネイティブクライアントが代わりに行うこと」です。各機能をどのような問題のために、どのような方法で解決したかをまとめます。

### 1. Edge WebView2 から CefSharp への移植

出発点となったツールは Windows に内蔵されている Edge WebView2 を使っていましたが、このプロジェクトでは Web ビューのエンジンを CefSharp（Chromium Embedded Framework）に置き換えました。WebView2 はランタイムがユーザーの環境に依存するのに対し、CefSharp は Chromium をアプリと一緒に配布するので環境に左右されず、レンダープロセス、スクリプトの注入、ズームといった動作をより直接的に制御できます。ページの読み込み開始時（`FrameLoadStart`）と完了時（`FrameLoadEnd`）にスクリプトを注入し、Web からアプリへのメッセージを `JavascriptMessageReceived` で受け取る方式で統合しました。

### 2. ネイティブウィンドウ制御

Web アプリにはできない OS のウィンドウ制御を、デスクトップのウィンドウで直接扱います。ピン留めと半透明は WPF のウィンドウのプロパティで、グローバルショートカットキーやトレイからの復帰のように WPF にない動作は P/Invoke（user32.dll）で処理します。

- **Always-on-Top**：ウィンドウの `Topmost` をピンボタンの状態にバインドして、ゲームの上に固定。トレイから戻すときはフォーカスを奪わないよう `SetWindowPos` でウィンドウだけを前面に出し、このときもピンの状態（`HWND_TOPMOST` または `HWND_TOP`）を守る
- **半透明ウィンドウ**：枠のない透明ウィンドウ（`AllowsTransparency`）の内容の `Opacity` を透明度の設定にバインド。上部バーが隠れているときと透明度スライダーをドラッグしている間だけ適用し、操作するときは不透明に見える
- **グローバルショートカットキー**：低レベルキーボードフック（`SetWindowsHookEx`）で、ゲームにフォーカスがある状態でも表示を切り替え

Win32 の宣言は `PInvoke.cs` にまとめています。例外として、`Program.cs` は既に起動しているウィンドウを前面に出す単一インスタンス処理のために独自の宣言を持っています。

### 3. リアルタイムの座標同期（FileSystemWatcher + 自前のミニマップ）

スクリーンショットフォルダーを `FileSystemWatcher` で監視し、最新のファイル名を現在のマップに結び付けて保持します。Online は Core DLL がファイル名とリソースの定数から座標を計算し、サイトの表示状態に合わせてブラウザー上の WPF Canvas に位置の円と向きの矢印を描きます。Local ミニマップはファイル名から座標と回転を読み、位置と向きを描きます。両モードは位置の高さから階層を選びます。ゲームログも `LogsWatcher` で監視し、入場したマップへ切り替えます。

アプリは現在のマップの最新入力を一つ保持します。同じマップでモードを切り替えると位置を引き継ぎ、別のマップへ移動すると以前の位置を終了します。Origin は表示せず入力だけを保持します。Online はファイル名ごとに初めて画面内に表示したときだけ円を拡大して知らせ、表示状態を取得できない場合はログと Local への切り替え案内を表示します。Local は読み込み中に受け取った位置や再読み込みで消えた位置を確認して再送します。

2026-08-17 までは、アプリ内で ASP.NET Core Kestrel を使ってポート `5123` に WebSocket サーバーを立て、サイトがそのサーバーに接続してファイル名を受け取っていました。同じ日に tarkov-market が Pilot v2 をデプロイし、サイトはローカルのアプリではなく自社のサーバー（`wss://tarkov-market.com/ws/pilot`）にだけ接続するよう変わったため、サーバーを立てても接続してくるクライアントがいなくなりました。サーバー中継の仕組みに合わせるにはアカウント認証まで実装する必要がありますが、`window.pilot` はそれなしで同じことができるため、WebSocket サーバーと ASP.NET Core への依存を取り除き、ブリッジの呼び出しに切り替えました。

2026-10-07 には、サイトが `window.pilot` の位置関数と Pilot サービスの位置入力をどちらも削除しました。残ったのはユーザーがスクリーンショットのファイル名を貼り付ける「Where am i」入力だけだったため、ブリッジが画面に描画中の Vue コンポーネントからその入力のハンドラーを見つけ、同じファイル名を渡すようにしました。圧縮されたバンドルの関数名はデプロイのたびに変わりますが、テンプレートの prop 名は残るという点を利用しました。

2026-10-08 には、サイトが地図と自分の位置を canvas に描き、向きの矢印を PRO ユーザーにだけ表示するように変わったため、Online の向き表示と位置の確認がふたたび途切れました。位置入力の経路とサイト自身の位置の描画はデプロイのたびに変わってきましたが、地図の座標変換は変わっていませんでした。そこでサイトに位置を渡す代わりに、アプリが位置と向きを自分で描き、サイトからは座標変換だけを借りるように変えました。

サイトが地図の状態を通常のリアクティブ登録から外したため、従来の WeakMap の監視では取得できなくなりました。現在の Online は Proxy の生成時に必要な状態を記録し、座標と向きの計算を Core DLL、マーカーの描画を WPF に分離しています。Local はサイトの状態に依存しない表示経路として維持します。

### 4. オフラインマップ（Local）

上部バーで Local を選ぶと、サイトに接続せず、アプリに同梱された地図データでマップを開きます。地図と階層、選んだ陣営の脱出地点、現在の位置と向きだけを残すため、サイトが停止していたり、サイトの地図の構造が変わったりしても、レイドに必要な表示は動作し続けます。

最初は、サイトが送ってきた応答を丸ごと保存したコピーを、リクエストをインターセプトして返していました。動作はしたものの、コピーは圧縮されたバンドルの塊で中身を読めず、サイトが構造を変えると丸ごとダウンロードし直すしかありませんでした。現在はサイトの地図ドキュメントだけを収集して SVG と JSON に変換して Core DLL に含め、アプリに同梱したミニマップ（`viewer/`）がサイトの地図画面と同じ見た目で描画します。変換した SVG は、収集したサイトのレンダラーで描いた結果と階層ごとにピクセル単位で照合し、座標変換はサイトが計算した値と比較して検証します。

Local は独立した一時的な保存領域で開き、サイト（Online、Origin）の DB やキャッシュと混ざらないようにします。モードを切り替えると同じマップを新しいモードで開き直し、Local には最後の位置を渡します。アプリの拡大率はすべてのモードに、陣営と「UI 要素を隠す」の設定は Online と Local に適用し直します。

### 5. ゲームログの解析によるマップの自動切り替え

ゲームは起動するたびに、ログフォルダー（公式ランチャー版は `ゲームフォルダー\Logs`、Steam 版は `ゲームフォルダー\build\Logs`）の下に新しいセッションフォルダーを作り、`application.log` などに状態を記録します。ゲームフォルダーはレジストリから自動で検出し（公式ランチャー -> Steam の順）、検出できない場合は設定で指定できます。

- **公式ランチャー**：`HKLM\SOFTWARE\WOW6432Node\Microsoft\Windows\CurrentVersion\Uninstall\EscapeFromTarkov` の `InstallLocation` の値（フォルダーが実際に存在する場合のみ採用）
- **Steam**：`HKLM\SOFTWARE\WOW6432Node\Valve\Steam` の `InstallPath` から `steamapps\libraryfolders.vdf` を解析し、得られたすべてのライブラリフォルダーで `steamapps\common\Escape from Tarkov` を確認

`LogsWatcher` は最も新しいセッションフォルダーを選んで監視し（新しいフォルダーができると自動で乗り換え）、ログファイルが更新されるたびに、最後に読んだ位置から新しく追加された行だけを続けて読みます（`FileShare.ReadWrite` で開くので、ゲームの書き込みと競合しません）。アプリの起動前にすでに溜まっていた過去のログでは画面を切り替えないため、前のレイドのマップに誤って切り替わることを防げます。

マップの判別は、シーン読み込みのログ（`scene preset`）の行から `path:maps/<プリセット>.bundle` のプリセット名を取り出して行います。マッチ作成のログ（`TRACE-NetworkGameCreate profileStatus`）の `Location:` の値にも同じ情報がありますが、シーン読み込みの行が常に先に出力され、シーン読み込みの行しか残らないレイドもあるため、シーン読み込みの行だけを見ます。

取り出したプリセット名は、検出したその場でマップとして解釈します。ログの文字列を解釈するコードを `LogsWatcher` の一か所にまとめておくためで、それ以降の段階は文字列ではなくマップのオブジェクトだけをやり取りします。

```
scene preset の行を検出
  -> LogsWatcher          プリセット名を抽出
  -> MapConfiguration     プリセットをマップとして解釈（登録されていない値ならここで中断）
  -> MapEventService      マップ変更イベントを発行
  -> MainWindowViewModel  SelectedMapInfo に代入（ドロップダウンでの手動選択が合流する地点）
  -> WebBrowserViewModel  CefSharp のアドレスを移動
```

マップとプリセットの関係は 1:N です。Ground Zero はプレイヤーレベル帯ごとに、Factory は時間帯ごとにプリセットが分かれているため、一つのマップがプリセットの一覧を持つ形で `MapConfiguration` に登録します。一覧にないプリセットが出てきた場合は切り替えず、その名前だけをアプリのログに残します。ゲームに新しいマップが追加されたとき、何を登録すればよいかがその行でわかります。

自動切り替えが `SelectedMapInfo` を経由するのも意図したものです。ユーザーがドロップダウンでマップを選ぶときと同じ地点に合流させると、アドレスを変えてスクリプトを注入し直すコードが一つで済みます。自動切り替えをオフにすると、この代入だけを飛ばすので、手動選択はそのまま動作します。

レイドに入った後にアプリを起動すると、入場のログはすでに過ぎているため、リアルタイムの検出では捉えられません。そこで過去のログからもマップ名だけは読んで最後の値を覚えておき、ゲーム内でしか撮れないスクリーンショットを合図にそのマップへ補正します。すでにそのマップを表示していれば何も起きないため、正しく切り替わった後はスクリーンショットを撮っても画面が揺れません。

このほか、BattlEye の初期化ログ（`BEClient inited successfully`）をレイドの区切りの合図にしてスクリーンショットの自動整理を実行します。

### 6. CefSharp と JavaScript の双方向通信

位置と向きの表示を修正した後は、サイトに接続できるかどうかに関係なく、同じ失敗条件を自動テストでもう一度確認します。テストはウィンドウのない Chromium で、アプリに同梱したミニマップと地図リソースを使い、インストーラーを作るたびに実行します。現在のサイトで Online の状態記録、地図の自動調整、階層選択、UI 非表示と陣営の切り替えが動作するかは、実際のサイトにアプリと同じスクリプトを注入する診断ツールで別途確認します。

Web の UI をアプリに合わせて整えるロジックは JavaScript で注入します。サイトに注入する JavaScript と実行契約は Core DLL に EmbeddedResource として含めています。Core の `SiteControl` は呼び出し順序と陣営の再試行を、`OnlineOverlay` はサイト応答の解釈と位置の同期を担当します。アプリは CEF のライフサイクル、ドキュメントの有効性の確認と WPF 表示を担当します。スクリプトは二つの時点で実行します。ページの読み込みが始まったときは、地図の状態記録とページのエラー監視スクリプトを先に注入し、読み込みが終わったら残りを `EvaluateScriptAsync` で実行します（ヘッダーとフッターの削除、パネルの切り替え、陣営フィルターの適用など）。逆に、ページの状態（エラー、マップが描画されたか）は `postMessage` で送って `JavascriptMessageReceived` で受け取り、アプリのログに残します。ViewModel 間の受け渡しは CommunityToolkit.Mvvm の `WeakReferenceMessenger` が担います。C# と JS の境界をメッセージで緩やかにつないでいます。Local のミニマップには注入せず、ミニマップが公開している `window.tanukiViewer` の関数だけを呼び出します。Origin はサイトをそのまま表示するモードなので、何も注入しません。注入するかどうかはページを開くときに決まるため、Online と Origin を切り替えると現在のページを開き直します。

### 7. MVVM アーキテクチャと DI

コードビハインド（`*.xaml.cs`）にはロジックを置かないことを原則としています。メインウィンドウに残っている初期化ロジックは整理対象として管理しています。UI のインタラクションは Microsoft.Xaml.Behaviors ベースの Behavior に分け（ウィンドウのドラッグ、トレイへの最小化、ショートカットキー入力のキャプチャなど）、データとビジネスロジックは ViewModel と Service に置きます。サービスは Microsoft.Extensions.DependencyInjection で登録して `ServiceLocator` からアクセスし、ViewModel 同士の通信は直接の参照ではなく Messenger で行って結合度を下げました。

### 8. リリースの自動化（Velopack + GitHub Releases）

バージョンタグを付けると、ビルドと検査、self-contained ビルドと Velopack のパッケージ化を経て、インストーラーとアップデートパッケージを GitHub Releases にアップロードします。このリポジトリには、リリースごとにそのバージョンのソースを一つのコミットとして追加し、同じ名前のタグを付けます。リリースの本文とインストーラーパッケージに入るアップデート内容は同じファイルから作られ、タグとプロジェクトのバージョンが異なるか、内容がない場合は配布を中止します。インストール済みアプリは、メインウィンドウを開いた後に更新をダウンロードし、通常終了時に CefSharp を終了してから適用します。

### 9. バージョンの選択と切り戻し

自動アップデートは最新バージョンにしか進みません。これは、新しいバージョンで問題に遭ったユーザーが自分で抜け出す方法がないということなので、設定で自動アップデートをオフにし、好きなバージョンを直接選べるようにしました。

これには Velopack の標準の経路を使えません。`GithubSource` は「最新のリリース一つにすべてのパッケージが集まっている」ことを前提に、そのリリースの `releases.win.json` だけを読み、ダウンロード先もその中でしか探しません。このリポジトリではフルパッケージが数百 MB あるため、タグごとに自分のバージョンだけをアップロードしており、標準の経路では最新とその一つ前の二つのバージョンしか見えません。そこでリリースの一覧は GitHub Releases API で直接取得し、選んだタグ一つに固定した `IUpdateSource`（`GitHubReleaseSource`）を作って、Velopack のダウンロード、チェックサム検証、適用の手順に乗せます。このアップデートのコードは、ほかのアプリでも使えるように [Siakun.AutoUpdate](https://github.com/siakun/Siakun.AutoUpdate) パッケージとして分離しました。

パッケージのメタデータを自分で組み立てず、リリースがすでに持っているフィードの JSON を解析するのもこのためです。Velopack はダウンロードしたパッケージの SHA をフィードの値と照合しますが、手で作った値にはそのハッシュがないため、検証を通す方法がありません。

上のバージョンに上がるときは、間にあるバージョンの差分パッケージ（delta）をつなげてダウンロードします。フルパッケージは数百 MB ですが、delta は一つあたり数百 KB なので、差は大きくなります。戻すときは常にフルパッケージをダウンロードします。delta は上がる方向にしか作られないためです。間のリリースが削除されている場合、飛ばす段階が多すぎる場合、delta の合計サイズがフルパッケージに比べて大きくなる場合も、フルパッケージをダウンロードします。時間がかかることのある作業なので、進行状況を画面に表示します。ダウンロードが終わってもプロセスを強制終了せず、CefSharp が Cookie と IndexedDB のファイルを手放せるよう正常に終了してから、パッケージを適用します。

最新ではないバージョンを選ぶと、自動アップデートも一緒にオフにします。オンのままだと次回の起動ですぐに最新に戻り、ユーザーが選んだバージョンが消えてしまうためです。

設定の「試験的な機能」で「ベータ版を受け取る」をオンにすると、`v0.1.1-beta` のような正式リリース前のバージョンも一覧と自動アップデートの対象に入ります。オフにしておくと取得の段階で除外されるため、一覧に見えるものと自動アップデートが追う対象は常に一致します。

この防止策は、自動アップデートの設定が入ったバージョンから有効です。それより古いバージョンに下げると、そのバージョンのアップデートのコードが設定を見ずに最新版を取ってくるため、そこに留まることはできません。すでに配布されたコードは変更できず、設計で防ぐ方法がないため、設定画面でそのことを事前に知らせることで代えています。

### 10. レイド位置共有（SignalR）

フレンドと同じレイドに入っても、アプリは自分の位置しか表示しません。フレンドのスクリーンショットの位置も自分のマップに表示するため、開発者が運用するサーバーを通じて位置をやり取りするようにしました。アプリにサーバーのアドレスとアクセスキーが入っているので、起動すると自動接続します。

同じパーティで同じレイドに入ったかどうかはゲームのログで判定します。サーバーがレイドを作ると、application ログにそのレイドが動くゲームサーバーのセッションが記録され、メニューに戻るとプロファイルを選び直す行が記録されます。同じログからサーバーモード（PvE、PvP）と自分のアカウント ID も読み取ります。パーティがマッチングを始めると push-notifications ログの通知にパーティのグループ ID が届き、直後の割り当て通知に同じサーバーセッションが届きます。アプリはこの 2 つをサーバーセッションで結び付けてサーバー上の `モード:パーティグループ ID` という名前のルームに入り、スクリーンショットを撮るたびに解析した座標を送ります。最初は画面右下のレイド ID（`shortId`）でルームを分けていましたが、同じレイドでも人によって最後の 1 文字が異なり、フレンド同士が別のルームに入ってしまいました。パーティグループ ID は同じパーティの同じレイドでだけ同じになり画面にも映らないため、同じレイドの別のパーティや配信の視聴者はルームに入れません。サーバー（ASP.NET Core SignalR ハブ）は同じルームの他の人にだけ WebSocket で位置を送り届けるので、自分がスクリーンショットを撮らなくても、フレンドが撮ればすぐに自分のマップに表示されます。後から入った人にはルームの最後の位置を渡します。サーバーとアプリはハブの取り決めを Core DLL の 1 か所から読み、食い違わないようにしています。

パーティ通知から仲間のアカウントIDとニックネームを読み取ります。自分の名前も、インベントリエラーのプロファイルタグや他の人が持つドッグタグに残る場合があります。プロファイルタグは同じセッションのプロファイルIDとアカウントIDを照合します。現在のアカウントに保存した名前がなければ、過去のセッションも範囲と時間を制限してバックグラウンドで調べます。名前はアカウントIDと一緒に保存し、同じアカウントでだけ復元します。現在のセッションのログ、仲間から受け取った名前、過去のログ、保存値の順で優先します。入室時や名前が更新されたときに同じ部屋へ知らせます。不明ならアカウントIDの末尾4桁、IDもなければ `?` を表示します。フレンドのマーカーは最初に現れた順に赤、オレンジ、黄、緑で、自分のマーカーは明るい灰色です。

アプリは公開配布されるため、アプリに入っているアクセスキーは秘密ではありません。キーはアプリ以外からの接続を防ぎ、キーを変えて古いバージョンのアプリの接続を断つために使います。人を絞るのはキーではなくパーティグループ ID の役割です。サーバーは許可するモードを決めて特定のモードの共有を止められます。

入退室通知とメンバー一覧で、スクリーンショットとは独立してパーティ表示を更新します。WPFがすべての表示モードで左下に自分を先頭、仲間を色番号順に表示します。サーバーの運用者は、未入室の接続も含め、接続ごとの IP、アプリのバージョン、User-Agent、アカウントID、ニックネーム、部屋ID、最後の位置を確認できます。参加アカウント、ニックネーム、モード、マップ、入退室時刻と位置送信回数をSQLiteに記録して統計に使い、IPと座標は保存しません。既存のハブ契約を維持して機能を追加するため、サーバーとアプリを別々に更新できます。古いサーバーでは一覧と名前交換だけを省略し、受信した位置からパーティを表示します。

共有は付加機能なので、サーバーが止まっていたり遅かったりしても自分の位置表示が待たないように経路を分けました。共有サービスはスクリーンショットのイベントから例外を外に出さず、サーバーとの通信を別に実行し、フレンドのマーカーは自分のマーカーとは別の要素に描きます。

## 開発について

ビルドには Windows と .NET 10 SDK 以降が必要です。アプリは .NET 8 で動作し、ViewModel の partial プロパティ生成（`LangVersion=preview`）に最新の C# コンパイラーを使います。

```powershell
dotnet build TanukiTarkovMap.csproj
dotnet publish TanukiTarkovMap.csproj -c Release -r win-x64 --self-contained true -o publish
```

座標計算、設定、ファイル監視、位置共有とサイト制御は、`packages/` に含まれる TanukiTarkovMap.Core パッケージが担当します。プロジェクトファイルがこのパッケージのバージョンを固定し、`NuGet.Config` が Core をリポジトリの `packages/` から、そのほかの依存関係を NuGet.org から復元するため、別途アカウントや認証は必要ありません。Core DLL は Obfuscar で難読化されており、公開 API と JSON の契約はそのままです。Releases のインストーラーは、同じタグのソースからビルドしています。
