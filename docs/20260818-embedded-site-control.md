## 적용 범위와 용어

이 문서는 소스가 없고 빌드에 손댈 수 없으며 통보 없이 바뀌는 남의 웹사이트를, 그 사이트를 품은
앱 쪽에서 고쳐 쓰는 기법을 다룹니다. 기법은 특정 엔진에 매이지 않습니다. CefSharp, WebView2,
Electron의 BrowserView, Playwright처럼 브라우저 엔진을 통제하고 페이지 컨텍스트에서 코드를
실행할 수 있는 환경이면 그대로 통합니다.

읽는 데 필요한 배경은 셋입니다. HTML/DOM과 CSS 우선순위, JavaScript 이벤트 전파, 그리고
"앱이 브라우저를 품고 있다"는 구조 감각입니다.

본문은 다음 용어로 서술합니다.

| 용어 | 정의 |
|---|---|
| 대상 사이트 | 앱 안에 띄우는, 소스와 빌드에 손댈 수 없는 남의 웹사이트 |
| 호스트 앱 | 브라우저 엔진을 품고 대상 사이트를 띄우는 앱 |
| 제어 측 | 호스트 앱과 그 주입 스크립트, 조사 도구를 묶어 부르는 이름 |
| 페이지 컨텍스트 | 대상 사이트의 코드와 같은 전역(`window`)을 공유하는 실행 환경 |
| 주입 | 호스트 앱이 페이지 로드 후 페이지 컨텍스트에서 스크립트를 실행시키는 일 |
| 주입 스크립트 | 주입되어 페이지 안에서 도는 코드 (2절) |
| 조사 도구 | 페이지 밖 Node 프로세스에서 실행 중인 페이지를 조사하는 코드 (2절) |
| 신뢰 입력 | 브라우저 엔진이 만든 입력 이벤트. `event.isTrusted === true` |
| 합성 입력 | 페이지 안 코드가 `dispatchEvent`로 만든 입력 이벤트. `isTrusted`는 false |
| 렌더 층 | 사이트의 내부 상태 하나를 화면에 그려 내는 개별 경로. 한 화면이 canvas 그리기와 CSS `transform`처럼 여러 층으로 이뤄지기도 함 |

**예시**: 이 문서의 예시는 모두 TanukiTarkovMap 저장소에서 가져옵니다. WPF 앱 안에
CefSharp(Chromium Embedded Framework)로 tarkov-market.com을 띄워 게임 밖 화면에서 맵을 보는
도구입니다. 사이트를 그대로 쓰면 앱에 필요 없는 헤더와 안내 배너가 자리를 차지하고, 맵을 끌다
화면 밖으로 놓치고, 사이트가 죽으면 앱도 함께 죽습니다. 이 문제들을 아래 기법으로 풀었습니다.

## 1. 제어 측의 권한과 두 원칙

제어 측이 가진 권한은 실행, 가로채기, 엔진 설정 셋이고, 소스, 문서, 변경 통보는 없습니다.
이 비대칭이 문서 전체를 관통하는 두 원칙을 정합니다.

| 가진 권한 | 없는 것 |
|---|---|
| 페이지 컨텍스트에서 임의의 JavaScript 실행 | 소스와 빌드 |
| 네트워크 요청을 가로채 다른 응답 반환 | 안정된 API와 문서 |
| 브라우저 엔진 설정 (줌, 창 크기, 원격 디버깅 포트) | 변경 통보 |

**원칙 1. 대상 사이트가 이미 열어 둔 입구로 들어갑니다.** 사이트의 내부 상태를 제어 측이 직접
고치면, 그 상태를 근거로 그려지는 다른 렌더 층과 어긋납니다(5.9절). 마우스와 휠 같은 입력,
사이트가 `window`에 열어 둔 함수, CSS 우선순위처럼 사이트가 원래 처리하게 되어 있는 경로로
들어가면 나머지 일관성은 사이트가 지킵니다.

**원칙 2. 무엇을 하든 밖에서 측정할 수 있어야 합니다.** 대상이 남의 코드이므로 추측이 늘어나고,
추측을 줄이는 유일한 방법은 실행 중인 페이지에서 숫자를 읽는 것입니다. 관측 통로(4절)를 먼저
만들고 기능을 만드는 순서가 반대 순서보다 언제나 빠릅니다.

## 2. 주입 스크립트와 조사 도구: `.js`와 `.mjs`

제어 코드는 페이지 안에서 도는 주입 스크립트와, 페이지 밖에서 그 페이지를 조사하는 도구로
나뉩니다. 성격이 다른 두 벌이며, 이 저장소는 확장자로 구분합니다.

| 구분 | 주입 스크립트 (`src/.../Scripts/*.js`) | 조사 도구 (`tools/*.mjs`) |
|---|---|---|
| 실행 위치 | 페이지 컨텍스트, 사이트 코드와 같은 전역 | Node 프로세스, 페이지 밖 |
| 실행 주체 | 호스트 앱이 페이지 로드 후 주입 | 사람이 명령줄에서 실행 |
| 배포 | 빌드 때 DLL에 Embedded Resource로 포함 | 저장소에만 존재, 사용자에게 배포되지 않음 |
| 쓰는 API | DOM, 이벤트, `window` | CDP, `fetch`, `WebSocket`, 파일 시스템 |
| 수정 확인 비용 | 앱 재빌드와 재실행 | 즉시 |

`.mjs`는 Node의 확장자 규칙입니다. Node는 확장자로 모듈 방식을 정하는데, `.mjs`는 ES 모듈로
읽혀 `package.json` 없이 `import`와 최상위 `await`를 쓸 수 있습니다. 조사 도구를 파일 하나짜리
스크립트로 유지하는 데 이 두 가지가 결정적입니다.

조사 도구는 의존성을 두지 않습니다. Node 22의 내장 `fetch`와 `WebSocket`만으로 브라우저에
붙습니다. `npm install`이 필요한 도구는 환경을 맞춰야 쓸 수 있어 급할 때 쓰이지 않습니다.

## 3. 주입 파이프라인

주입은 스크립트를 빌드 시 앱에 품었다가, 페이지 로드가 끝난 시점에 페이지 컨텍스트에서
실행시키는 파이프라인으로 구성합니다.

```
빌드 시                                실행 시
Scripts/*.js --임베드--> DLL --Load()--> 문자열
                                          |
                              FrameLoadEnd (메인 프레임)
                                          |
                                EvaluateScriptAsync
                                          v
                              페이지 컨텍스트에서 실행
```

C# 쪽은 파일 하나를 상수 하나로 감쌉니다.

```csharp
// MapKeepVisible.js.cs: 파일 이름과 호출 상수를 한곳에 묶는다
public static string KEEP_MAP_VISIBLE_SCRIPT => JavaScriptLoader.Load("map-keep-visible.js");

// 페이지 로드가 끝난 뒤 주입한다
await ExecuteScriptAsync(MapKeepVisible.KEEP_MAP_VISIBLE_SCRIPT);
```

JavaScript 쪽은 즉시 실행 함수로 감싸고, 밖에서 볼 것만 `window`에 붙입니다.

```javascript
(function () {
    'use strict';
    // 밖에서 판을 확인할 수 있게 표시를 남긴다
    window.__tanukiKeepVisible = { version: 6, log: function () { return debugLog; } };
})();
```

스크립트를 C# 문자열에 넣지 않고 별도 파일로 두는 이유는 셋입니다. 편집기가 문법을 검사하고,
`node --check` 같은 도구로 커밋 전에 문법을 확인할 수 있고, 조사 도구(4절)가 배포될 코드와
**같은 파일**을 읽어 주입해 볼 수 있습니다. 셋째가 특히 중요합니다. 시험한 코드와 배포되는
코드가 다르면 시험이 증거가 되지 못합니다.

주입에는 걸리기 쉬운 함정이 넷 있습니다.

**주입은 문서마다 다시 합니다.** 주소를 바꿔 페이지를 새로 읽으면 주입 스크립트가 사라지므로
로드 이벤트마다 다시 주입합니다. 반대로 SPA에서는 사이트 안 링크를 눌러도 문서를 다시 읽지 않고
화면만 바뀌므로 로드 이벤트가 오지 않고, 이미 들어가 있는 주입 스크립트도 다시 돌지 않습니다.
새 화면에 맞춰 다시 할 일이 있으면 스크립트 안에서 주소 변화를 직접 감시합니다.

```javascript
// 사이트 안에서 화면만 바뀌는 경우를 잡는다
var fittedPath = location.pathname;
setInterval(function () {
    if (location.pathname === fittedPath) return;
    fittedPath = location.pathname;
    // 새 화면에 맞춰 다시 할 일
}, 500);
```

**준비 상태를 UI 프레임워크 속성으로 판정하지 않습니다.** CefSharp의 `IsBrowserInitialized`와
`Address`는 WPF DependencyProperty라 CEF가 UI 스레드에 따로 게시해 갱신하는데, 릴리즈
빌드에서는 첫 페이지 로드가 그 갱신보다 먼저 처리되는 일이 생깁니다. 그 값으로 판정하면 페이지
후처리가 통째로 조용히 건너뛰어집니다. 준비 상태는 실제 인스턴스인 `BrowserCore`로 판정하고,
주소는 로드 이벤트가 준 `e.Url`을 씁니다. **예시** (0.2.3): 디버그 빌드는 정상인데 릴리즈
빌드만 UI 숨김과 위치 표시가 안 되는 증상의 원인이 이 갱신 지연이었습니다.

**실패를 조용히 넘기지 않습니다.** 건너뛴 주입은 오류를 내지 않으므로, 로그가 없으면 위 증상처럼
원인이 오래 숨습니다. 주입을 건너뛰었으면 왜 건너뛰었는지 한 줄이라도 남깁니다.

**주입 순서에 의존이 생깁니다.** 뒤에 도는 스크립트가 앞 스크립트의 결과를 덮을 수 있습니다.
5.1절의 기법이 이 실패에서 나왔습니다.

## 4. 관측 통로: CDP

관측 통로는 브라우저 엔진의 원격 디버깅 포트에 CDP(Chrome DevTools Protocol)로 붙여 만듭니다.
CDP는 크로미움이 그 포트로 여는 프로토콜로, DOM 조회, JavaScript 실행, 스크린샷을 페이지 밖에서
주고받을 수 있습니다. 앱 안 브라우저에서 F12로 여는 DevTools 창은 사람만 볼 수 있어 자동화된
확인에는 쓸 수 없습니다.

포트는 Debug 빌드에서만 엽니다. 릴리즈 빌드에서 열면 사용자 컴퓨터에서 앱 안 페이지를 아무나
조작할 수 있는 통로가 됩니다.

```csharp
#if DEBUG
    // Debug 빌드 한정, localhost 전용
    settings.RemoteDebuggingPort = 9222;
#endif
```

붙는 쪽은 조사 도구 `tools/cdp-debug.mjs` 하나입니다. `/json/list`로 페이지 목록을 받아
`webSocketDebuggerUrl`에 접속하면, 그 뒤로는 JSON 명령을 주고받는 일이 전부입니다.

```bash
node tools/cdp-debug.mjs targets                  # 디버깅 가능한 페이지 목록
node tools/cdp-debug.mjs eval "document.title"    # 페이지 안에서 JS 실행
node tools/cdp-debug.mjs html ".panel_left"       # 선택자의 outerHTML
node tools/cdp-debug.mjs screenshot               # 렌더링 화면 PNG 저장
```

스크린샷은 숫자가 맞는데 눈으로 보면 틀린 경우를 잡습니다(7절). **예시**: 맵 맞추기 작업에서
"채움 비율 0.95, 중심 어긋남 1px"이라는 수치가 실제로 어떤 화면인지는 캡처로 확인해 확정했습니다.

**포트는 자리를 정해 둡니다.** 규약 없이 포트를 겹치면 명령이 엉뚱한 프로세스로 흘러갑니다.
앱이 9222를 쓰는 동안 같은 포트로 크롬을 띄우면, 크롬은 바인딩에 실패해도 조용히 떠 있고 이후
CDP 명령이 전부 실행 중인 앱으로 흘러 들어가 사용자가 보는 화면을 시험 스크립트가 조작하게
됩니다.

| 포트 | 자리 |
|---|---|
| 9222 | 실행 중인 앱 |
| 9223 | 손으로 띄우는 재현 실험용 브라우저 |
| 자동 할당 | 조사 도구가 띄우는 브라우저 (`--remote-debugging-port=0`, 임시 프로필) |

조사 도구가 브라우저를 직접 띄울 때는 포트를 정하지 않고 0을 넘겨 빈 포트를 받습니다. 브라우저가
임시 프로필 폴더에 남기는 `DevToolsActivePort` 파일에서 실제 포트를 읽으면 겹칠 일이 없습니다.
**예시**: [headless-chrome.mjs](../tools/headless-chrome.mjs)가 이렇게 띄우고, 지도 데이터 수집기와
검사 도구가 모두 이 실행기를 씁니다.

<!--
INTENT: 조사 도구가 실제 사이트에 접속하면서 처음으로 봇 확인에 막혔다. 같은 증상에서 원인을
갈라 볼 순서와, 자동화 표시를 지우는 일이 무엇을 보장하지 않는지를 함께 남긴다.
-->
**실제 사이트에 붙는 조사 브라우저는 자동화 표시를 지웁니다.** 사람이 쓰는 브라우저에서는 멀쩡한
사이트가 headless 조사 브라우저에서만 다르게 동작할 수 있습니다. 증상은 두 갈래로 나타났습니다.

- 페이지 대신 봇 확인 화면이 뜨고 넘어가지 않습니다. headless Chrome은 User-Agent에 `HeadlessChrome`을
  적는데, Cloudflare 같은 방어 계층이 이 문자열을 봅니다. 캡처로 확인 화면을 보면 바로 구별됩니다.
- 페이지와 캔버스는 정상으로 그려지는데 사이트의 데이터 상태만 끝내 비어 있습니다. 자동화로 띄운
  브라우저는 `navigator.webdriver`가 true이고, 사이트가 이 값을 보고 데이터 요청을 하지 않을 수
  있습니다. 같은 페이지를 사람 브라우저와 조사 브라우저에서 열어 `navigator.webdriver`와 데이터 상태를
  나란히 찍으면 갈립니다. 화면이 그려졌다는 사실만으로 데이터까지 받았다고 판단하지 않습니다.

조사 브라우저에서는 User-Agent의 `HeadlessChrome`을 `Chrome`으로 바꾸고(CDP의
`Emulation.setUserAgentOverride`), `--disable-blink-features=AutomationControlled`로 띄워
`navigator.webdriver`를 끕니다. 이것은 사람 브라우저와 같은 조건을 맞추는 일일 뿐 접속을 보장하지
않습니다. 방어 계층은 언제든 다른 신호를 볼 수 있으므로, 실제 사이트에 기대는 검사는 CI에 넣지 않고
사람이 돌리는 진단으로 둡니다. 자동 수집이 사이트 이용약관이 허락하는 범위인지도 따로 확인합니다.

**실험은 시나리오 파일로 적습니다.** 한 번 확인하고 버릴 실험도 `.mjs` 파일로 적습니다. 같은
조건을 다시 돌릴 수 있어야 앞뒤 결과를 비교할 수 있기 때문입니다. 전형적인 구성은 네 단계입니다.

```javascript
// 1. 대상 페이지를 연다
await send('Page.navigate', { url: 'https://example.com/page' });
await new Promise((r) => setTimeout(r, 12000));

// 2. 배포될 스크립트를 그대로 읽어 넣는다
await evaluate(await readFile('src/.../Scripts/map-keep-visible.js', 'utf8'));

// 3. 사람이 하듯 입력을 보낸다 (신뢰 입력)
await send('Input.dispatchMouseEvent', { type: 'mousePressed', x: 700, y: 500, button: 'left', clickCount: 1 });

// 4. 결과를 숫자로 읽는다
console.log(await evaluate(`getComputedStyle(document.querySelector('.map-wrap')).transform`));
```

**신뢰 입력과 합성 입력을 갈라 시험합니다.** CDP의 `Input.dispatchMouseEvent`가 보내는 입력은
브라우저가 만든 신뢰 입력이고, 페이지 안에서 `dispatchEvent`로 만든 입력은 합성 입력입니다.
둘을 갈라 시험하면 "사이트가 합성 입력을 거른다"와 "사이트가 그 자리를 다르게 취급한다"를
구별할 수 있습니다. 이 구별이 5.5절의 입력 선택을 정하는 근거입니다.

## 5. 개입 기법 카탈로그

개입은 약한 것부터 강한 것 순서로 고르고, 위 기법으로 되면 아래로 내려가지 않습니다. 각 기법은
적용 조건, 방법, 실패 모드, 검증의 같은 틀로 적습니다.

### 5.1 스타일시트 한 장으로 숨기기

**적용 조건**: 대상 사이트의 특정 영역을 보이지 않게 하는 경우입니다.

**방법**: 요소마다 `style.display`를 넣지 않고, `!important`가 붙은 규칙을 담은 `<style>` 한
장을 문서에 넣습니다. 토글이 필요하면 `html`에 클래스를 붙였다 떼어 규칙을 켜고 끕니다.

```javascript
var STYLE_ID = 'tanuki-visibility-rules';
var rules = 'header, .footer-wrap { display: none !important; }'
          + '.cookie-consent { display: none !important; }';
```

**실패 모드**: 인라인 스타일로 숨기면 두 곳에서 깨집니다. 나중에 만들어진 요소를 놓치고, 다른
스크립트가 `style.cssText`를 통째로 대입하면 함께 지워집니다. `!important` 규칙은 인라인
스타일보다 우선하므로 두 경우를 모두 막습니다. **예시**: 주입 스크립트 두 개가 서로의 인라인
스타일을 지워, 숨겼던 헤더가 릴리즈 빌드에서만 되살아나는 증상이 있었습니다(3절의 순서 의존).

**검증**: `getComputedStyle(el).display`를 CDP로 읽습니다. 요소가 없어졌는지가 아니라 계산된
값을 봅니다.

<!--
INTENT: 규칙을 거는 방법(위)과 규칙에 무엇을 적을지(아래)는 따로 내리는 판단이라 5.1 안의 하위 절로
둔다. 뒤 절의 번호와 6절, 9절의 절 참조를 바꾸지 않으려고 새 절 번호를 만들지 않는다.
-->
#### 숨길 대상이 계속 늘어날 때: 남길 것을 적기

**적용 조건**: 대상 사이트가 같은 영역에 UI를 자주 새로 얹어, 숨길 요소를 나열한 규칙이 사이트가
바뀔 때마다 낡는 경우입니다. 그 영역에서 꼭 남겨야 하는 것(사이트가 화면을 그리는 층)이 UI보다
드물게 바뀔 때 이득입니다.

**진단**: 규칙을 바꾸기 전에 페이지에서 세 가지를 확인합니다.

1. 새로 나타난 요소가 어디에 붙었는지 봅니다. 요소의 글자로 텍스트 노드를 찾아 조상 사슬을 찍으면,
   기존 규칙이 숨기던 영역 안인지 그 옆인지가 갈립니다. **예시**: 새 가이드 패널은 기존 규칙이
   숨기던 좌우 패널 안이 아니라 맵을 그리는 컨테이너(`.map-cont`)의 직계 자식으로 들어왔습니다.
2. 그 컨테이너의 직계 자식을 모두 나열해 그리는 층과 UI로 나눕니다. 태그, 크기, `position`,
   `z-index`를 함께 찍으면 나누기 쉽습니다. **예시**: 보이는 UI는 모두 `z-index` 20 이상의 절대 위치
   상자였고, 그리는 층은 캔버스와 맵 SVG, 그리고 `z-index` 10 이하의 기준점 상자였습니다.
3. 절대 가리면 안 되는 요소를 실제로 만들어 어느 층에 붙는지 확인합니다. 층 이름만 보고 짐작하면
   틀립니다. **예시**: 현재 위치 마커는 캔버스나 맵 SVG가 아니라 이름만 보면 스쿼드 기능 같은
   `.squad-layer`에 붙었습니다. 위치를 한 번 보낸 뒤 `.marker`의 조상 사슬을 찍어 알아냈습니다.

사이트에 비슷한 숨김 기능이 이미 있으면 그것부터 시험합니다(1절의 원칙 1). 다만 무엇을 숨기는지
직접 확인합니다. **예시**: 사이트의 Hide panels 버튼은 좌우 패널만 접고 상단 도구 줄, 가이드 패널,
출처 줄을 남겨 이 용도를 대신하지 못했습니다.

**방법**: 컨테이너의 직계 자식 가운데 남길 층만 적고, 나머지는 `:not()`으로 한꺼번에 숨깁니다.

```javascript
var MAP_LAYER_SELECTORS = ['.map-wrap', 'canvas', '.map-compass-anchor',
                           '.squad-layer', '.popup-layer', ':has(.marker)'].join(', ');
var rule = 'html.tanuki-panels-hidden .map-cont > :not(' + MAP_LAYER_SELECTORS + ')'
         + ' { display: none !important; }';
```

경계는 직계 자식에 둡니다. 그리는 층과 UI가 갈리는 곳이 거기입니다. 더 깊이 내려가면 층 내부
구조까지 알아야 하고, 문서 전체로 넓히면 사이트가 본문 밖에 따로 붙이는 요소까지 판단해야 합니다.
**예시**: 이 사이트는 Nuxt의 Teleport 대상인 `#teleports`를 `body` 바로 아래에 둡니다. 캔버스는
클래스 대신 태그로 적어, 사이트가 캔버스 층을 더해도 남게 합니다.

컨테이너는 정체를 나타내는 클래스로 찾고 상태 클래스는 피합니다. 도구를 켜고 끌 때 클래스 목록이
바뀌는지, 사이트 CSS에 같은 요소의 다른 상태 규칙이 있는지 보면 가릴 수 있습니다. **예시**:
`.pan.map-cont`의 `pan`은 조작 상태 클래스라(사이트 CSS에 `.map-cont.draw`, `.map-cont.edit`이 함께
있음) 규칙은 `.map-cont`에 겁니다.

**실패 모드**: 셋이 알려져 있습니다.

- **실패하는 방향이 뒤집힙니다.** 숨길 것을 나열하면 사이트가 UI를 새로 얹을 때 그 UI가 보이는
  쪽으로 실패합니다. 눈에 띄지만 해롭지는 않습니다. 남길 것을 적으면 사이트가 그리는 층을 새로
  만들 때 그 층이 숨는 쪽으로 실패합니다. 토글을 꺼야 보이는 것이 있으면 그 층을 목록에 추가합니다.
- **핵심 요소가 조용히 사라질 수 있습니다.** 남길 층의 이름이 바뀌면 핵심 요소는 문서에 그대로
  있고 화면에서만 사라집니다. 요소의 존재를 확인하는 코드는 이것을 잡지 못합니다. 핵심 요소를 담은
  층은 `:has(핵심 요소)`를 목록에 넣어 층 이름과 무관하게 남깁니다.
- **`:not()` 목록은 하나라도 해석되지 않으면 규칙 전체가 버려집니다.** 엔진이 `:has()`를 모르면
  숨김이 통째로 사라집니다. 규칙이 실제로 들어갔는지 `style.sheet.cssRules.length`로 확인합니다.

**검증**: 토글을 켠 상태와 끈 상태에서 컨테이너 직계 자식의 계산된 `display`를 모두 찍습니다.
핵심 요소는 [`checkVisibility()`](https://developer.mozilla.org/en-US/docs/Web/API/Element/checkVisibility)로
봅니다. 조상이 가려지면 요소 자신의 계산된 `display`는 그대로 `block`이라 이 절 앞부분의 검증
방법으로는 잡히지 않고, `checkVisibility()`만 false를 돌려줍니다(실측). 두 실패 방향도 직접 만들어 봅니다. 이름 모를
요소를 컨테이너에 붙이면 숨어야 하고, 핵심 요소를 담은 층의 클래스를 바꿔도 남아야 합니다. 창 폭에
따라 다른 UI가 켜지는 사이트라면 그 폭에서도 같은 확인을 반복합니다.

### 5.2 사이트가 열어 둔 전역 함수 호출

**적용 조건**: 사이트에 시킬 일을, 사이트가 이미 그 일을 하는 함수로 전역에 열어 둔 경우입니다.

**방법**: 그 함수를 그대로 부릅니다. 부르기 전에 존재를 확인하고, 실패를 삼키지 않고 로그로 남깁니다.

```javascript
var pilot = window.pilot;
if (!pilot || typeof pilot[methodName] !== 'function') return false;
```

**예시**: 전역 진입점이 있던 판에서는 `window.pilot.positionFromScreenshot`으로 위치를
전달했고, 전역 객체가 없는 판에서는 Nuxt 서비스(`$pilot.positionUpdate`)에서 입력 함수를 찾았습니다.
전달과 복구 구현은 [Pilot 연동 문서](20260817-pilot-bridge.md#지금-구조)를 참고합니다.

**실패 모드**: 전역 함수는 계약이 아니므로 언제든 이름이 바뀌거나 사라집니다. 존재 확인과 실패
로그가 없으면 사이트 변경이 조용한 기능 중단으로 나타납니다.

**검증**: `Object.keys(window.pilot)`를 CDP로 찍어 전역에 무엇이 열려 있는지 조사합니다. 이름만
그럴듯한 값에 속지 않도록 실제 내용까지 확인합니다. **예시**: `window.map`은 사이트의 맵 상태가
아니라 `id="map"`인 요소였습니다.

객체가 있다는 것과 외부에서 입력할 수 있다는 것은 다릅니다. `$pilot`에
`onPositionUpdate`와 `offPositionUpdate`만 있으면 위치 변경을 구독할 수 있을 뿐,
`positionUpdate`나 `positionFromScreenshot`으로 위치를 입력할 수는 없습니다. 객체를 찾았다는
이유로 진입점이 살아 있다고 판단하지 않고, 부를 함수가 실제로 있는지 봅니다.

입력을 받아들였다는 응답도 렌더링 성공과 구분합니다. 내부 좌표와 CSS 위치가 일치해도 마커나
그 상위 요소가 숨겨져 있으면 화면에는 나타나지 않습니다. 새 입력 직후에는 올바른 문서와 맵에서
마커와 방향 표시의 가시성을 확인합니다. 이후의 상태 점검에서는 사용자가 지도를 끌어 마커를
화면 밖으로 옮긴 경우를 구분해야 합니다. 이 상태까지 실패로 처리해 계속 재전송하면 지도가
재센터링돼 사용자의 탐색을 방해합니다.

<!--
INTENT: 사이트가 프로그램용 진입점을 모두 없앴을 때 쓴 복구 기법이다. 압축된 번들에서 무엇이 배포를
넘어 살아남는지(템플릿의 prop 이름)를 근거로 삼은 이유와, 이 기법도 결합을 하나 더 만든다는 한계를
함께 남긴다. 5.2의 하위 절로 두어 뒤 절 번호를 바꾸지 않는다.
-->
#### 진입점이 사라졌을 때: 화면 컴포넌트의 처리기 부르기

**적용 조건**: 사이트가 프로그램용 진입점을 없앴지만, 사용자가 같은 일을 하는 UI는 남은 경우입니다.
그 UI가 부르는 처리기를 제어 측이 같은 인자로 부르면, 입력란에 글자를 흉내 내 넣지 않고도 사이트가
그 일을 원래 경로대로 처리합니다.

**진단**: 세 가지로 "사이트 기능이 죽었다"와 "진입점만 사라졌다"를 가릅니다.

1. 같은 입력을 사이트 UI로 직접 넣어 봅니다. UI로는 되고 제어 측 호출만 안 되면 사이트 기능은
   살아 있고 진입점만 바뀐 것입니다. 파일 감지나 입력 데이터부터 의심하지 않습니다.
2. 전역 객체와 서비스 객체의 키를 찍어 입력 함수와 구독 함수를 나눕니다.
3. 그 UI 요소에서 컴포넌트 트리를 거슬러 올라가며 각 컴포넌트의 props를 찍어, 입력을 처리하는
   함수 prop과 그 결과를 담는 상태 객체 prop을 찾습니다.

**예시**: 위치 입력 함수가 모두 사라진 판에서도 상단 패널의 "Where am i" 창은 스크린샷 파일명을
붙여 넣으면 위치를 표시했습니다. 그 패널 컴포넌트의 props에 붙여 넣기 처리기
`onScreenPositionChange`와 표시 상태를 담은 `playerData`가 있었습니다.

**방법**: Vue 3 앱이면 루트 요소에 붙은 `_vnode`에서 시작해 `component.subTree`,
`suspense.activeBranch`, `children`을 따라 내려가며 조건에 맞는 props를 찾습니다.

```javascript
function findProps(predicate) {
    const nodes = [document.getElementById('__nuxt')?._vnode];
    const seen = new Set();
    for (let i = 0; i < nodes.length; i++) {
        const node = nodes[i];
        if (!node || typeof node !== 'object' || seen.has(node)) continue;
        seen.add(node);
        if (node.props && predicate(node.props)) return node.props;
        nodes.push(node.component?.subTree, node.suspense?.activeBranch);
        if (Array.isArray(node.children)) nodes.push(...node.children);
    }
    return null;
}

// 이름 하나가 아니라 함수 prop, 상태 객체, 그 안의 키를 함께 걸어 다른 컴포넌트를 고르지 않는다
const panel = findProps(props => typeof props.onScreenPositionChange === 'function'
    && props.playerData && 'isPlayerMarkerVisible' in props.playerData);
panel.onScreenPositionChange({ target: { value: filename } });   // UI가 넘기는 모양 그대로
```

근거를 prop 이름에 두는 이유는 압축이 무엇을 남기는지에 있습니다. 압축은 지역 변수, setup 안의
함수 이름, 청크 파일 이름을 배포마다 바꾸지만, 템플릿이 자식 컴포넌트에 넘기는 prop 이름은 컴포넌트
사이의 계약이라 그대로 남습니다. Vue 3는 부모 템플릿의 이벤트 리스너도 `on` 접두사가 붙은 prop으로
넘기므로(`@screen-position-change` -> `onScreenPositionChange`) 사용자 입력 처리기를 이 방식으로 찾을
수 있습니다([Vue 3 이전 안내: `$listeners` 제거](https://v3-migration.vuejs.org/breaking-changes/listeners-removed.html)).
찾은 결과는 캐시하지 않습니다. 같은 주소에서 컴포넌트만 교체되면 옛 props가 남아, 사라진 화면에
입력을 넣게 됩니다.

처리기가 UI의 다른 상태에 기대는지도 봅니다. **예시**: 붙여 넣기 처리기는 좌표만 바꾸고 마커는
"Where am i" 창이 열린 동안만 보였습니다. 그래서 프로그램용 입력이 하던 것과 같은 표시 상태
(`playerData.isPlayerMarkerVisible`)를 켜고, 새 입력일 때만 사이트의 위치 핑 처리기도 불렀습니다.
같은 입력을 다시 보낼 때마다 핑을 켜면 6절의 "다시 보내는 입력" 실패가 생깁니다.

**실패 모드**: 셋이 알려져 있습니다.

- 이 기법도 결합을 하나 더 만듭니다. 사이트가 컴포넌트를 나누거나 prop 이름을 바꾸면 찾지 못합니다.
  진입점마다 어댑터를 두고 첫 번째로 찾은 것을 쓰며, 하나도 없으면 그 상태를 이름으로 드러냅니다.
  조용히 실패하지 않으면 다음 배포에서 무엇이 바뀌었는지 바로 알 수 있습니다.
- 입력란에 글자를 넣는 합성 입력은 UI를 열어야 하고, 앱이 UI를 숨기는 기능과 충돌합니다.
- 처리기 대신 그 처리기가 바꾸는 상태를 직접 쓰면 사이트의 갱신 경로를 건너뛰어 5.9절의 어긋남이
  생깁니다.

핵심 기능을 이런 결합 위에만 두면 사이트가 바뀔 때마다 그 기능이 함께 멈춥니다. 핵심 기능에는
사이트 런타임 없이 도는 대체 경로를 따로 둡니다. **예시**: 이 저장소의 Local 모드는 사이트의 지도
데이터만 받아 앱이 직접 그립니다([로컬 맵 뷰어 설계](20260821-local-viewer-design.md)). 입력 경로가 거듭
바뀌면 결합 자체를 줄이는 쪽도 검토합니다. 이 저장소는 결국 Online에서도 처리기에 입력을 넣지 않고, 사이트의
투영 함수만 빌려 제어 측이 표시를 그리게 바꿨습니다(5.7절).

**검증**: 같은 입력을 사이트 UI와 처리기 호출로 각각 넣어 결과 상태와 화면이 같은지 봅니다. 진입점이
있던 판과 사라진 판을 작은 재현 페이지로 만들어 어댑터가 각각 맞는 경로를 고르는지 회귀 검사합니다.
처리기는 앱이 쓰지 않게 된 뒤에도 검사의 기준으로 쓸 수 있습니다. **예시**:
[verify-online.mjs](../tools/verify-online.mjs)는 같은 파일명을 "Where am i" 처리기로도 넣어 사이트가 그린 원과
앱이 그린 원이 겹치는지 비교합니다.

### 5.3 번들에서 라이브러리 식별

**적용 조건**: 사이트의 동작을 정확히 예측해야 하는 경우입니다. 휠 한 칸이 몇 배인지, 드래그가
커서와 1:1인지 같은 값이 여기에 해당합니다.

**방법**: 사이트가 받은 번들을 저장해 두고 문자열로 찾습니다. 최소화된 코드라도 원본
라이브러리의 특징적인 문자열(옵션 이름, 이벤트 이름, 오류 문구)은 남아 있어 어떤 라이브러리인지
알아낼 수 있고, 라이브러리를 알면 그 소스를 읽어 규칙을 확정할 수 있습니다.

**예시**: 대상 사이트가 맵 이동에 anvaka/panzoom을 다음 옵션으로 쓴다는 것을 번들에서
확인했습니다.

```
panzoom(.map-wrap, { autocenter: true, bounds: true, smoothScroll: false,
                     minZoom, maxZoom, zoomDoubleClickSpeed: 1,
                     beforeMouseDown, beforeWheel })
```

옵션 목록과 라이브러리 소스에서 세 규칙이 나옵니다. `smoothScroll: false`라 손을 뗀 뒤 관성이 없고, 이동은 커서와
1:1이며, `beforeMouseDown`이 사이트 상태를 보고 이동을 막을 수 있습니다.

**실패 모드**: 최소화된 식별자(`ht`, `pt`, `ve`)는 빌드마다 바뀝니다. 식별자를 근거로 삼으면
다음 배포에서 근거가 사라집니다. 근거는 알아낸 규칙에 두어야 실측으로 다시 확인할 수 있습니다.

**검증**: 알아낸 규칙을 페이지에서 직접 재 봅니다. "휠 한 칸이 1.25배"는 소스를 읽어 얻은
값이지만, 실제로 한 칸 보내고 폭을 재서 확정합니다.

### 5.4 입력을 가로채 고쳐 보내기

**적용 조건**: 사이트의 동작은 그대로 두되, 사용자가 만든 입력에 제어 측 규칙을 얹는
경우입니다. **예시**: "맵을 끌어도 화면 한가운데에는 언제나 맵이 있어야 한다"는 제한.

**방법**: 캡처 단계에서 사이트보다 먼저 이벤트를 받아, 필요하면 좌표를 고친 복제 이벤트를 대신
보냅니다.

```javascript
// 캡처 단계에서 먼저 받는다
window.addEventListener('mousemove', onMove, true);

function onMove(event) {
    if (!dragging || event[OURS]) return;      // 복제 이벤트는 그냥 흘려보낸다
    // ...허용량 계산...
    if (nextX === event.clientX && nextY === event.clientY) return;  // 고칠 게 없으면 원본 통과

    event.stopImmediatePropagation();
    event.preventDefault();
    replaceMove(event, nextX, nextY);          // 고친 좌표로 다시 보낸다
}
```

**실패 모드**: 셋이 알려져 있습니다.

- **복제 이벤트를 자기 처리기가 다시 가로챕니다.** 복제 이벤트에 표시를 남기지 않으면 처리기가
  그것을 또 줄여 사이트에 아무것도 닿지 않습니다. 이벤트 객체에 속성 하나를 붙여 표시합니다.
- **원래 이벤트의 `target`으로 다시 보내면 튑니다.** 커서가 창 밖으로 나가면 그 자리에 요소가
  없어 이벤트가 사이트에 닿지 않고, 사이트가 기억하는 커서 위치가 멈춰 있다가 커서가 돌아오는
  순간 그 차이만큼 한꺼번에 움직입니다. 맵 컨테이너처럼 사라지지 않는 요소로 보내면 사이트가
  어디에 처리기를 달았든 그 위로 전파됩니다.
- **막은 양을 기억하지 않으면 경계에서 밀립니다.** 경계에서 막기만 하면 사용자가 커서를 되돌릴
  때 그동안 벌어진 차이가 한꺼번에 반영됩니다. 넘기지 못한 양을 누적해 두고 커서가 돌아올 때
  상쇄하면 경계에서 즉시 따라옵니다.

**검증**: 커서를 100px씩 옮기며 맵이 몇 px 움직이는지 기록합니다. 경계 전에는 100, 경계에서는
줄어든 값, 되돌릴 때는 다시 100이 나와야 정상입니다.

### 5.5 합성 입력으로 정확히 조작하기

**적용 조건**: 사이트에 특정 배율과 위치를 만들어야 하는 경우입니다. 맵을 열 때 그림이 창을
채우게 맞추는 일이 여기에 해당합니다.

**방법**: 사이트가 이미 처리하는 입력을 만들어 보냅니다. 성패는 어떤 입력을 고르는지가
가르므로, 사이트가 조건에 따라 차단하는 입력을 피하고 차단이 없는 입력을 고릅니다.

**예시** (입력 선택): 드래그는 버리고 휠로 맞춥니다. 사이트는 누른 자리에
마커나 그린 도형이 있으면 그것을 옮기는 동작으로 보고 맵 이동을 꺼 버립니다(번들의 마커 층
`mousedown`에서 `togglePanEnabled(false)`). 중심을 맞추려면 화면 한가운데에서 끌어야 하는데 그
자리가 바로 마커가 몰려 있는 자리라, 맵과 위치에 따라 되기도 하고 안 되기도 합니다. 신뢰
입력과 합성 입력이 똑같이 막히므로 입력 종류의 문제가 아닙니다(4절). 휠에는 그 차단이 없습니다.

휠 한 칸은 커서 자리 `a`를 고정점으로 삼아 위치를 다음과 같이 바꿉니다.

```
x' = r * x + (1 - r) * a
```

배율만 필요하면 그림 중심을 고정점으로 두고 한 칸씩 보냅니다. 위치만 필요하면 축소 한 칸과
확대 한 칸을 서로 다른 자리에서 연달아 겁니다.

```
축소(r) at a, 확대(1/r) at b
  ->  x'' = x + (1/r - 1) * (a - b)
  r = 0.8 이면 x'' = x + (a - b) / 4
```

배율은 `0.8 x 1.25 = 1`로 정확히 돌아오고 평행이동만 남으므로, 옮길 거리의 4배만큼 떨어진
자리를 고르면 원하는 만큼 옮겨집니다. 한 칸의 배율 `r`는 라이브러리가 `deltaY`로 정합니다.

**예시** (배율 값): anvaka/panzoom은 `1 - sign(deltaY) * min(0.25, |deltaY| / 128)`을 쓰므로
`deltaY = 25.6`이면 0.8배, `deltaY = -32`이면 1.25배입니다. 두 값이 서로의 역수라는 점이 위
짝을 성립시킵니다. 실측에서 목표 200,120에 결과 200,120, 배율 변화 없음을 확인했습니다.

**실패 모드**: 셋이 알려져 있습니다.

- 두 칸을 시간 간격을 두고 보내면 중간의 축소된 화면이 한 번 그려집니다. 같은 틱에 연달아
  보내면 사용자는 최종 상태만 봅니다.
- 제어 측 조작과 사용자 조작이 겹치면 화면이 손 아래에서 움직입니다. 사용자가 직접 끌거나 휠을
  돌리면(`event.isTrusted`가 true) 그 뒤로는 제어 측 조작을 중단합니다. 제어 측이 보낸 이벤트는
  `isTrusted`가 false라 이 판정에 걸리지 않습니다.
- **배율 한계에서는 짝이 깨집니다.** 짝은 두 칸이 모두 온전히 적용된다는 전제에서만 배율이 제자리로
  돌아옵니다. 라이브러리의 최소 배율에 닿아 있으면 축소 칸이 막히고 확대 칸만 적용되어, 배율은 한
  칸만큼 올라가고 평행이동은 식과 다르게 나옵니다. 지형이 최소 배율에서도 창보다 큰 맵에서 맞추기가
  끝난 자리가 바로 이 상태라, 가운데 맞추기가 수렴하지 않고 배율이 칸마다 올라갔습니다.

<!--
INTENT: 휠 짝은 사이트 객체에 손댈 수 없을 때의 우회였다. 라이브러리의 이동 함수에 닿을 수 있으면
그쪽이 배율 한계와 무관하게 정확하므로 고르는 순서를 남긴다.
-->
위치를 옮기는 데는 라이브러리 인스턴스의 이동 함수에 닿을 수 있으면 그것을 먼저 씁니다. 휠 짝은
인스턴스에 닿을 길이 없을 때의 우회입니다. **예시**: 5.2절의 방법으로 지도 컴포넌트의 props에서
지도 객체를 얻으면 그 안의 panzoom 인스턴스가 있고, `panzoom.moveBy(dx, dy, false)`는 배율을
건드리지 않고 옮깁니다. 사이트 자신이 쓰는 라이브러리의 함수라 변환이 바뀌면 사이트가 캔버스와
마커를 함께 다시 그리므로, 5.9절의 금지 기법과 달리 층이 어긋나지 않습니다. 배율은 지금도 휠
한 칸씩 맞춥니다. 휠은 커서 자리를 고정점으로 삼는 사이트의 확대 경로를 그대로 탑니다.

**검증**: 그림이 창에서 차지하는 비율과, 그림 중심과 창 중심의 어긋남을 재서 숫자 합격선을
넘는지 봅니다(7절). **예시**: 맵 12개 전부에서 채움 비율 0.75~0.98, 중심 어긋남 3px 이내를
합격선으로 잽니다.

### 5.6 네트워크 요청 가로채기

**적용 조건**: 대상 사이트가 죽어도 호스트 앱이 돌아야 하는 경우입니다.

**방법**: 브라우저 엔진의 요청 가로채기로 미리 저장해 둔 응답을 돌려줍니다. CefSharp에서는
`IResourceRequestHandlerFactory`가 그 자리입니다. 사본은 실제 브라우저로 페이지를 열어 받은
응답을 그대로 저장해 만들며, 사이트 코드가 무엇을 필요로 하는지 제어 측이 알아낼 필요가 없다는
것이 이 방식의 핵심입니다. 주소는 온라인과 같게 두고 응답만 바꿉니다.

**실패 모드**: 셋이 알려져 있습니다.

- 커스텀 스킴을 만들면 사이트의 라우팅과 주입 스크립트의 주소 판정이 모두 어긋납니다. 주소를
  온라인과 같게 두는 이유가 이것입니다.
- 사본은 사이트 런타임을 통째로 담으므로, 사이트가 진입점이나 렌더링 구조를 바꾼 판을 다시 받으면
  사본에서도 같은 기능이 깨집니다. 네트워크 장애는 막아도 사이트 변경은 막지 못합니다.
- 압축된 번들 덩어리라 무엇이 들었는지 읽을 수 없고, 갱신의 diff가 의미를 주지 않습니다.

사이트 변경까지 견뎌야 하는 기능이면, 사이트에서 데이터만 받아 제어 측이 직접 그리는 쪽이
맞습니다. 대신 그리는 코드와 데이터 변환기를 제어 측이 유지합니다. **예시**: 이 저장소의 Local
모드는 처음에 이 기법을 썼다가 데이터만 받아 그리는 미니맵으로 옮겼습니다
([로컬 맵 뷰어 설계](20260821-local-viewer-design.md)).

**검증**: 사본만으로 응답하는 상태에서 페이지가 온라인과 같이 동작하는지 봅니다. 설계와 한계는
[오프라인 맵 설계](20260818-offline-map.md)에 있습니다.

함수 하나만 빌리고 제어 측이 그리는 구조로 옮기는 판단 근거, 방법, 대가를 남긴다. 표시가 DOM에서 캔버스로
옮겨 가 덧붙일 요소가 사라진 경우도 같은 방법으로 푼다.

### 5.7 핵심 표시는 직접 그리고 투영만 빌리기

**적용 조건**: 끊기면 안 되는 표시(내 위치 같은)를 사이트에 입력을 넣어 사이트가 그리게 하고 있고, 그 입력
경로나 사이트의 그리기 방식이 배포마다 바뀌는 경우입니다. 사이트가 표시를 DOM 요소 대신 캔버스에 그려 그
요소에 정보를 덧붙일 수 없게 된 경우도 여기에 해당합니다. 표시가 사이트 화면(지형, 배율, 회전)과 함께
움직여야 하므로, 사이트의 좌표 투영 함수에는 닿을 수 있어야 합니다.

**진단**: 표시 하나가 사이트의 무엇에 기대는지 나눠 적고, 그 가운데 무엇이 배포마다 바뀌었는지 이력과
번들에서 확인합니다. 덧붙이던 요소가 페이지에 없으면 컨테이너의 직계 자식을 나열해 어느 캔버스가 그 표시를
그리는지 보고, 번들에서 그 캔버스의 그리기 함수가 무엇을 조건으로 그리는지 읽습니다. **예시**: 내 위치
표시는 입력 경로(전역 함수, 서비스, 화면 처리기), 사이트의 내 위치 렌더러, 지도 상태의 좌표 변환에
기댔습니다. 앞의 둘은 배포마다 바뀌었고(렌더러는 DOM 요소에서 `players-canvas`로 옮기며 방향 화살표를 PRO
사용자에게만 그리게 바뀜), 좌표 변환은 같은 이름으로 남았습니다.

**방법**: 입력 해석과 그리기는 제어 측이 맡고, 사이트에서는 투영 함수와 표시를 얹을 컨테이너만 빌립니다.

- 입력은 제어 측이 직접 해석합니다. 대체 경로(사이트 없이 도는 모드)가 있으면 그 경로와 같은 해석을 쓰고
  두 해석을 대조하는 검사를 둡니다. 두 경로가 같은 입력을 다르게 읽으면 사용자는 어느 쪽을 믿을지 모릅니다.
- 자리는 사이트의 투영 함수(이 사이트는 지도 상태의 `gamePosToMapPos`와 `mapPosToScreenPos`)로 구합니다.
  사이트와 같은 함수를 쓰므로 확대, 이동, 회전이 지형과 함께 맞고, 사이트가 식을 바꿔도 따라갑니다. 투영
  결과의 원점은 컨테이너 안쪽의 왼쪽 위이므로 요소도 컨테이너를 기준으로 배치합니다. 방향처럼 각도가 필요한
  값도 각도 식을 옮겨 오지 않고 방향 벡터를 같은 함수로 투영해 구합니다.
- 투영 함수를 다시 구현하지 않습니다. 대체 경로의 데이터로 같은 식을 만들 수 있어도, 사이트가 식이나
  데이터를 바꾸면 표시가 지형과 어긋난 채 경고 없이 남습니다. 투영 함수를 잃으면 그리지 않고 상태 이름으로
  알립니다. 틀린 자리를 확신 있게 보여 주는 것보다 안전합니다.
- 사이트의 표시를 남긴 채 정보만 덧붙이는 방법(사이트가 그린 원 앞에 화살표만 얹기)은 그 표시의 크기와
  그리는 조건에 다시 묶입니다. 핵심 표시라면 전부 그립니다.
- 투영 함수를 가진 상태가 렌더 트리에 없으면 5.8절의 방법으로 얻습니다. 기록 조건은 실제로 쓰는 칸만으로
  정합니다. 쓰지 않는 칸까지 요구하면 사이트가 그 칸만 바꿔도 핵심 표시가 멈춥니다.
- 사이트는 다시 그릴 때 밖에 알리지 않습니다. 대상 지도가 화면에 붙어 있는 동안 매 프레임 자리를 다시
  구하고, 값이 달라진 프레임에만 DOM을 갱신합니다. 대상이 끝나면(다른 화면으로 이동, 지도 제거) 루프를
  멈추고 다시 맡을 때 시작합니다. 같은 화면에서 사이트가 상태를 새로 만들면 지난 상태의 투영은 더 갱신되지
  않으므로, 화면에 붙은 가장 새 상태일 때만 그립니다.
- 표시 요소는 사이트의 표시 층 위, 설명 창 같은 UI 층 아래에 둡니다. 숨김 규칙이 화이트리스트라면(5.1절)
  표시 요소를 남길 층 목록에 추가합니다. 추가하지 않으면 UI 숨김을 켤 때 함께 사라집니다.
- 스타일은 요소의 인라인 `!important`로 지정합니다. 스타일시트를 따로 두면 그 스타일시트까지 복구해야 합니다.
  애니메이션할 속성만 `!important`에서 뺍니다. `!important` 선언은 애니메이션보다 우선해 효과가 보이지 않습니다.
- 사이트의 다른 기능이 그 값에 기대면 그 값만 사이트의 입력 상태로 넘겨 사이트가 계속 하게 합니다. 사이트의
  표시 상태는 켜지 않으므로 표시가 두 벌이 되지 않습니다. 어떤 기능이 그 값에 기대는지는 입력 처리기가 아니라
  그 값을 지켜보는 곳을 찾아야 보입니다(6절의 "기능은 상태를 지켜보는 곳에 있을 수 있습니다").

**예시**: Online의 내 위치는 앱이 파일명을 읽고(Local 미니맵과 같은 식), 지도 컨테이너에 얹은 원 요소
하나(안에 방향 삼각형)를 사이트의 좌표 변환으로 구한 자리에 매 프레임 맞춥니다. 모양과 핑은 Local 미니맵과
같고, 사이트의 위치 입력 경로, 내 위치 렌더러, 핑, 표시 상태는 쓰지 않습니다. 층은 사이트가 `playerPos`의
변화로 고르므로 같은 좌표를 `playerPos`에도 넣습니다.

**대가**: 사이트는 제어 측이 그린 표시를 모릅니다. 사이트에서 그 값에 기대는 기능 가운데 넘기지 않은 것(이
사이트는 스쿼드 공유와 사이트 UI의 위치 표시)에는 반영되지 않습니다. 투영 함수를 잃으면 이전 구조에서는
사이트가 표시만이라도 그렸지만, 이 구조에서는 아무것도 그리지 않습니다. 그래서 그 상태를 이름으로 드러내고
대체 경로를 둡니다.

**실패 모드**:

- 투영 함수의 이름이나 인자가 바뀌면 그리지 못합니다. 이름은 같은데 의미(축 순서 같은)가 바뀌면 틀린 자리에
  그리므로, 사이트가 같은 입력으로 그리는 결과와 대조하는 검사를 둡니다.
- 매 프레임 루프는 비용이 작아도 계속 돕니다. 대상이 끝났을 때 멈추는 조건을 함께 둡니다.

**검증**: 표시 요소가 스스로 보고하는 값이 아니라 요소의 화면 위치(`getBoundingClientRect`)로 판정합니다.
사이트가 같은 입력으로 직접 그리는 결과가 있으면 그 결과와 겹치는지 비교하고, 방향은 제어 측의 투영과 다른
경로(사이트의 그리기 식)로 구한 각도와 비교합니다. 이동과 회전 뒤에도 같은 판정을 반복합니다. **예시**:
[verify-online.mjs](../tools/verify-online.mjs)는 같은 파일명을 사이트의 "Where am i" 처리기에도 넣어 사이트가
그린 원의 픽셀 중심과 앱이 그린 원의 중심을 1.5px 안에서 비교하고, 삼각형의 각도를 사이트가 방향 화살표를
그리는 식(시선 + 270 - 지도 회전 + 화면 회전)과 3도 안에서 비교합니다. 층이 여럿인 맵에서는 기본 층이 아닌
위치를 맵을 열자마자 보내고, 사이트가 가진 층 데이터에 같은 판정 식을 적용한 층으로 바뀌었는지 봅니다.
[verify-map-recovery.mjs](../tools/verify-map-recovery.mjs)는 Online과 Local의 파일명 해석을 대조합니다.

### 5.8 만들어진 뒤 닿지 않는 상태: 만들어지는 순간에 기록하기

**적용 조건**: 제어 측이 읽어야 하는 사이트의 내부 상태(좌표 변환 함수, 현재 위치 같은 값)가 렌더
트리 어디에도 없고 클로저 안에만 있는 경우입니다. 하위 컴포넌트에 상태 대신 getter만 가진 얼린
객체(파사드)를 넘기는 구조가 여기에 해당합니다.

**진단**: "상태가 없어졌다"와 "상태가 숨었다"를 가립니다.

1. 번들에서 그 상태를 만드는 코드를 찾습니다. 압축해도 객체 리터럴의 키 이름은 남으므로, 전에 읽던
   필드 이름으로 검색합니다.
2. 렌더 트리의 모든 컴포넌트에서 props, `setupState`, `provides`, `exposed`를 깊이 우선으로 훑어 그
   모양의 객체를 찾습니다. 어디에도 없고 하위 컴포넌트가 받는 객체가 getter만 가진 `Object.freeze`
   결과라면 상태는 클로저 안에만 있습니다. `<script setup>`을 인라인 템플릿으로 빌드하면 `setup()`이
   렌더 함수를 돌려주므로 `setupState`도 비어 있습니다.
3. getter와 클로저가 붙든 값은 바깥에서 꺼낼 수 없습니다. 이 단계에서는 상태를 찾는 방법이 없고
   만들어질 때 잡는 방법만 남습니다.

**예시**: 2026-10 판의 지도 페이지는 지도 상태를 `reactive({ cont, zoom, x, y, playerPos, marker,
panzoom, gamePosToMapPos, mapPosToScreenPos, ... })`로 만들고, 하위 컴포넌트에는
`Object.freeze({ get state() { ... }, rotateView, centerMap, ensureElementVisible })`만 넘겼습니다.
렌더 트리의 모든 컴포넌트를 훑어도 지도 상태는 나오지 않았습니다.

**방법**: Vue 3의 `reactive(target)`은 프록시를 만든 뒤 원본을 키로, 프록시를 값으로 WeakMap에
등록합니다. 같은 원본에 같은 프록시를 돌려주려는 캐시입니다. 이 등록은 `WeakMap.prototype.set`을
거치므로, 페이지 스크립트보다 먼저 그 메서드를 감싸면 상태가 만들어지는 순간을 볼 수 있습니다.

```javascript
const hasOwn = Object.prototype.hasOwnProperty;
const nativeSet = WeakMap.prototype.set;
WeakMap.prototype.set = function set(key, value) {
    const result = nativeSet.call(this, key, value);   // 원래 동작과 반환값은 그대로 둔다
    // 키(원본)와 값(프록시)이 모두 그 모양일 때만 기록한다. 같은 원본을 키로 쓰는 의존성 표의 값은 걸러진다
    if (value !== key && isMapState(key) && isMapState(value)) records.push(new WeakRef(value));
    return result;
};
```

- 모양은 키 하나가 아니라 여러 키로 판정합니다. 다른 객체를 기록하면 엉뚱한 상태로 위치를 그리게
  됩니다. 키는 제어 측이 실제로 쓰는 칸에서 고릅니다. 쓰지 않는 칸까지 요구하면 사이트가 그 칸만 바꿔도
  기록이 빕니다. 칸이 처음부터 `null`로 만들어지는 상태라면 함수가 들어오기 전인 등록 순간에도 판정할 수
  있습니다.
- 키가 있는지는 `in`이 아니라 `hasOwnProperty`로 확인합니다. `in`은 Vue 프록시의 `has` 트랩을 거쳐,
  그 순간 실행 중인 반응형 효과에 의존성을 추가할 수 있습니다.
- 원본이 아니라 프록시를 기록합니다. 사이트의 함수들은 프록시로 상태를 읽고 쓰므로 같은 값을 봅니다.
- 약한 참조(`WeakRef`)로 보관합니다. SPA에서 화면을 옮길 때마다 새 상태가 생기므로, 강한 참조로 모으면
  버린 화면이 메모리에 남습니다.
- 사용할 때는 화면에 붙은(`cont.isConnected`) 상태 가운데 가장 나중에 만든 것을 고릅니다. 새 화면의
  상태는 화면에 붙기 전에 만들어지고, 그동안 이전 화면이 남아 있습니다.
- 같은 등록에서 다른 상태도 기록할 수 있습니다. 모양 판정은 원본(키)만 읽습니다. 프록시를 읽으면 그 순간의
  반응형 효과에 의존성이 더해질 수 있습니다. 판정할 값이 많은 표라면 첫 항목에서 걸러지게 써서, 잦은 등록마다
  큰 객체를 끝까지 훑지 않게 합니다. **예시**: 지도 상태와 함께 층 데이터 표(층 이름마다 `num`과 `visible`을
  가진 표)를 기록해, 사이트가 층 데이터를 채웠는지 브리지가 확인합니다.

**주입 시점**: 페이지 스크립트가 상태를 만들기 전이어야 하므로 로드가 끝난 뒤 주입하는 일반 경로(3절)로는
늦습니다. CDP는 `Page.addScriptToEvaluateOnNewDocument`, WebView2는
`AddScriptToExecuteOnDocumentCreatedAsync`로 문서가 만들어질 때 실행할 스크립트를 등록합니다. CefSharp의
`FrameLoadStart`에서 `IFrame.ExecuteJavaScriptAsync`를 호출하는 방법은 탐색이 확정된 직후에 실행됩니다.
모듈 스크립트는 문서 파싱이 끝난 뒤 실행되므로 대개 그보다 앞서지만, 앞의 두 방법과 달리 순서를
보장하지 않습니다. 그래서 기록 스크립트가 없는 경우와 기록이 빈 경우를 서로 다른 상태 이름으로 남깁니다.
**예시**: 이 저장소는 `FrameLoadStart`에 `map-state-capture.js`를 주입하고, 브리지가
`map-unavailable (capture-missing)`과 `map-unavailable (not-captured)`로 두 경우를 구분합니다. 실제 사이트
검사([verify-online.mjs](../tools/verify-online.mjs))는 `Page.addScriptToEvaluateOnNewDocument`로 같은
스크립트를 주입합니다.

**실패 모드**:

- 내장 메서드를 감싸므로 영향 범위가 넓습니다. 원래 메서드를 같은 `this`와 인자로 호출하고 반환값을
  그대로 돌려주며, 판정에서 부수 효과를 만들지 않습니다.
- 사이트가 상태를 reactive 객체로 만들지 않거나 키 이름을 변경하면 기록이 비고, 그 상태에 기대는
  기능은 확인 단계에서 멈춥니다. 그때는 번들에서 상태를 만드는 코드를 다시 찾는 데서 시작합니다.
- 주입이 늦으면 그 문서에서는 다시 기록할 기회가 없고, 새로고침해야 회복합니다.

**검증**: 재현 페이지에서 원본과 프록시를 WeakMap에 등록해 상태를 만들고, 기록에서 그 프록시를 찾는지,
`set`의 반환값과 `get`, `has`가 그대로인지, 다른 모양의 객체를 기록하지 않는지 봅니다. 기록 스크립트를
상태보다 늦게 주입한 경우도 재현해 상태 이름을 확인합니다. 실제 사이트에서는 문서가 만들어질 때
실행되는 스크립트로 주입하고 기록의 개수와 필드를 찍습니다. 재현 페이지는 사이트처럼 프록시를 붙들고 있어야
합니다. 등록에만 쓰고 놓아 버린 프록시는 가비지 컬렉션으로 사라져, 약한 참조 기록이 비어 기록에 실패한
것처럼 보입니다.

### 5.9 금지 기법: 사이트 상태 직접 수정

**적용 조건**: 없습니다. 가장 먼저 떠오르는 방법이지만, 다른 기법이 모두 막혀도 이 방법으로
내려가지 않습니다.

**방법**: 사이트가 내부 상태에서 계산해 그리는 값(CSS `transform` 같은 렌더 산출물)을 제어 측이
직접 쓰는 방식을 말합니다. 쓰지 않습니다.

**실패 모드**: 렌더 층이 둘 이상인 화면에서 한 층만 고치면 반드시 어긋납니다. 사이트의 입력
경로로 들어가면 사이트가 모든 층을 함께 갱신합니다(1절의 원칙 1). **예시**: 맵을 옮기려고
`.map-wrap`의 CSS `transform`을 직접 쓰면 마커만 움직이고 바닥 맵은 그대로 남습니다. 이 사이트는
바닥 맵을 `canvas`에 그리고 마커는 CSS `transform`으로 옮기는데, 둘 다 사이트의 내부 상태에서
나오기 때문입니다.

<!--
INTENT: 이 절의 금지와, 입력 처리기가 쓰는 반응형 입력 상태에 같은 값을 넣는 일(5.7절의 예시)을 구별한다.
둘을 섞으면 "상태를 쓰면 안 된다"를 근거로 더 약한 결합을 버리거나, 반대로 파생 값까지 쓰게 된다.
-->
입력 상태와는 구별합니다. 사이트의 입력 처리기가 그대로 쓰는 반응형 입력 상태(이 사이트의 `playerPos`)는
처리기를 거치지 않고 같은 프록시로 써도 사이트의 watcher가 거기서 나머지 층을 다시 계산하므로 어긋나지
않습니다. 처리기에 닿기 어렵거나 처리기가 원하지 않는 다른 효과를 함께 낼 때 이 길을 씁니다. 그 값에서
계산되는 파생 상태(이 사이트의 `selectedLevel`)와 렌더 산출물은 여전히 쓰지 않습니다. 파생 상태를 쓰면 그 값을
계산하는 원래 상태(선택한 층)와 그 원래 상태를 보는 다른 기능(Levels 패널, 마커 필터)이 어긋납니다.

**검증**: 층의 어긋남은 좌표 수치로 잡히지 않고 스크린샷(7절)에서 드러납니다.

## 6. 실패 모드 색인

아래 표는 이 방식의 작업에서 반복해 나타나는 실패를 증상, 원인, 규칙으로 정리한 색인입니다.
증상으로 찾고 규칙 열이 가리키는 절에서 배경을 봅니다. 규칙 열에 절 번호가 없는 줄은 표 아래에서
부연합니다.

| 증상 | 원인 | 규칙 |
|---|---|---|
| 마커만 움직이고 바닥 맵은 그대로 | 렌더 층 두 개 중 하나만 수정 | 상태 대신 입력으로 조작 (5.9절) |
| 숨긴 요소가 되살아남 | 다른 스크립트의 `style.cssText` 대입 | `!important` 스타일시트로 숨김 (5.1절) |
| 사이트가 UI를 더할 때마다 숨김 규칙을 고침 | 숨길 요소를 나열한 규칙 | 컨테이너 직계 자식 중 남길 층만 적기 (5.1절) |
| 토글을 켜면 핵심 요소만 사라짐 | 남길 층 목록에서 빠진 층 | `:has()`로 담은 층 보호, `checkVisibility()`로 검증 (5.1절) |
| 디버그 빌드는 정상, 릴리즈만 깨짐 | UI 프레임워크 속성의 갱신 지연 | 엔진 인스턴스와 이벤트 인자로 판정 (3절) |
| 제어 측 조작이 사이트에 전혀 닿지 않음 | 자기가 만든 복제 이벤트를 다시 가로챔 | 복제 이벤트에 표시 남기기 (5.4절) |
| 커서를 창 밖으로 뺐다 넣으면 튐 | 사라진 요소로 이벤트 전송 | 사라지지 않는 컨테이너로 전송 (5.4절) |
| 움직임이 진동하고 텔레포트 | 실측 비율로 나눈 값의 폭주 | 나눗셈 대신 상한과 계수 |
| 기록은 정상인데 맵이 작게 뜨고 멀리 끌려감 | 그림을 재던 요소가 사라져 상자로 대신 잼 | 대신하지 말고 멈추기, 그려진 결과로 재기 |
| 맵이 화면 밖으로 사라짐 | 상자 크기로 경계 계산 | 실제 그려진 범위로 계산 |
| 그림 측정이 오류 없이 멈춤 | 같은 클래스의 숨은 캔버스가 먼저 선택됨 | 표시된 후보만 고르고 모호하면 멈추기 |
| 합성 드래그가 맵마다 되고 안 됨 | 누른 자리가 마커면 사이트가 이동을 끔 | 차단 없는 입력(휠)으로 우회 (5.5절) |
| 최소 배율에서 가운데 맞추기가 어긋나고 배율이 오름 | 휠 짝의 축소 칸이 배율 한계에 막힘 | 위치는 라이브러리 이동 함수로 (5.5절) |
| 확대할 때마다 보정이 한 칸씩 늦게 따라옴 | 제어 측 프레임 콜백이 사이트의 갱신보다 먼저 실행 | 사이트가 그린 다음 프레임에 재기 |
| 맞춘 뒤 위치 마커가 화면 밖으로 밀려남 | 맞추기와 위치 표시가 서로 화면을 옮김 | 화면 가운데의 주인을 하나로 정하기 |
| 사이트 진입점 호출이 늘 준비 안 됨으로 끝남 | 사이트가 프로그램용 진입점을 없앰 | 화면 컴포넌트의 처리기 부르기 (5.2절) |
| 조사 브라우저에서만 확인 화면이 뜨거나 데이터가 빔 | User-Agent의 HeadlessChrome, `navigator.webdriver` | 조사 브라우저의 자동화 표시 지우기 (4절) |
| 덧붙이던 표시가 사라지고 위치 확인이 늘 실패함 | 사이트가 표시를 캔버스로 옮기고 상태를 클로저에 숨김 | 상태는 만들 때 기록 (5.8절), 표시는 직접 그리고 투영만 빌리기 (5.7절) |
| 사이트가 배포할 때마다 핵심 표시가 끊김 | 입력 경로와 사이트의 그리기에 함께 기댐 | 바뀌지 않은 투영 함수만 빌리고 나머지는 직접 (5.7절) |
| 입력 전달 방식을 바꾼 뒤 관련 없어 보이는 기능(층 자동 선택)이 멈춤 | 그 기능이 입력 처리기가 아니라 입력 상태를 지켜보는 곳에 있었음 | 상태를 지켜보는 곳을 번들 전체에서 찾기 |
| 화면을 열자마자 넣은 입력에만 사이트가 반응하지 않음 | 사이트가 데이터 도착 전의 변화를 버리고 도착 뒤에 다시 보지 않음 | 데이터 준비 신호를 찾아 그 뒤에 넣기 |
| 새 입력이 없는데 표시가 불규칙한 간격으로 커졌다 줄어듦 | 확인이 늘 실패해 같은 입력을 다시 보내고, 보낼 때마다 주의 표시를 켬 | 주의 표시는 새 입력에만 켜고, 확인 근거를 복구 |

**상자와 그림은 다릅니다.** 요소의 상자와 그 안에 실제로 그려진 그림은 다르며, 화면에 남았는지의
판정은 그림을 기준으로 합니다. 상자를 기준으로 판정하면 상자가 화면 가운데를 덮은 채로 그림만
화면 밖으로 나가는 상태를 정상으로 오판합니다. **예시**: `.map-wrap` 상자는 여백까지 포함한 맵
좌표 공간 전체(Ground Zero는 2800x3100)이고 실제 그림은 그 안의 일부(800x1100)뿐입니다. 그림 범위는 SVG
자식들의 `getBBox()`를 합쳐 구하고, 뷰박스의 98% 이상을 덮는 자식은 배경이므로 제외합니다.

<!--
INTENT: 그림을 재는 요소가 사라진 사건에서 일반 규칙만 남긴다. 대체값으로 조용히 넘어가는 코드가
사이트 변경을 숨긴다는 점과, 캔버스에 그려진 그림을 재는 방법을 바로 위 문단에 이어 적는다.
-->
**그림을 재는 요소도 사이트가 바꿉니다.** 그림 범위를 어떤 요소로 재는지 역시 사이트의 현재 모습에
기댄 값입니다. 사이트가 그리는 방식을 바꾸면 재던 요소가 사라지고, 그때 상자로 대신 재는 코드는
오류 없이 틀린 값을 냅니다. 기록된 숫자는 여전히 목표 범위에 수렴하므로 증상만 남고 원인은
숨습니다. 그래서 그림을 재지 못하면 대체값으로 넘어가지 않고 그 기능을 멈추며, 무엇으로 쟀는지를
기록에 남깁니다. **예시**: 사이트가 바닥 맵을 SVG(`svg.svg-map`)에서 캔버스(`canvas.doc-map-canvas`)로
옮기자 맞추기 스크립트가 `.map-wrap` 상자를 그림으로 삼았습니다. 스크립트가 기록한 채움 비율은 0.9를
넘었지만 실제 그림은 창의 절반도 채우지 못했고, 이동 제한은 그림이 화면 가운데를 벗어날 만큼
헐거워졌습니다.

이 증상에서는 기록이 무엇을 쟀는지부터 봅니다. 재던 요소가 페이지에 아직 있는지 확인하고, 없으면
사이트가 지금 무엇으로 그리는지 찾습니다. 캔버스라면 캔버스의 투명하지 않은 픽셀 범위가 그림과
맞는지 캡처와 대조합니다.

그림이 캔버스에 그려지면 투명하지 않은 픽셀의 범위를 잽니다. 이 방법도 지형을 그리는 캔버스를
정확히 골라야 동작합니다. 사이트가 같은 클래스의 숨은 캔버스(예: 미니맵용 개요)를 지형 캔버스보다
앞에 넣으면 `querySelector`는 그 캔버스를 돌려주고, 화면 크기가 0인 캔버스에서 잰 그림은 없으므로
맞추기와 이동 제한이 오류 없이 멈춥니다. 이 증상에서는 같은 선택자에 걸리는 요소를 모두 나열해
요소마다 비트맵 크기, 화면 크기(`getBoundingClientRect`), `visibility`와 `opacity`를 찍습니다. 비트맵
크기가 있다는 사실만으로 화면에 표시 중이라고 판단하지 않습니다. 고칠 때는 DOM 순서로 고르지 않고
화면에 표시된 후보만 고르며, 표시된 후보가 둘 이상이면 어느 것이 지형인지 보장할 수 없으므로
재지 않고 멈춥니다. **예시**: 지금 판의 지도 컨테이너에는 `canvas.doc-map-canvas`가 둘 있습니다.
첫째는 지도 전체를 담은 캔버스로 보통 배율에서는 `display: none`이고, 둘째가 창보다 조금 큰
캔버스로 화면을 그립니다. 배율을 많이 줄이면 사이트가 둘을 맞바꿔 첫째를 보이고 둘째를
`visibility: hidden`으로 숨깁니다. 숨은 둘째는 화면 크기를 그대로 가지므로 크기만 보고 골라도
틀립니다. 다음 네 가지를 지킵니다.

- 사이트 캔버스를 줄여서 우리 캔버스(`willReadFrequently: true`)에 옮긴 뒤 읽습니다. 사이트
  캔버스에서는 `getImageData`를 부르지 않고, 읽는 양도 줄어듭니다. **예시**: 원본 해상도로 읽으면
  약 4ms, 가로세로를 1/4로 줄이면 1ms 미만이었습니다.
- 결과는 확대와 이동이 걸리는 상자에 대한 비율로 저장합니다. 사이트가 캔버스와 그 상자를
  같은 변환으로 움직이면 이 비율은 끌고 확대해도 그대로라, 끄는 도중에는 다시 잴 필요가 없습니다.
  이 전제는 확대와 이동 전후의 비율을 비교해 확인합니다. 그 상자를 가진 요소가 없으면 사이트 상태의
  변환과 크기로 같은 상자를 계산합니다. **예시**: 2026-10 판은 `.map-wrap`이 없어, 지도 상태의 panzoom
  변환(x, y, zoom)과 회전을 반영한 맵 크기(`viewSize`)로 상자를 계산합니다.
- 캔버스는 창에 보이는 부분만 그립니다. 범위가 캔버스 가장자리에 닿으면 잘린 값으로 보고, 먼저
  줄여서 다시 잽니다. 잘린 값으로 맞추면 창보다 큰 그림을 맞았다고 판단합니다.
- 회전처럼 상자와 캔버스의 관계를 바꾸는 변환이 걸리면 다시 잽니다. **예시**: 예전 판의 회전은
  `.map-wrap`이 아니라 안쪽 `.map-scene`의 `transform`에 걸렸고, 지금 판은 지도 상태의 `viewRotation`이
  그 값입니다. 그 값을 저장값을 다시 잴지 가리는 기준으로 사용합니다.

캐시의 소유자는 전체 컨테이너만으로 정하지 않습니다. 같은 컨테이너 안의 Canvas가 교체되면
이전 지형 범위를 폐기해야 합니다. 같은 Canvas라도 층 전환으로 실제 지형이 달라질 수 있으므로
맵과 렌더 대상, 회전, 층별 내용이 캐시의 적용 조건인지 구분합니다. 한 지도의 층 전환에서 외곽이
같았다는 결과만으로 다른 지도의 캐시 재사용까지 보장하지 않습니다.

**이동 제한은 입력 종류가 아니라 변환 결과의 조건입니다.** 드래그가 정상이어도 휠 확대는 별도
경로에서 맵의 원점과 배율을 변경합니다. 지형 바깥에 포인터를 둔 채 확대하면 그 기준점을 유지하는
계산 때문에 지형 전체가 뷰포트 밖으로 이동할 수 있습니다. 휠, 버튼, 키보드, 리사이즈와 층 전환도
검증해야 하는 이유입니다. 자체 렌더러에서는 변환을 적용하는 공통 경로에서 가시성 조건을 유지하고,
외부 렌더러를 보정할 때는 실제 그리기가 끝난 뒤의 범위로 판정합니다.

<!--
INTENT: "그리기가 끝난 뒤"를 한 프레임 뒤로 잡으면 보정이 한 칸씩 늦는다. 왜 한 프레임으로는
부족한지와, 그 원인을 구별하는 관찰을 남긴다.
-->
**사이트가 그린 다음에 잽니다.** 사이트가 처리한 입력의 결과를 보정하려면 사이트가 새 변환을 DOM에
쓴 뒤에 재야 합니다. 캡처 단계 처리기(5.4절)는 같은 이벤트를 사이트보다 먼저 받으므로, 처리기에서
`requestAnimationFrame`을 예약하면 사이트가 같은 이벤트에서 예약한 프레임 콜백보다 먼저 줄을 섭니다.
브라우저는 다음 프레임에서 콜백을 예약된 순서대로 실행하므로([HTML 명세의 animation frame callbacks](https://html.spec.whatwg.org/multipage/imagebitmap-and-animations.html)),
한 프레임 뒤에 잰 값은 사이트가 변환을 쓰기 전의 화면입니다. 그 값으로 계산한 보정이 새 화면에
더해지면 보정이 입력 한 번씩 늦게 따라가고, 연속으로 확대하면 결국 그림이 화면 밖으로 나갑니다.
원인은 보정 이동량을 입력마다 기록해 보면 드러납니다. 이동량이 그 입력이 아니라 바로 앞 입력의
값과 일치합니다. 고칠 때는 프레임 콜백 안에서 한 번 더 예약해 두 프레임 뒤에 잽니다. 사이트가
변환을 다음 프레임에 몰아 쓰는 라이브러리(anvaka/panzoom이 그렇다)를 쓰면 같은 일이 생깁니다.

<!--
INTENT: 화면을 옮기는 두 기능이 각자 옳은 일을 하면서 서로의 결과를 지우는 실패다. 기능 하나씩
시험해서는 안 보이고 실행 순서까지 재현해야 드러나므로, 순서를 재현하는 검사와 함께 남긴다.
-->
**화면 가운데의 주인을 하나로 정합니다.** 화면을 옮기는 기능이 둘이면 각자 옳게 동작해도 서로의
결과를 지웁니다. **예시**: 지도 맞추기는 그림 가운데를 창 가운데에 두고, 위치 표시는 새 위치가 화면
밖이면 마커를 가운데로 옮깁니다. 앱은 맵을 열자마자 위치를 보내고 맞추기 스크립트는 그 뒤에 넣으므로,
맞추기와 그 뒤의 재확인이 마커를 옮긴 화면을 다시 그림 가운데로 돌렸습니다. 지형이 창보다 작으면
마커가 가장자리에 남아 눈에 띄지 않았고, 최소 배율에서도 지형이 창보다 큰 맵에서만 마커가 화면 밖으로
나갔습니다. 그래서 한 맵의 실패로 드러났지만 순서의 문제는 모든 맵에 있었습니다.

이런 실패는 각 기능을 따로 시험해서는 보이지 않고, 실제 실행 순서를 재현해야 보입니다. 고칠 때는 한
기능이 가운데의 주인이 되게 정합니다. 위치가 표시되면 가운데는 위치가 정하고, 맞추기는 끝날 때마다
위치 표시 쪽에 마커를 보이게 하라고 맡기며, 재확인은 그림 가운데로 다시 옮기지 않습니다. 두 기능이
같은 판정(마커가 화면 안쪽에 있는지)을 공유해야 번갈아 움직이지 않습니다. 검사는 순서를 그대로
재현합니다. 위치를 먼저 표시한 상태에서 맞추기 스크립트를 넣고, 맞추기와 재확인이 모두 끝난 뒤
마커가 화면 안쪽에 있고, 배율이 그대로이며, 화면이 더 움직이지 않는지 봅니다.

<!--
INTENT: 확인한 뒤 다시 보내는 유지 루프는 확인이 깨지면 같은 입력을 끝없이 보낸다. 그 재전송이 상태
갱신 말고 다른 효과를 내면 보이는 잡음이 된다는 규칙과, 주기가 불규칙해 보이는 이유를 구별하는 관찰을
남긴다.
-->
**다시 보내는 입력은 조용해야 합니다.** 표시가 사라졌는지 주기적으로 확인하고 사라졌으면 마지막 입력을
다시 보내는 유지 루프는, 확인 근거가 깨지면 확인이 매번 실패해 같은 입력을 끝없이 보냅니다. 그 입력이
상태 갱신 말고 다른 효과(주의를 끄는 애니메이션, 알림, 소리)를 내면 그 효과가 사용자 눈에 반복됩니다.
**예시**: 사이트가 지도 상태를 숨긴 뒤 위치 확인이 매번 실패했고, 앱은 2초마다 같은 스크린샷을 다시
보냈습니다. 브리지가 보낼 때마다 사이트의 핑(내 위치를 0.7초 동안 최대 2.5배로 키움)을 켰으므로, 새
스크린샷이 없는데도 위치가 커졌다 줄어들었습니다.

주기가 불규칙해 보이는 이유도 같은 곳에 있습니다. 사이트의 핑 표시는 켜진 뒤 2초 동안 유지되고, 꺼졌다
다시 켜질 때만 애니메이션을 새로 시작합니다. 재전송 간격이 2초 안팎에서 흔들리므로, 표시가 꺼진 뒤에
도착한 재전송만 애니메이션을 시작했습니다. 이 증상에서는 재전송 시각과 표시 상태가 바뀐 시각을 함께
기록해 봅니다. 애니메이션이 재전송 가운데 일부에서만 시작하고, 그 재전송이 모두 표시가 꺼진 직후에
도착했다면 이 원인입니다.

바로잡을 때는 두 가지를 함께 합니다. 확인 근거를 복구해 재전송을 멈추고, 재전송 경로가 다시 깨져도
조용하도록 주의 표시는 새 입력에만 켭니다. 입력이 새것인지는 주의 표시를 마지막으로 켠 입력과 비교해
판정하고, 표시가 실제로 보인 뒤에만 그 입력을 기록합니다. 보이지 않은 채 끝난 입력을 기록하면 다음 재전송이
처음 보이는 순간에도 주의 표시를 켜지 않습니다. 확인이 실패한 이유는 이름으로 로그에 남겨, 재전송 루프가
돌고 있다는 사실이 로그에서 바로 보이게 합니다. **예시**: 지금은 앱이 핑을 직접 켜므로, 브리지가 마지막으로
핑을 켠 파일명을 기억하고 마커가 보였을 때만 갱신합니다.

<!--
INTENT: 입력 처리기만 읽고 "그 경로는 이 기능을 일으키지 않는다"고 결론 내린 실수에서 진단 규칙을 남긴다.
반응형 프레임워크에서는 기능이 처리기 안이 아니라 상태를 지켜보는 쪽에서 일어나고, 그 코드는 다른 청크에
있을 수 있다.
-->
**기능은 상태를 지켜보는 곳에 있을 수 있습니다.** 반응형 프레임워크(Vue, React의 effect 등)를 쓰는 사이트에서
입력 처리기는 상태만 바꾸고, 그 상태로 하는 일은 상태를 지켜보는 watcher나 computed가 맡는 경우가 많습니다.
그래서 처리기 코드만 읽고 "이 입력은 그 기능을 일으키지 않는다"고 판단하면 틀립니다. 입력을 넣는 방식을 바꾼
뒤 관련 없어 보이는 기능이 멈추면, 처리기가 쓰는 상태 이름과 그 상태 객체를 인자로 받는 함수를 번들 전체에서
찾습니다. 화면 청크만 보지 말고 진입 청크와 공용 청크도 봅니다. 찾았으면 그 상태를 바꿨을 때 기능이 일어나는지
실제 페이지에서 확인합니다. **예시**: Online의 층 자동 선택은 "Where am i" 처리기가 아니라, 지도 상태의
`playerPos`를 인자로 받아 깊게 지켜보는 층 선택 컴포저블에 있었습니다. 그 코드는 지도 화면과 다른 청크에 있어
처음 조사에서 빠졌고, 앱이 `playerPos`를 바꾸지 않게 되자 층 선택도 함께 멈췄습니다.

<!--
INTENT: 데이터가 준비되기 전의 입력을 버리고 나중에 다시 보지 않는 사이트에서, 시간에 기대지 않고 준비 신호에
기대어 넣는 규칙과, 그 원인을 구별하는 관찰을 남긴다.
-->
**데이터가 준비되기 전의 입력은 버려질 수 있습니다.** 상태를 지켜보는 기능은 대개 바뀌는 순간 한 번만 판단합니다.
그 순간 판단에 필요한 데이터(비동기로 오는 문서 같은)가 없으면 아무것도 하지 않고, 데이터가 나중에 와도 같은
상태를 다시 보지 않습니다. 제어 측이 화면을 열자마자 입력을 넣으면 그 입력만 효과가 없습니다. 같은 값을 다시
넣어도 반응형 프레임워크는 값이 그대로라 반응하지 않습니다. 이 원인은 화면이 붙은 뒤 여러 시각에 입력을 넣어
보면 드러납니다. 이른 입력은 끝내 효과가 없고, 데이터가 도착한 뒤의 입력만 효과가 있습니다. 고칠 때는 그
기능이 판단에 쓰는 데이터가 채워졌다는 신호를 찾아(5.8절의 방법으로 데이터 객체를 기록) 신호가 온 뒤에
넣습니다. 일정 시간 뒤에 값을 흔들어 다시 넣는 방법은 데이터가 그보다 늦으면 여전히 놓치고, 그 사이 사용자가
바꾼 결과(손으로 고른 층)를 덮어씁니다. **예시**: 사이트는 층 데이터 표에 지도 문서의 높이와 구역이 채워지기
전에 바뀐 `playerPos`로는 층을 고르지 않았습니다. 브리지는 표에 높이나 구역이 생길 때까지 기다렸다가 좌표를
넣습니다.

**한 지점의 측정으로 일반 법칙을 만들지 않습니다.** 조건을 바꿔 여러 번 재고, 성패가 갈리면
갈리는 조건을 원인 후보로 봅니다. **예시**: "합성 입력이 안 먹는다"는 결론은 드래그 시작점을
다섯 군데로 바꿔 재면서 뒤집혔습니다. 세 곳은 정상이었고, 실패한 두 곳은 마커 위였습니다.
원인은 합성 입력 차단이 아니라 마커 위 이동 차단입니다(5.5절).

## 7. 검증 방법론

검증은 판 확인, 과정 기록, 숫자 판정, 시각 확인 네 가지를 갖춥니다.

**판 번호를 심습니다.** 주입 스크립트가 자기 판 번호를 전역에 남기면, 화면이 이상할 때 옛 판이
도는 중인지 새 판이 틀린 것인지 한 번에 갈립니다. 이 구분이 없으면 옛 판의 증상을 새 판의
결함으로 쫓게 됩니다.

```javascript
window.__tanukiKeepVisible = { version: 6, rule: 'fit-on-open + center-clamp, picture from svg or canvas', log: function () { return debugLog; } };
```

**과정을 링 버퍼에 남깁니다.** `console.log`는 앱 안에서 사람이 보기 어렵습니다. 최근 몇십 개만
배열에 남기고 전역으로 꺼내면 CDP(4절)로 언제든 읽을 수 있습니다.

**합격 기준을 숫자로 정합니다.** "잘 보인다"가 아니라 "채움 0.75~0.98, 중심 어긋남 3px 이내"로
적습니다. 숫자라야 여러 대상에 일괄로 돌려 표로 만들 수 있습니다.

**판정은 스크립트가 쓰는 측정과 다른 경로로 합니다.** 스크립트가 남긴 기록만으로 합격을 판정하면,
스크립트가 엉뚱한 대상을 재는 동안에도 합격이 나옵니다. 검증 도구는 같은 값을 따로 잽니다.
**예시**: 맞추기 스크립트는 1/4로 줄인 캔버스로 그림을 재고, 검증 도구는 원본 해상도로 캔버스를
따로 읽어 채움과 중심을 쟀습니다. 사이트가 바닥 맵을 캔버스로 옮긴 뒤의 수정 전 스크립트는
스스로 채움 0.96을 기록했지만, 따로 잰 값은 0.44였습니다.

**마지막에는 눈으로 봅니다.** 스크린샷을 캡처해 확인합니다. 수치가 맞아도 층이 어긋나거나
엉뚱한 영역이 잘려 있는 경우는 여기서 잡습니다.

**수정 전 판으로 같은 검사를 돌려 실패를 확인합니다.** 회귀 검사가 버그를 실제로 재현하는지는 수정 전
코드에서 실패하는지로 확인합니다. 검사 도구가 주입 스크립트의 위치를 인자로 받게 하면, 이전 커밋을 임시
작업 트리(`git worktree add`)로 꺼내 같은 검사를 돌릴 수 있습니다. 수정 전 코드에서도 통과하는 사례는 그
버그를 재현하지 못한 것입니다. **예시**: [verify-map-recovery.mjs](../tools/verify-map-recovery.mjs)의
`--scripts`와 [verify-map-keep-visible.mjs](../tools/verify-map-keep-visible.mjs)의 `--script`가 그
인자입니다.

**재현 페이지와 실제 사이트를 둘 다 씁니다.** 작은 재현 페이지는 네트워크 없이 매번 같은 조건을
만들어 회귀를 잡고, 실제 사이트 검사는 재현 페이지가 모르는 사이트의 변화를 잡습니다. 재현 페이지의
통과를 지금 사이트에서의 동작으로 확대하지 않습니다. **예시**:
[verify-map-keep-visible.mjs](../tools/verify-map-keep-visible.mjs)는 재현 페이지로 캔버스 후보 선택,
맞춤, 끌기와 휠 제한, 배율 한계에서의 위치 유지를 검사하고(CI),
[verify-online.mjs](../tools/verify-online.mjs)는 실제 사이트에 앱과 같은 스크립트를 같은 순서로 넣어
맵마다 위치, 맞춤, 휠 확대 뒤 지형 픽셀을 검사합니다(사람이 실행). 어느 쪽도 실제 WPF 창의 입력과
포커스를 검증하지 않습니다.

## 8. 사이트 변경에 취약한 지점

주입 방식은 사이트의 현재 모습에 기대므로, 무엇에 기댔는지와 다시 재는 법을 함께 적어 두어야
다음 사람이 고칠 수 있습니다. 값 자체보다 **다시 재는 법**이 중요합니다. 값은 낡지만 재는 법은
오래 갑니다. 이 저장소가 기대는 값은 다음과 같습니다.

| 기대는 것 | 구현에서 확인할 대상 | 다시 재는 법 |
|---|---|---|
| 맵 요소 선택자 | `.pan.map-cont` (2026-10 판부터 `.map-wrap`은 없음) | 페이지에서 요소 구조 확인 |
| 바닥 맵을 그리는 곳 | `canvas.doc-map-canvas` 가운데 화면에 표시된 하나 | `picture().source`를 보고, 같은 선택자의 후보마다 비트맵과 화면 크기, 표시 상태를 확인 |
| 맵 컨테이너의 남길 층 | `web-elements-control.js`의 `MAP_LAYER_SELECTORS` | 컨테이너 직계 자식을 나열하고, 숨김을 켰을 때 사라지는 맵 요소가 있는지 비교 |
| 지도 상태 | `map-state-capture.js`가 만들어질 때 기록한 reactive 프록시. 기록 조건은 컨테이너와 좌표 변환 둘이고, 화면 이동(`centerOnPosition`)과 맞춤(`panzoom`, `x`, `y`, `zoom`, `viewSize`, `viewRotation`)도 씀 | `tanukiPilot.getMap()`이 객체를 돌려주는지, 없으면 `tanukiPilot.status()`의 `map-unavailable` 사유. `verify-online.mjs`에서 앱의 원이 사이트가 같은 파일명으로 그린 원과 겹치는지, `panzoom.moveBy` 뒤 캔버스와 마커가 함께 움직이는지 |

## 9. 새 프로젝트 적용 순서

1. 관측 통로부터 만듭니다. 디버그 빌드에서 원격 디버깅 포트를 열고, 붙는 조사 도구를 짧게 하나
   씁니다(4절).
2. 전역과 번들을 훑습니다. 사이트가 열어 둔 함수(5.2절), 쓰는 라이브러리(5.3절), 렌더 층이 몇
   개인지 확인합니다. 읽어야 할 상태가 렌더 트리에 없으면 만들어지는 순간에 기록할 수 있는지
   봅니다(5.8절).
3. 가장 약한 개입부터 시도합니다. 스타일시트(5.1절), 사이트 함수 호출(5.2절), 입력
   가로채기(5.4절), 합성 입력(5.5절), 요청 가로채기(5.6절) 순서입니다.
4. 주입 스크립트에 판 번호와 로그를 심습니다(7절).
5. 합격 기준을 숫자로 적고 여러 대상에 일괄로 돌립니다. 마지막은 캡처로 확인합니다(7절).
6. 실측한 값은 근거와 함께 그 값을 쓰는 파일 안에 적습니다. 별도 문서에만 적힌 근거는 다음
   사람이 찾지 못합니다(8절).
7. 끊기면 안 되는 핵심 기능이 사이트 내부에 기대면, 사이트 런타임 없이 도는 대체 경로를 따로
   둡니다(5.6절). 주입은 사이트가 바뀔 때마다 따라가야 하는 방식이라, 따라가는 동안에도 핵심 기능이
   돌 길이 있어야 합니다. 사이트 안에서도 핵심 표시가 기대는 부분은 잘 바뀌지 않는 투영 함수로 줄이고
   나머지는 직접 그립니다(5.7절).
