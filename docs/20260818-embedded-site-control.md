## 적용 범위와 용어

이 문서는 소스가 없고 빌드에 손댈 수 없으며 통보 없이 바뀌는 남의 웹사이트를, 그 사이트를 품은
앱 쪽에서 고쳐 쓰는 기법을 다룹니다. 기법은 특정 엔진에 매이지 않습니다. CefSharp, WebView2,
Electron의 BrowserView, Playwright처럼 브라우저 엔진을 통제하고 페이지 컨텍스트에서 코드를
실행할 수 있는 환경이면 그대로 통합니다.

읽는 데 필요한 배경은 셋입니다. HTML/DOM과 CSS 우선순위, JavaScript 이벤트 전파, 그리고
"앱이 브라우저를 품고 있다"는 구조 감각입니다.

본문은 다음 용어로 서술합니다.

| 용어 | 정의 |
|---|---|
| 대상 사이트 | 앱 안에 띄우는, 소스와 빌드에 손댈 수 없는 남의 웹사이트 |
| 호스트 앱 | 브라우저 엔진을 품고 대상 사이트를 띄우는 앱 |
| 제어 측 | 호스트 앱과 그 주입 스크립트, 조사 도구를 묶어 부르는 이름 |
| 페이지 컨텍스트 | 대상 사이트의 코드와 같은 전역(`window`)을 공유하는 실행 환경 |
| 주입 | 호스트 앱이 페이지 로드 후 페이지 컨텍스트에서 스크립트를 실행시키는 일 |
| 주입 스크립트 | 주입되어 페이지 안에서 도는 코드 (2절) |
| 조사 도구 | 페이지 밖 Node 프로세스에서 실행 중인 페이지를 조사하는 코드 (2절) |
| 신뢰 입력 | 브라우저 엔진이 만든 입력 이벤트. `event.isTrusted === true` |
| 합성 입력 | 페이지 안 코드가 `dispatchEvent`로 만든 입력 이벤트. `isTrusted`는 false |
| 렌더 층 | 사이트의 내부 상태 하나를 화면에 그려 내는 개별 경로. 한 화면이 canvas 그리기와 CSS `transform`처럼 여러 층으로 이뤄지기도 함 |

**예시**: 이 문서의 예시는 모두 TanukiTarkovMap 저장소에서 가져옵니다. WPF 앱 안에
CefSharp(Chromium Embedded Framework)로 tarkov-market.com을 띄워 게임 밖 화면에서 맵을 보는
도구입니다. 사이트를 그대로 쓰면 앱에 필요 없는 헤더와 안내 배너가 자리를 차지하고, 맵을 끌다
화면 밖으로 놓치고, 사이트가 죽으면 앱도 함께 죽습니다. 이 문제들을 아래 기법으로 풀었습니다.

## 1. 제어 측의 권한과 두 원칙

제어 측이 가진 권한은 실행, 가로채기, 엔진 설정 셋이고, 소스, 문서, 변경 통보는 없습니다.
이 비대칭이 문서 전체를 관통하는 두 원칙을 정합니다.

| 가진 권한 | 없는 것 |
|---|---|
| 페이지 컨텍스트에서 임의의 JavaScript 실행 | 소스와 빌드 |
| 네트워크 요청을 가로채 다른 응답 반환 | 안정된 API와 문서 |
| 브라우저 엔진 설정 (줌, 창 크기, 원격 디버깅 포트) | 변경 통보 |

**원칙 1. 대상 사이트가 이미 열어 둔 입구로 들어갑니다.** 사이트의 내부 상태를 제어 측이 직접
고치면, 그 상태를 근거로 그려지는 다른 렌더 층과 어긋납니다(5.7절). 마우스와 휠 같은 입력,
사이트가 `window`에 열어 둔 함수, CSS 우선순위처럼 사이트가 원래 처리하게 되어 있는 경로로
들어가면 나머지 일관성은 사이트가 지킵니다.

**원칙 2. 무엇을 하든 밖에서 측정할 수 있어야 합니다.** 대상이 남의 코드이므로 추측이 늘어나고,
추측을 줄이는 유일한 방법은 실행 중인 페이지에서 숫자를 읽는 것입니다. 관측 통로(4절)를 먼저
만들고 기능을 만드는 순서가 반대 순서보다 언제나 빠릅니다.

## 2. 주입 스크립트와 조사 도구: `.js`와 `.mjs`

제어 코드는 페이지 안에서 도는 주입 스크립트와, 페이지 밖에서 그 페이지를 조사하는 도구로
나뉩니다. 성격이 다른 두 벌이며, 이 저장소는 확장자로 구분합니다.

| 구분 | 주입 스크립트 (`src/.../Scripts/*.js`) | 조사 도구 (`tools/*.mjs`) |
|---|---|---|
| 실행 위치 | 페이지 컨텍스트, 사이트 코드와 같은 전역 | Node 프로세스, 페이지 밖 |
| 실행 주체 | 호스트 앱이 페이지 로드 후 주입 | 사람이 명령줄에서 실행 |
| 배포 | 빌드 때 DLL에 Embedded Resource로 포함 | 저장소에만 존재, 사용자에게 배포되지 않음 |
| 쓰는 API | DOM, 이벤트, `window` | CDP, `fetch`, `WebSocket`, 파일 시스템 |
| 수정 확인 비용 | 앱 재빌드와 재실행 | 즉시 |

`.mjs`는 Node의 확장자 규칙입니다. Node는 확장자로 모듈 방식을 정하는데, `.mjs`는 ES 모듈로
읽혀 `package.json` 없이 `import`와 최상위 `await`를 쓸 수 있습니다. 조사 도구를 파일 하나짜리
스크립트로 유지하는 데 이 두 가지가 결정적입니다.

조사 도구는 의존성을 두지 않습니다. Node 22의 내장 `fetch`와 `WebSocket`만으로 브라우저에
붙습니다. `npm install`이 필요한 도구는 환경을 맞춰야 쓸 수 있어 급할 때 쓰이지 않습니다.

## 3. 주입 파이프라인

주입은 스크립트를 빌드 시 앱에 품었다가, 페이지 로드가 끝난 시점에 페이지 컨텍스트에서
실행시키는 파이프라인으로 구성합니다.

```
빌드 시                                실행 시
Scripts/*.js --임베드--> DLL --Load()--> 문자열
                                          |
                              FrameLoadEnd (메인 프레임)
                                          |
                                EvaluateScriptAsync
                                          v
                              페이지 컨텍스트에서 실행
```

C# 쪽은 파일 하나를 상수 하나로 감쌉니다.

```csharp
// MapKeepVisible.js.cs: 파일 이름과 호출 상수를 한곳에 묶는다
public static string KEEP_MAP_VISIBLE_SCRIPT => JavaScriptLoader.Load("map-keep-visible.js");

// 페이지 로드가 끝난 뒤 주입한다
await ExecuteScriptAsync(MapKeepVisible.KEEP_MAP_VISIBLE_SCRIPT);
```

JavaScript 쪽은 즉시 실행 함수로 감싸고, 밖에서 볼 것만 `window`에 붙입니다.

```javascript
(function () {
    'use strict';
    // 밖에서 판을 확인할 수 있게 표시를 남긴다
    window.__tanukiKeepVisible = { version: 5, log: function () { return debugLog; } };
})();
```

스크립트를 C# 문자열에 넣지 않고 별도 파일로 두는 이유는 셋입니다. 편집기가 문법을 검사하고,
`node --check` 같은 도구로 커밋 전에 문법을 확인할 수 있고, 조사 도구(4절)가 배포될 코드와
**같은 파일**을 읽어 주입해 볼 수 있습니다. 셋째가 특히 중요합니다. 시험한 코드와 배포되는
코드가 다르면 시험이 증거가 되지 못합니다.

주입에는 걸리기 쉬운 함정이 넷 있습니다.

**주입은 문서마다 다시 합니다.** 주소를 바꿔 페이지를 새로 읽으면 주입 스크립트가 사라지므로
로드 이벤트마다 다시 주입합니다. 반대로 SPA에서는 사이트 안 링크를 눌러도 문서를 다시 읽지 않고
화면만 바뀌므로 로드 이벤트가 오지 않고, 이미 들어가 있는 주입 스크립트도 다시 돌지 않습니다.
새 화면에 맞춰 다시 할 일이 있으면 스크립트 안에서 주소 변화를 직접 감시합니다.

```javascript
// 사이트 안에서 화면만 바뀌는 경우를 잡는다
var fittedPath = location.pathname;
setInterval(function () {
    if (location.pathname === fittedPath) return;
    fittedPath = location.pathname;
    // 새 화면에 맞춰 다시 할 일
}, 500);
```

**준비 상태를 UI 프레임워크 속성으로 판정하지 않습니다.** CefSharp의 `IsBrowserInitialized`와
`Address`는 WPF DependencyProperty라 CEF가 UI 스레드에 따로 게시해 갱신하는데, 릴리즈
빌드에서는 첫 페이지 로드가 그 갱신보다 먼저 처리되는 일이 생깁니다. 그 값으로 판정하면 페이지
후처리가 통째로 조용히 건너뛰어집니다. 준비 상태는 실제 인스턴스인 `BrowserCore`로 판정하고,
주소는 로드 이벤트가 준 `e.Url`을 씁니다. **예시** (0.2.3): 디버그 빌드는 정상인데 릴리즈
빌드만 UI 숨김과 위치 표시가 안 되는 증상의 원인이 이 갱신 지연이었습니다.

**실패를 조용히 넘기지 않습니다.** 건너뛴 주입은 오류를 내지 않으므로, 로그가 없으면 위 증상처럼
원인이 오래 숨습니다. 주입을 건너뛰었으면 왜 건너뛰었는지 한 줄이라도 남깁니다.

**주입 순서에 의존이 생깁니다.** 뒤에 도는 스크립트가 앞 스크립트의 결과를 덮을 수 있습니다.
5.1절의 기법이 이 실패에서 나왔습니다.

## 4. 관측 통로: CDP

관측 통로는 브라우저 엔진의 원격 디버깅 포트에 CDP(Chrome DevTools Protocol)로 붙여 만듭니다.
CDP는 크로미움이 그 포트로 여는 프로토콜로, DOM 조회, JavaScript 실행, 스크린샷을 페이지 밖에서
주고받을 수 있습니다. 앱 안 브라우저에서 F12로 여는 DevTools 창은 사람만 볼 수 있어 자동화된
확인에는 쓸 수 없습니다.

포트는 Debug 빌드에서만 엽니다. 릴리즈 빌드에서 열면 사용자 컴퓨터에서 앱 안 페이지를 아무나
조작할 수 있는 통로가 됩니다.

```csharp
#if DEBUG
    // Debug 빌드 한정, localhost 전용
    settings.RemoteDebuggingPort = 9222;
#endif
```

붙는 쪽은 조사 도구 `tools/cdp-debug.mjs` 하나입니다. `/json/list`로 페이지 목록을 받아
`webSocketDebuggerUrl`에 접속하면, 그 뒤로는 JSON 명령을 주고받는 일이 전부입니다.

```bash
node tools/cdp-debug.mjs targets                  # 디버깅 가능한 페이지 목록
node tools/cdp-debug.mjs eval "document.title"    # 페이지 안에서 JS 실행
node tools/cdp-debug.mjs html ".panel_left"       # 선택자의 outerHTML
node tools/cdp-debug.mjs screenshot               # 렌더링 화면 PNG 저장
```

스크린샷은 숫자가 맞는데 눈으로 보면 틀린 경우를 잡습니다(7절). **예시**: 맵 맞추기 작업에서
"채움 비율 0.95, 중심 어긋남 1px"이라는 수치가 실제로 어떤 화면인지는 캡처로 확인해 확정했습니다.

**포트는 자리를 정해 둡니다.** 규약 없이 포트를 겹치면 명령이 엉뚱한 프로세스로 흘러갑니다.
앱이 9222를 쓰는 동안 같은 포트로 크롬을 띄우면, 크롬은 바인딩에 실패해도 조용히 떠 있고 이후
CDP 명령이 전부 실행 중인 앱으로 흘러 들어가 사용자가 보는 화면을 시험 스크립트가 조작하게
됩니다.

| 포트 | 자리 |
|---|---|
| 9222 | 실행 중인 앱 |
| 9223 | 재현 실험용 브라우저 |
| 9224 | 사본 수집 도구 |

**실험은 시나리오 파일로 적습니다.** 한 번 확인하고 버릴 실험도 `.mjs` 파일로 적습니다. 같은
조건을 다시 돌릴 수 있어야 앞뒤 결과를 비교할 수 있기 때문입니다. 전형적인 구성은 네 단계입니다.

```javascript
// 1. 대상 페이지를 연다
await send('Page.navigate', { url: 'https://example.com/page' });
await new Promise((r) => setTimeout(r, 12000));

// 2. 배포될 스크립트를 그대로 읽어 넣는다
await evaluate(await readFile('src/.../Scripts/map-keep-visible.js', 'utf8'));

// 3. 사람이 하듯 입력을 보낸다 (신뢰 입력)
await send('Input.dispatchMouseEvent', { type: 'mousePressed', x: 700, y: 500, button: 'left', clickCount: 1 });

// 4. 결과를 숫자로 읽는다
console.log(await evaluate(`getComputedStyle(document.querySelector('.map-wrap')).transform`));
```

**신뢰 입력과 합성 입력을 갈라 시험합니다.** CDP의 `Input.dispatchMouseEvent`가 보내는 입력은
브라우저가 만든 신뢰 입력이고, 페이지 안에서 `dispatchEvent`로 만든 입력은 합성 입력입니다.
둘을 갈라 시험하면 "사이트가 합성 입력을 거른다"와 "사이트가 그 자리를 다르게 취급한다"를
구별할 수 있습니다. 이 구별이 5.5절의 입력 선택을 정하는 근거입니다.

## 5. 개입 기법 카탈로그

개입은 약한 것부터 강한 것 순서로 고르고, 위 기법으로 되면 아래로 내려가지 않습니다. 각 기법은
적용 조건, 방법, 실패 모드, 검증의 같은 틀로 적습니다.

### 5.1 스타일시트 한 장으로 숨기기

**적용 조건**: 대상 사이트의 특정 영역을 보이지 않게 하는 경우입니다.

**방법**: 요소마다 `style.display`를 넣지 않고, `!important`가 붙은 규칙을 담은 `<style>` 한
장을 문서에 넣습니다. 토글이 필요하면 `html`에 클래스를 붙였다 떼어 규칙을 켜고 끕니다.

```javascript
var STYLE_ID = 'tanuki-visibility-rules';
var rules = 'header, .footer-wrap { display: none !important; }'
          + 'html.tanuki-panels-hidden .panel_left { display: none !important; }';
```

**실패 모드**: 인라인 스타일로 숨기면 두 곳에서 깨집니다. 나중에 만들어진 요소를 놓치고, 다른
스크립트가 `style.cssText`를 통째로 대입하면 함께 지워집니다. `!important` 규칙은 인라인
스타일보다 우선하므로 두 경우를 모두 막습니다. **예시**: 주입 스크립트 두 개가 서로의 인라인
스타일을 지워, 숨겼던 헤더가 릴리즈 빌드에서만 되살아나는 증상이 있었습니다(3절의 순서 의존).

**검증**: `getComputedStyle(el).display`를 CDP로 읽습니다. 요소가 없어졌는지가 아니라 계산된
값을 봅니다.

### 5.2 사이트가 열어 둔 전역 함수 호출

**적용 조건**: 사이트에 시킬 일을, 사이트가 이미 그 일을 하는 함수로 전역에 열어 둔 경우입니다.

**방법**: 그 함수를 그대로 부릅니다. 부르기 전에 존재를 확인하고, 실패를 삼키지 않고 로그로 남깁니다.

```javascript
var pilot = window.pilot;
if (!pilot || typeof pilot[methodName] !== 'function') return false;
```

**예시**: 호스트 앱은 스크린샷 파일명을 사이트의 `window.pilot.positionFromScreenshot`에 넘겨
맵에 위치를 띄웁니다.

**실패 모드**: 전역 함수는 계약이 아니므로 언제든 이름이 바뀌거나 사라집니다. 존재 확인과 실패
로그가 없으면 사이트 변경이 조용한 기능 중단으로 나타납니다.

**검증**: `Object.keys(window.pilot)`를 CDP로 찍어 전역에 무엇이 열려 있는지 조사합니다. 이름만
그럴듯한 값에 속지 않도록 실제 내용까지 확인합니다. **예시**: `window.map`은 사이트의 맵 상태가
아니라 `id="map"`인 요소였습니다.

### 5.3 번들에서 라이브러리 식별

**적용 조건**: 사이트의 동작을 정확히 예측해야 하는 경우입니다. 휠 한 칸이 몇 배인지, 드래그가
커서와 1:1인지 같은 값이 여기에 해당합니다.

**방법**: 사이트가 받은 번들을 저장해 두고 문자열로 찾습니다. 최소화된 코드라도 원본
라이브러리의 특징적인 문자열(옵션 이름, 이벤트 이름, 오류 문구)은 남아 있어 어떤 라이브러리인지
알아낼 수 있고, 라이브러리를 알면 그 소스를 읽어 규칙을 확정할 수 있습니다.

**예시**: 대상 사이트가 맵 이동에 anvaka/panzoom을 다음 옵션으로 쓴다는 것을 번들에서
확인했습니다.

```
panzoom(.map-wrap, { autocenter: true, bounds: true, smoothScroll: false,
                     minZoom, maxZoom, zoomDoubleClickSpeed: 1,
                     beforeMouseDown, beforeWheel })
```

옵션 목록과 라이브러리 소스에서 세 규칙이 나옵니다. `smoothScroll: false`라 손을 뗀 뒤 관성이 없고, 이동은 커서와
1:1이며, `beforeMouseDown`이 사이트 상태를 보고 이동을 막을 수 있습니다.

**실패 모드**: 최소화된 식별자(`ht`, `pt`, `ve`)는 빌드마다 바뀝니다. 식별자를 근거로 삼으면
다음 배포에서 근거가 사라집니다. 근거는 알아낸 규칙에 두어야 실측으로 다시 확인할 수 있습니다.

**검증**: 알아낸 규칙을 페이지에서 직접 재 봅니다. "휠 한 칸이 1.25배"는 소스를 읽어 얻은
값이지만, 실제로 한 칸 보내고 폭을 재서 확정합니다.

### 5.4 입력을 가로채 고쳐 보내기

**적용 조건**: 사이트의 동작은 그대로 두되, 사용자가 만든 입력에 제어 측 규칙을 얹는
경우입니다. **예시**: "맵을 끌어도 화면 한가운데에는 언제나 맵이 있어야 한다"는 제한.

**방법**: 캡처 단계에서 사이트보다 먼저 이벤트를 받아, 필요하면 좌표를 고친 복제 이벤트를 대신
보냅니다.

```javascript
// 캡처 단계에서 먼저 받는다
window.addEventListener('mousemove', onMove, true);

function onMove(event) {
    if (!dragging || event[OURS]) return;      // 복제 이벤트는 그냥 흘려보낸다
    // ...허용량 계산...
    if (nextX === event.clientX && nextY === event.clientY) return;  // 고칠 게 없으면 원본 통과

    event.stopImmediatePropagation();
    event.preventDefault();
    replaceMove(event, nextX, nextY);          // 고친 좌표로 다시 보낸다
}
```

**실패 모드**: 셋이 알려져 있습니다.

- **복제 이벤트를 자기 처리기가 다시 가로챕니다.** 복제 이벤트에 표시를 남기지 않으면 처리기가
  그것을 또 줄여 사이트에 아무것도 닿지 않습니다. 이벤트 객체에 속성 하나를 붙여 표시합니다.
- **원래 이벤트의 `target`으로 다시 보내면 튑니다.** 커서가 창 밖으로 나가면 그 자리에 요소가
  없어 이벤트가 사이트에 닿지 않고, 사이트가 기억하는 커서 위치가 멈춰 있다가 커서가 돌아오는
  순간 그 차이만큼 한꺼번에 움직입니다. 맵 컨테이너처럼 사라지지 않는 요소로 보내면 사이트가
  어디에 처리기를 달았든 그 위로 전파됩니다.
- **막은 양을 기억하지 않으면 경계에서 밀립니다.** 경계에서 막기만 하면 사용자가 커서를 되돌릴
  때 그동안 벌어진 차이가 한꺼번에 반영됩니다. 넘기지 못한 양을 누적해 두고 커서가 돌아올 때
  상쇄하면 경계에서 즉시 따라옵니다.

**검증**: 커서를 100px씩 옮기며 맵이 몇 px 움직이는지 기록합니다. 경계 전에는 100, 경계에서는
줄어든 값, 되돌릴 때는 다시 100이 나와야 정상입니다.

### 5.5 합성 입력으로 정확히 조작하기

**적용 조건**: 사이트에 특정 배율과 위치를 만들어야 하는 경우입니다. 맵을 열 때 그림이 창을
채우게 맞추는 일이 여기에 해당합니다.

**방법**: 사이트가 이미 처리하는 입력을 만들어 보냅니다. 성패는 어떤 입력을 고르는지가
가르므로, 사이트가 조건에 따라 차단하는 입력을 피하고 차단이 없는 입력을 고릅니다.

**예시** (입력 선택): 드래그는 버리고 배율과 위치를 모두 휠로 맞춥니다. 사이트는 누른 자리에
마커나 그린 도형이 있으면 그것을 옮기는 동작으로 보고 맵 이동을 꺼 버립니다(번들의 마커 층
`mousedown`에서 `togglePanEnabled(false)`). 중심을 맞추려면 화면 한가운데에서 끌어야 하는데 그
자리가 바로 마커가 몰려 있는 자리라, 맵과 위치에 따라 되기도 하고 안 되기도 합니다. 신뢰
입력과 합성 입력이 똑같이 막히므로 입력 종류의 문제가 아닙니다(4절). 휠에는 그 차단이 없습니다.

휠 한 칸은 커서 자리 `a`를 고정점으로 삼아 위치를 다음과 같이 바꿉니다.

```
x' = r * x + (1 - r) * a
```

배율만 필요하면 그림 중심을 고정점으로 두고 한 칸씩 보냅니다. 위치만 필요하면 축소 한 칸과
확대 한 칸을 서로 다른 자리에서 연달아 겁니다.

```
축소(r) at a, 확대(1/r) at b
  ->  x'' = x + (1/r - 1) * (a - b)
  r = 0.8 이면 x'' = x + (a - b) / 4
```

배율은 `0.8 x 1.25 = 1`로 정확히 돌아오고 평행이동만 남으므로, 옮길 거리의 4배만큼 떨어진
자리를 고르면 원하는 만큼 옮겨집니다. 한 칸의 배율 `r`는 라이브러리가 `deltaY`로 정합니다.

**예시** (배율 값): anvaka/panzoom은 `1 - sign(deltaY) * min(0.25, |deltaY| / 128)`을 쓰므로
`deltaY = 25.6`이면 0.8배, `deltaY = -32`이면 1.25배입니다. 두 값이 서로의 역수라는 점이 위
짝을 성립시킵니다. 실측에서 목표 200,120에 결과 200,120, 배율 변화 없음을 확인했습니다.

**실패 모드**: 둘이 알려져 있습니다.

- 두 칸을 시간 간격을 두고 보내면 중간의 축소된 화면이 한 번 그려집니다. 같은 틱에 연달아
  보내면 사용자는 최종 상태만 봅니다.
- 제어 측 조작과 사용자 조작이 겹치면 화면이 손 아래에서 움직입니다. 사용자가 직접 끌거나 휠을
  돌리면(`event.isTrusted`가 true) 그 뒤로는 제어 측 조작을 중단합니다. 제어 측이 보낸 이벤트는
  `isTrusted`가 false라 이 판정에 걸리지 않습니다.

**검증**: 그림이 창에서 차지하는 비율과, 그림 중심과 창 중심의 어긋남을 재서 숫자 합격선을
넘는지 봅니다(7절). **예시**: 맵 12개 전부에서 채움 비율 0.75~0.98, 중심 어긋남 3px 이내를
합격선으로 잽니다.

### 5.6 네트워크 요청 가로채기

**적용 조건**: 대상 사이트가 죽어도 호스트 앱이 돌아야 하는 경우입니다.

**방법**: 브라우저 엔진의 요청 가로채기로 미리 저장해 둔 응답을 돌려줍니다. CefSharp에서는
`IResourceRequestHandlerFactory`가 그 자리입니다. 사본은 실제 브라우저로 페이지를 열어 받은
응답을 그대로 저장해 만들며(`tools/archive-maps.mjs`), 사이트 코드가 무엇을 필요로 하는지 제어
측이 알아낼 필요가 없다는 것이 이 방식의 핵심입니다. 주소는 온라인과 같게 두고 응답만 바꿉니다.

**실패 모드**: 커스텀 스킴을 만들면 사이트의 라우팅과 주입 스크립트의 주소 판정이 모두
어긋납니다. 주소를 온라인과 같게 두는 이유가 이것입니다.

**검증**: 사본만으로 응답하는 상태에서 페이지가 온라인과 같이 동작하는지 봅니다. 설계와 한계는
[오프라인 맵 설계](20260818-offline-map.md)에 있습니다.

### 5.7 금지 기법: 사이트 상태 직접 수정

**적용 조건**: 없습니다. 가장 먼저 떠오르는 방법이지만, 다른 기법이 모두 막혀도 이 방법으로
내려가지 않습니다.

**방법**: 사이트가 내부 상태에서 계산해 그리는 값(CSS `transform` 같은 렌더 산출물)을 제어 측이
직접 쓰는 방식을 말합니다. 쓰지 않습니다.

**실패 모드**: 렌더 층이 둘 이상인 화면에서 한 층만 고치면 반드시 어긋납니다. 사이트의 입력
경로로 들어가면 사이트가 모든 층을 함께 갱신합니다(1절의 원칙 1). **예시**: 맵을 옮기려고
`.map-wrap`의 CSS `transform`을 직접 쓰면 마커만 움직이고 바닥 맵은 그대로 남습니다. 이 사이트는
바닥 맵을 `canvas`에 그리고 마커는 CSS `transform`으로 옮기는데, 둘 다 사이트의 내부 상태에서
나오기 때문입니다.

**검증**: 층의 어긋남은 좌표 수치로 잡히지 않고 스크린샷(7절)에서 드러납니다.

## 6. 실패 모드 색인

아래 표는 이 방식의 작업에서 반복해 나타나는 실패를 증상, 원인, 규칙으로 정리한 색인입니다.
증상으로 찾고 규칙 열이 가리키는 절에서 배경을 봅니다. 마지막 두 줄은 표 아래에서 부연합니다.

| 증상 | 원인 | 규칙 |
|---|---|---|
| 마커만 움직이고 바닥 맵은 그대로 | 렌더 층 두 개 중 하나만 수정 | 상태 대신 입력으로 조작 (5.7절) |
| 숨긴 요소가 되살아남 | 다른 스크립트의 `style.cssText` 대입 | `!important` 스타일시트로 숨김 (5.1절) |
| 디버그 빌드는 정상, 릴리즈만 깨짐 | UI 프레임워크 속성의 갱신 지연 | 엔진 인스턴스와 이벤트 인자로 판정 (3절) |
| 제어 측 조작이 사이트에 전혀 닿지 않음 | 자기가 만든 복제 이벤트를 다시 가로챔 | 복제 이벤트에 표시 남기기 (5.4절) |
| 커서를 창 밖으로 뺐다 넣으면 튐 | 사라진 요소로 이벤트 전송 | 사라지지 않는 컨테이너로 전송 (5.4절) |
| 움직임이 진동하고 텔레포트 | 실측 비율로 나눈 값의 폭주 | 나눗셈 대신 상한과 계수 |
| 맵이 화면 밖으로 사라짐 | 상자 크기로 경계 계산 | 실제 그려진 범위로 계산 |
| 합성 드래그가 맵마다 되고 안 됨 | 누른 자리가 마커면 사이트가 이동을 끔 | 차단 없는 입력(휠)으로 우회 (5.5절) |

**상자와 그림은 다릅니다.** 요소의 상자와 그 안에 실제로 그려진 그림은 다르며, 화면에 남았는지의
판정은 그림을 기준으로 합니다. 상자를 기준으로 판정하면 상자가 화면 가운데를 덮은 채로 그림만
화면 밖으로 나가는 상태를 정상으로 오판합니다. **예시**: `.map-wrap` 상자는 맵 문서
전체(Ground Zero는 2800x3100)이고 실제 그림은 그 안의 일부(800x1100)뿐입니다. 그림 범위는 SVG
자식들의 `getBBox()`를 합쳐 구하고, 뷰박스의 98% 이상을 덮는 자식은 배경이므로 제외합니다.

**한 지점의 측정으로 일반 법칙을 만들지 않습니다.** 조건을 바꿔 여러 번 재고, 성패가 갈리면
갈리는 조건을 원인 후보로 봅니다. **예시**: "합성 입력이 안 먹는다"는 결론은 드래그 시작점을
다섯 군데로 바꿔 재면서 뒤집혔습니다. 세 곳은 정상이었고, 실패한 두 곳은 마커 위였습니다.
원인은 합성 입력 차단이 아니라 마커 위 이동 차단입니다(5.5절).

## 7. 검증 방법론

검증은 판 확인, 과정 기록, 숫자 판정, 시각 확인 네 가지를 갖춥니다.

**판 번호를 심습니다.** 주입 스크립트가 자기 판 번호를 전역에 남기면, 화면이 이상할 때 옛 판이
도는 중인지 새 판이 틀린 것인지 한 번에 갈립니다. 이 구분이 없으면 옛 판의 증상을 새 판의
결함으로 쫓게 됩니다.

```javascript
window.__tanukiKeepVisible = { version: 5, rule: 'fit-on-open + center-clamp', log: function () { return debugLog; } };
```

**과정을 링 버퍼에 남깁니다.** `console.log`는 앱 안에서 사람이 보기 어렵습니다. 최근 몇십 개만
배열에 남기고 전역으로 꺼내면 CDP(4절)로 언제든 읽을 수 있습니다.

**합격 기준을 숫자로 정합니다.** "잘 보인다"가 아니라 "채움 0.75~0.98, 중심 어긋남 3px 이내"로
적습니다. 숫자라야 여러 대상에 일괄로 돌려 표로 만들 수 있습니다.

**마지막에는 눈으로 봅니다.** 스크린샷을 캡처해 확인합니다. 수치가 맞아도 층이 어긋나거나
엉뚱한 영역이 잘려 있는 경우는 여기서 잡습니다.

## 8. 사이트 변경에 취약한 지점

주입 방식은 사이트의 현재 모습에 기대므로, 무엇에 기댔는지와 다시 재는 법을 함께 적어 두어야
다음 사람이 고칠 수 있습니다. 값 자체보다 **다시 재는 법**이 중요합니다. 값은 낡지만 재는 법은
오래 갑니다. 이 저장소가 기대는 값은 다음과 같습니다.

| 기대는 것 | 지금 값 | 다시 재는 법 |
|---|---|---|
| 맵 요소 선택자 | `.map-wrap`, `.pan.map-cont` | 페이지에서 요소 구조 확인 |
| 사이트 전역 함수 | `window.pilot`의 네 함수 | `Object.keys(window.pilot)` |
| 휠 한 칸 배율 | `deltaY 25.6` = 0.8배, `-32` = 1.25배 | 한 칸 보내고 폭 비교 |
| 드래그 비율 | 커서 1px에 맵 1px | 커서 100px 이동 후 비교 |
| 이동 차단 조건 | 마커 위에서 누르면 이동 꺼짐 | 여러 지점에서 끌어 비교 |

## 9. 새 프로젝트 적용 순서

1. 관측 통로부터 만듭니다. 디버그 빌드에서 원격 디버깅 포트를 열고, 붙는 조사 도구를 짧게 하나
   씁니다(4절).
2. 전역과 번들을 훑습니다. 사이트가 열어 둔 함수(5.2절), 쓰는 라이브러리(5.3절), 렌더 층이 몇
   개인지 확인합니다.
3. 가장 약한 개입부터 시도합니다. 스타일시트(5.1절), 사이트 함수 호출(5.2절), 입력
   가로채기(5.4절), 합성 입력(5.5절), 요청 가로채기(5.6절) 순서입니다.
4. 주입 스크립트에 판 번호와 로그를 심습니다(7절).
5. 합격 기준을 숫자로 적고 여러 대상에 일괄로 돌립니다. 마지막은 캡처로 확인합니다(7절).
6. 실측한 값은 근거와 함께 그 값을 쓰는 파일 안에 적습니다. 별도 문서에만 적힌 근거는 다음
   사람이 찾지 못합니다(8절).
