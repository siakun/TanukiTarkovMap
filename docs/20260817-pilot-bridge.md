## 결론

Online에서 앱은 스크린샷 파일명을 직접 읽고, 사이트 지도 위에 내 위치 원과 방향 삼각형을 직접 그립니다.
사이트에서 빌리는 것은 지도 컨테이너와 지도 상태의 좌표 변환(`gamePosToMapPos`, `mapPosToScreenPos`)뿐이고,
사이트의 위치 입력 경로와 내 위치 그리기는 쓰지 않습니다. 지도가 준비되기 전이나 표시가 사라졌을 때는
최신 입력을 보관했다가 다시 맡깁니다. Local 모드는 사이트 코드 없이 앱의 미니맵이 직접 그립니다
([로컬 맵 뷰어 설계](20260821-local-viewer-design.md)). 두 모드의 파일명 해석과 표시 모양은 같습니다.

위치 표시는 페이지 안에서 처리하며 사이트 중계 서버의 연결을 기다리지 않습니다. 아래 기록은 사이트의
위치 입력 경로를 쓰던 시기의 조사와, 그 경로를 버리고 앱이 그리게 된 경위입니다. 유지할 동작은
"지금 구조" 절에 설명합니다.

## 무엇이 깨졌는가

증상은 "스크린샷을 찍어도 맵에 위치가 뜨지 않는다" 하나였습니다. 원인은 앱이 아니라
사이트에 있었고, 다음 네 가지로 확인했습니다.

**앱 로그**: 스크린샷 감지와 파일명 파싱은 정상인데 받아 갈 상대가 없었습니다.

```
[WS] SendFilename: 2026-08-17[20-36]_-125.67, 5.64, -364.04_... .png | Clients: 0
[WS] No connected clients - skipping send
```

같은 자리에 하루 전(2026-08-16 03:24) 로그는 `Clients: 1`, `Sent to 1 client(s)`였습니다.

**사이트 번들**: pilot 페이지와 맵 페이지가 받는 `/_nuxt3` 청크를 모두 내려받아 훑었습니다.
`localhost:5123` 문자열은 어디에도 없고, `new WebSocket`은 `wss://tarkov-market.com/ws/pilot`
한 곳뿐이었습니다. 그 연결도 로그인 사용자가 없으면 시도하지 않습니다.

**브라우저 캐시와의 대조**: 앱의 CEF 코드 캐시에 남아 있던 이전 번들(2026-08-17 00:05 기록)에는
아직 `ws://localhost:5123`이 들어 있었습니다. 바뀐 시점을 그 사이로 좁힐 수 있었습니다.

**사이트 공지**: pilot 페이지 상단이 Pilot v2 배포를 알리며 옛 버전은 더 동작하지 않는다고
적고 있었습니다. 페이지 하단의 갱신 시각은 같은 날 09:39이었습니다.

정리하면 연동 구조가 이렇게 바뀌었습니다.

```
v1 (2026-08-17 이전)
  브라우저 --접속--> 로컬 앱의 WebSocket 서버 (포트 5123)

v2 (초기 조사 당시)
  브라우저 --접속--> tarkov-market 서버 <--접속-- 공식 앱
                     (계정에 묶인 중계, 로그인 필요)
```

앱은 v1의 서버 쪽을 맡고 있었으므로, 서버를 그대로 띄워도 접속하는 클라이언트가 영영
생기지 않는 상태가 됐습니다.

## 고를 수 있었던 세 가지 길

| 길 | 필요한 일 | 버린 이유 |
|----|-----------|-----------|
| v2 중계 규약 따라가기 | 계정 인증, 앱 등록, 서버 프로토콜 추적 | 사이트 계정 자격을 앱이 다루게 되고, 사이트가 규약을 바꿀 때마다 다시 깨짐 |
| 좌표를 앱이 직접 그리기 | 맵별 좌표 변환과 마커 렌더링을 앱이 구현 | 사이트가 이미 하는 일을 맵 개수만큼 다시 만들고, 맵이 갱신될 때마다 따라가야 함 |
| `window.pilot` 직접 호출 | 페이지에 호출 통로 등록, 파일명 전달 | 선택. 사이트가 스스로 쓰는 진입점이라 좌표 해석과 마커 표시가 전부 사이트 몫으로 남음 |

## 어떻게 그 진입점을 찾았는가

번들을 읽어 사이트가 자기 기능을 어디서 노출하는지 확인했습니다. 루트 컴포넌트가 마운트될 때
전역 객체에 네 함수를 등록합니다.

```js
window.pilot = {
  position,                 // 좌표를 직접 넘김
  positionFromScreenshot,   // 스크린샷 파일명을 넘김 (좌표 파싱은 사이트가 함)
  mapChange,                // 맵 전환
  questComplete             // 퀘스트 완료
}
```

세 가지가 중요했습니다.

- 등록은 로그인 여부와 무관하게, 모든 페이지에서 일어납니다.
- `positionFromScreenshot`은 파일명을 사이트가 직접 정규식으로 파싱해 마커를 옮깁니다.
  중계 서버를 거치지 않으므로 연결 상태와 무관합니다.
- 맵 전환은 앱이 주소를 직접 바꾸므로 `mapChange`를 쓸 이유가 없습니다.

## 검증 방법

앱을 고치기 전에 사이트에서 가정부터 확인했습니다. 일반 브라우저로 `tarkov-market.com/maps/lab`을
열고, 로그인하지 않은 상태에서 실제 로그에 남은 파일명을 그대로 넘겼습니다.

- `window.pilot`의 네 함수가 모두 존재했습니다.
- 호출 직후 Lab 맵에 위치 마커가 찍혔습니다.
- 그 마커 요소는 여전히 `class="marker"`에 `rotate(...)` 변환을 가지고 있어,
  기존 방향 표시기 스크립트(`map-markers.js`)가 그대로 붙습니다.

가정이 사실인 것을 확인한 뒤에 앱을 고쳤습니다. 퀘스트 완료 전달은 사이트에서 pro 계정으로
로그인해야 반영되므로, 통로만 같은 방식으로 연결하고 실제 반영은 확인하지 않았습니다.

## 2026-10-07: 프로그램용 위치 입력이 사라짐

증상은 다시 "스크린샷을 찍어도 위치가 뜨지 않는다"였고, 앱 로그에는
`Screenshot pending: pilot-unavailable`만 남았습니다. 그날 배포된 번들에서 `window.pilot`의
`positionFromScreenshot`과 Nuxt Pilot 서비스의 `positionUpdate`가 모두 사라졌고, 서비스에는 구독
함수만 남았습니다. 앱이 쓰던 두 진입점이 한꺼번에 없어진 것입니다.

남은 입력은 상단 패널의 "Where am i" 창이었습니다. 사용자가 스크린샷 파일명을 붙여 넣으면 사이트가
직접 파싱해 마커를 옮깁니다. 브리지는 이 창의 입력 처리기를 썼습니다. 이 경로는 다음 날 앱이 위치를 직접
그리게 되면서 쓰지 않습니다(아래 "2026-10-08: 내 위치를 앱이 그림").

- 처리기는 렌더 중인 Vue 트리에서 `onScreenPositionChange` 함수와 `playerData` 객체를 props로 가진
  컴포넌트를 찾아 얻었습니다. 템플릿의 prop 이름은 번들을 압축해도 남지만, 청크 이름과 setup 안의
  변수명은 배포마다 바뀝니다.
- 처리기는 `{ target: { value: 파일명 } }`을 입력 사건처럼 받습니다. 붙여 넣기 처리기는 좌표만 바꾸고
  마커는 창이 열린 동안만 보이므로, Pilot 입력과 같은 표시 상태(`playerData.isPlayerMarkerVisible`)를
  켜고 위치 핑을 함께 불렀습니다.
- 입력란에 글자를 넣는 합성 입력은 버렸습니다. 창을 열어야 하고 앱의 UI 숨김과 충돌합니다. 압축된
  내부 함수를 이름으로 부르는 방법은 배포마다 이름이 바뀝니다. 사이트 상태(`playerPos`)를 직접 쓰는
  방법은 사이트의 갱신 경로를 건너뛰어 마커와 상태가 어긋날 수 있습니다.

새 위치가 지도 화면 밖이나 가장자리에 있으면 사이트의 `centerOnPosition`으로 가운데에 놓습니다.
사이트의 Pilot 입력은 확대한 상태에서만 가운데로 옮기는데, 작은 오버레이 창에서는 그보다 낮은
배율에서도 마커가 화면 밖에 놓입니다. 이 규칙은 앱이 위치를 그리는 지금도 같습니다.

## 2026-10-08: 지도가 캔버스로 바뀌고 지도 상태가 렌더 트리에서 빠짐

증상은 두 가지였습니다. Online에서 방향 표시가 보이지 않았고, 새 스크린샷이 없는데도 내 위치가 몇 초
간격으로 커졌다 줄어들었습니다. Local은 정상이었습니다. 사이트가 지도 화면을 다시 짠 결과였습니다.

- 마커와 내 위치를 DOM 요소가 아니라 캔버스(`markers-canvas`, `players-canvas`)에 그립니다. 방향 화살표가
  붙던 `.marker` 요소와 확대와 이동이 걸리던 `.map-wrap`이 없습니다.
- 내 위치는 원으로 그리고, 방향 화살표는 PRO 사용자에게만 그립니다. 렌더러가 사용자 정보의 `pro`를 확인합니다.
- 좌표 변환과 panzoom을 가진 지도 상태를 하위 컴포넌트에 props로 넘기지 않고, getter만 가진 얼린 객체
  (`view`)를 넘깁니다. 지도 상태는 페이지 컴포넌트의 클로저 안에만 남습니다.

두 증상의 원인은 하나였습니다. 브리지가 지도 상태를 찾지 못해 위치 확인이 늘 실패했고, 앱의 2초 점검이
같은 파일을 계속 다시 보냈습니다. 브리지는 보낼 때마다 사이트의 핑을 켰습니다. 사이트의 핑 표시는 2초
동안 켜져 있다가 꺼지고, 꺼졌다 다시 켜질 때만 애니메이션(약 0.7초 동안 최대 2.5배)을 새로 시작합니다.
그래서 재전송 간격이 2초를 조금 넘는 때에만 애니메이션이 보여 불규칙한 주기로 보였습니다. 방향 표시는
붙을 요소가 없어 그려지지 않았습니다.

고친 방법은 다음과 같습니다.

- 지도 상태는 만들어지는 순간에 기록합니다. Vue의 `reactive()`는 원본을 키로, 프록시를 값으로 WeakMap에
  등록하므로, 로드 시작 시점에 `WeakMap.prototype.set`을 감싸 지도 상태 모양의 프록시만 기록합니다
  (`map-state-capture.js`). 원래 동작과 반환값은 그대로 두고, 모양은 앱이 쓰는 칸(컨테이너와 두 좌표 변환)으로
  판정합니다.
- 내 위치와 방향은 사이트가 그린 원에 덧붙이지 않고 앱이 모두 그립니다. 그렇게 정한 이유는 다음 절에 있습니다.
- 핑은 새 스크린샷이 처음 보일 때만 켭니다. 같은 파일을 다시 보낼 때는 켜지 않으므로, 확인이 다시 깨져
  재전송이 반복돼도 위치가 커졌다 줄어들지 않습니다.

구조를 보고 검토했지만 고르지 않은 방법도 있습니다. 직접 시도해 실패한 것이 아니라 번들의 구조에서
한계를 판단했습니다.

| 방법 | 고르지 않은 이유 |
|------|------------------|
| 캔버스 컨텍스트의 그리기 함수를 감싸 내 위치 자리를 읽기 | 사이트 렌더러의 그리기 순서에 묶여 렌더러를 조금만 바꿔도 깨짐 |
| 내 위치 캔버스의 픽셀에서 원을 찾기 | 원이 화면 밖이면 자리를 알 수 없고, 위치 확인을 그림에 걸게 됨 |
| 나침반 요소의 인라인 스타일에서 panzoom 변환을 역산 | 회전과 기준 배율이 섞인 값이라, 사이트가 식을 바꾸면 조용히 틀림 |
| 사이트의 PRO 화살표를 켜기 | 사이트의 유료 기능을 우회하는 일이라 하지 않음 |

기록 스크립트는 사이트가 지도 상태를 만들기 전에 들어가야 합니다. 앱은 `page-health.js`와 같은
`FrameLoadStart`에 넣습니다. 늦게 들어가 기록이 없으면 Online은 위치를 그리지 않고 `map-unavailable`을
남깁니다.

## 2026-10-08: 내 위치를 앱이 그림

캔버스 판을 고치면서 위치 표시를 사이트에서 떼어 냈습니다. 그때까지 위치 표시는 사이트의 두 부분에 묶여
있었습니다. 위치를 넣는 입력 경로와 사이트가 내 위치를 그리는 렌더러입니다. 둘은 배포 때마다 바뀌었습니다.
입력 경로는 WebSocket, 전역 함수, Nuxt 서비스, "Where am i" 처리기로 옮겨 갔고, 렌더러는 DOM 요소에서
캔버스로 옮기며 방향을 PRO 전용으로 바꿨습니다. 반면 지도 상태의 좌표 변환(`gamePosToMapPos`,
`mapPosToScreenPos`)은 그동안 같은 이름으로 남았습니다.

그래서 Online의 위치 표시를 앱이 맡았습니다.

- 파일명은 앱이 읽습니다. Local 미니맵(`viewer/coords.js`)과 같은 정규식, 축 순서, 방향 식을 쓰며
  `verify-map-recovery.mjs`가 두 해석을 대조합니다.
- 내 위치 원과 방향 삼각형은 `map-markers.js`가 지도 컨테이너에 얹은 요소로 그립니다. 모양은 Local 미니맵의
  내 위치와 같습니다. 자리와 각도는 브리지가 사이트의 좌표 변환으로 구해 매 프레임 넘깁니다.
- 핑은 새 스크린샷이 처음 보일 때 앱이 켭니다. 사이트의 핑과 표시 상태(`playerData`)는 쓰지 않습니다.
- 성공은 앱이 그린 마커가 지도에 보이는 것으로 판정합니다. 사이트의 `playerPos`는 판정에 쓰지 않습니다.
- 지도 상태 기록은 앱이 쓰는 칸(컨테이너와 두 좌표 변환)만으로 지도 상태를 알아봅니다. 쓰지 않는 칸까지
  요구하면 사이트가 그 칸만 바꿔도 기록이 빕니다.

처음에 "좌표를 앱이 직접 그리기"를 버린 이유는 맵별 좌표 변환을 앱이 다시 구현해야 한다는 데 있었습니다.
지금 방식은 변환을 구현하지 않고 사이트의 변환을 그대로 부르므로 그 이유에 해당하지 않습니다. 변환을 앱에
따로 두면(리소스의 `meta.json` 변환 등) 사이트가 식이나 지도 갱신으로 값을 바꿀 때 마커가 지형과 어긋난 채
경고 없이 남습니다. 사이트의 변환을 쓰면 사이트가 식을 바꿔도 마커가 지형과 함께 움직이고, 변환이 사라지면
틀린 자리에 그리지 않고 `map-unavailable`로 멈춥니다. 틀린 위치를 확신 있게 보여 주는 것보다 멈추고
알리는 편이 안전합니다.

대가도 있습니다.

|------|------|------|

- 사이트는 앱이 그린 위치를 모릅니다. 층 선택 말고 사이트의 내 위치 기능(스쿼드 공유, 사이트 UI의 위치 표시)에는

## 2026-10-09: 층은 사이트가 고르게 함

앱이 위치를 직접 그리게 바꾼 뒤 Online에서 층이 자동으로 바뀌지 않았습니다. 원인은 사이트가 층을 고르는
방식에 있었습니다.

- 사이트의 층 선택 코드(층 데이터 표를 만드는 컴포저블)는 지도 상태의 `playerPos`를 깊게 지켜보다가 값이 바뀌면
  그 위치로 층을 고릅니다. 구역 안이고 높이가 맞는 층을 먼저 찾고, 없으면 층의 높이 범위로 찾습니다. Local
  미니맵의 `levelAtPosition`(`viewer/coords.js`)이 이 규칙을 옮긴 식입니다.
- "Where am i" 처리기는 `playerPos`를 바꾸는 일만 하고, 층은 그 변화를 본 watcher가 바꿉니다. 그래서 처리기를
  쓰던 때에는 층이 바뀌었고, 앱이 `playerPos`를 건드리지 않게 되자 층도 멈췄습니다. 앞 절을 쓸 때는 처리기와
  Pilot 입력만 읽고 "처리기는 층을 바꾸지 않는다"고 판단했는데, 층 선택 코드는 지도 화면과 다른 번들 파일에
  있었습니다.

고친 방법은 다음과 같습니다.

- 위치를 보일 때 같은 좌표를 `playerPos`의 x, y, z에 넣습니다. 방향(`look`)과 사이트의 표시 상태는 건드리지
  않으므로 사이트는 자기 원을 그리지 않습니다. 번들에서 `playerPos`를 읽는 곳은 층 선택, 사이트의 내 위치
  그리기, 상태 표시줄이었고 이 좌표를 서버로 보내는 경로는 없었습니다.
- 층(`selectedLevel`)은 직접 쓰지 않습니다. 사이트의 층 선택 상태에서 계산되는 값이라 직접 쓰면 Levels 패널과
  마커 필터가 어긋납니다.
- 사이트는 층 데이터(지도 문서의 높이 범위와 구역)가 채워지기 전에 바뀐 위치로는 층을 고르지 않고, 데이터가
  채워진 뒤에 다시 고르지도 않습니다. 앱은 맵을 열자마자 위치를 맡기므로 이 경합이 실제로 생깁니다. 그래서
  지도 상태 기록이 층 데이터 표도 함께 기록하고, 브리지는 표에 높이나 구역이 채워질 때까지 기다렸다가 좌표를
  넣습니다. 표를 기록하지 못한 판에서는 기다리지 않고 바로 넣습니다.
- 같은 좌표를 다시 넣으면 사이트가 반응하지 않습니다. 같은 스크린샷을 다시 맡겨도 사용자가 손으로 고른 층은
  그대로 남고, 좌표가 다른 새 스크린샷이 오면 사이트가 다시 고릅니다.

| 고르지 않은 방법 | 이유 |
|------|------|
| "Where am i" 처리기를 다시 부르기 | 같은 칸을 쓰는 일만 하는데, 처리기를 찾는 경로(렌더 트리의 props)에 다시 묶임 |
| 리소스의 층 데이터로 앱이 층을 정하고 사이트의 층을 바꾸기 | 사이트의 층 데이터와 리소스가 어긋날 수 있고, 층을 바꾸는 입구(Levels 패널, Alt 휠)는 화면 배치에 따라 없거나 한 칸씩만 움직임 |
| 일정 시간 뒤에 좌표를 다시 흔들어 넣기 | 그 사이 사용자가 고른 층을 덮어쓰고, 층 데이터가 그보다 늦으면 여전히 놓침 |

브리지가 부르는 사이트 함수는 좌표 변환 둘과 화면 이동(`centerOnPosition`), 퀘스트 완료(`questComplete`)뿐이고,
사이트 상태에 쓰는 값은 층 선택을 위한 `playerPos`의 x, y, z뿐입니다.
호출이 끝났어도 앱이 그린 마커가 지도에 보이지 않으면 성공으로 처리하지 않습니다. 같은 파일을 다시 맡길
때는 핑을 켜지 않습니다. 다른 맵 주소로 옮기면 그 맵에서 맡은 위치는 끝나고, 같은 주소에서 사이트가 지도
상태를 새로 만들면 지난 지도에 그린 마커를 숨긴 뒤 앱의 다음 점검이 같은 파일을 새 지도에 맡깁니다.
사이트가 컨테이너 요소만 바꾸면 마커가 지도 상태의 새 컨테이너로 옮겨 갑니다.

지도 맞춤 스크립트(`map-keep-visible.js`)도 같은 지도 상태를 브리지의 `getMap()`으로 얻어 화면을
옮기고, 맞춤이 끝날 때마다 `revealPosition()`으로 마커가 화면 안쪽에 남았는지 확인합니다. 앱은
맵을 열자마자 위치를 보내고 맞춤은 그 뒤에 돌기 때문입니다.

방향은 파일명의 quaternion으로 계산합니다. 기록한 지도 상태의 좌표 변환으로 방향 벡터와 위치를
화면 좌표로 투영하므로 지도마다 다른 회전과 화면 회전을 함께 반영합니다. 원과 삼각형은 지도 컨테이너에
얹은 요소 하나(원 안에 삼각형)이고, 위치를 맡은 지도가 화면에 붙어 있는 동안 매 프레임 자리와 각도를
다시 맞춥니다.

같은 지도에서 새로고침하거나 스크립트를 복구하면 마지막 입력을 다시 사용합니다. Online/Local
전환으로 브라우저가 교체될 때도 마지막 입력을 맵 이름에 묶어 보관하고, 준비용 `about:blank`는
맵 이동으로 처리하지 않습니다. 다른 지도로 이동하면 보관한 입력을 버려 지난 좌표가 새 지도에
나타나지 않게 합니다. 이전 문서에서 뒤늦게 돌아온 응답은 새 문서의 성공으로 처리하지 않습니다.
Local 브라우저의 저장 공간 분리는 [오프라인 맵 설계](20260818-offline-map.md)를 따릅니다.

퀘스트 완료는 같은 브리지가 사이트의 Pilot 서비스로 전달하지만 위치 재시도 큐에는 넣지 않습니다. 사이트
계정에 따른 퀘스트 반영 여부는 별도 조건입니다.

파일명 인자는 `JsonSerializer`로 감싸 넘깁니다. 스크린샷 파일명에는 공백, 쉼표, 괄호가
들어가므로 따옴표로 직접 감싸면 호출문이 깨집니다.

## 사이트가 또 바꿀 때 알아차리는 방법

이 경로는 사이트 내부의 지도 상태 모양(reactive 객체로 만들고 컨테이너와 두 좌표 변환을 가짐)과 그 변환의
의미에 의존합니다. 위치 입력 경로와 사이트의 내 위치 렌더러에는 의존하지 않습니다. 지도 상태가 바뀌는
변경까지 자동으로 해석할 수는 없으므로, 대기 이유와 복구 결과를 로그로 남깁니다.

층 자동 선택은 따로 두 가지에 더 의존합니다. 사이트가 `playerPos`의 변화로 층을 고른다는 점과 층 데이터 표의
모양(층 이름마다 `num`과 `visible`을 가짐)입니다. 이 둘이 바뀌어도 위치 표시는 그대로 돌고 층만 바뀌지
않습니다. 그때는 `tanukiPilot.levelSync()`의 `state`로 어디서 멈췄는지 봅니다. `waiting`이 끝나지 않으면 층
데이터가 채워지지 않는 것이고, `no-level-data`면 층 데이터 표를 기록하지 못한 것이며, `synced`인데 층이 그대로면
사이트가 층을 고르는 방식이 바뀐 것입니다.

| 로그 | 뜻 |
|------|-----|
| `Marker script restored` / `Bridge restored` | 응답하지 않는 앱 스크립트 복구 |
| `Position rendered` | 앱이 그린 마커가 지도에 보여 대기 해제 |
| `Screenshot pending: invalid-screenshot` | 파일명에서 좌표와 회전값을 읽지 못함 |
| `Screenshot pending: map-unavailable (capture-missing)` | 지도 상태 기록 스크립트가 페이지에 없음 |
| `Screenshot pending: map-unavailable (not-captured)` | 기록 스크립트가 지도 상태보다 늦게 들어갔거나 지도 상태의 모양이 바뀜 |
| `Screenshot pending: marker-unavailable` | 내 위치 표시 스크립트가 페이지에 없음. 다음 점검에서 앱이 다시 넣음 |
| `Screenshot pending: position-not-shown` | 마커를 붙였지만 화면에 보이지 않음 (지도 영역이 숨겨진 경우 등) |
| `Screenshot pending: site-error: ...` | 사이트의 좌표 변환이 예외를 던짐 |

대기가 이어지면 앱 없이 `node tools/verify-online.mjs --maps <맵>`으로 지금 사이트에서 같은
스크립트를 실행해 봅니다. 앱이 그린 원이 사이트가 같은 파일명으로 그리는 자리와 맞는지, 방향 삼각형이
맞는지, 맵을 열자마자 맡긴 다른 층의 위치로 사이트가 층을 바꾸는지 맵마다 보여 줍니다.
페이지 로딩 실패는 `page-health.js` 로그와 함께 확인합니다. 재주입으로 복구되는 앱 스크립트 누락과
사이트 연동 규약 변경을 구분해 조사합니다.

페이지 후처리를 시작할 때 준비 판정을 `ChromiumWebBrowser`의
`IsBrowserInitialized`나 `Address`로 하면 안 됩니다. 둘 다 WPF DependencyProperty여서 CEF가
UI 스레드에 따로 게시해 갱신하고, 릴리즈 빌드에서는 첫 페이지 로드가 그 갱신을 앞질러
등록이 통째로 빠집니다(0.2.3에서 실제로 겪은 일). 주소는 이벤트가 준 값을 쓰고, 준비 상태는
`BrowserCore`로 봅니다.

## 다시 뒤집을 조건

아래 전제가 깨지면 그때 재검토합니다. 그 전에는 이 구조를 유지합니다.

- 사이트가 지도 상태에서 좌표 변환을 없애거나, 지도 상태를 reactive 객체로 만들지 않아 만들어지는 순간에도
  기록할 수 없는 경우. 그동안 Online은 위치를 표시하지 않고 Local이 유일한 경로가 됩니다. 그때 좌표 변환을
  앱에 따로 두는 방법을 검토한다면, 사이트 지도와 어긋나는지 검사할 방법을 함께 마련합니다
- 사이트가 로컬 앱을 다시 직접 지원하고, 그 규약이 계정 자격을 요구하지 않는 경우
