# Pilot 연동과 위치 전달 경로

사이트 쪽 구조가 바뀐 뒤에 남은 유일하게 단순한 길입니다. 2026-08-17, tarkov-market이

## 결론

앱은 스크린샷 파일명의 좌표를 페이지 안의 Pilot 서비스에 넘깁니다. JavaScript 어댑터가
전역 객체와 Nuxt 서비스 중 사용 가능한 경로를 선택하며, 지도와 방향 표시가 준비되기 전에는
최신 입력을 보관했다가 다시 전달합니다.

위치 전달은 페이지 안에서 처리하며 사이트 중계 서버의 연결을 기다리지 않습니다.
아래의 초기 조사 기록은 전역 `window.pilot`을 선택했던 배경이고, 유지할 동작은
"지금 구조" 절에 설명합니다.

## 무엇이 깨졌는가

증상은 "스크린샷을 찍어도 맵에 위치가 뜨지 않는다" 하나였습니다. 원인은 앱이 아니라
사이트에 있었고, 다음 네 가지로 확인했습니다.

**앱 로그**: 스크린샷 감지와 파일명 파싱은 정상인데 받아 갈 상대가 없었습니다.

```
[WS] SendFilename: 2026-08-17[20-36]_-125.67, 5.64, -364.04_... .png | Clients: 0
[WS] No connected clients - skipping send
```

같은 자리에 하루 전(2026-08-16 03:24) 로그는 `Clients: 1`, `Sent to 1 client(s)`였습니다.

**사이트 번들**: pilot 페이지와 맵 페이지가 받는 `/_nuxt3` 청크를 모두 내려받아 훑었습니다.
`localhost:5123` 문자열은 어디에도 없고, `new WebSocket`은 `wss://tarkov-market.com/ws/pilot`
한 곳뿐이었습니다. 그 연결도 로그인 사용자가 없으면 시도하지 않습니다.

**브라우저 캐시와의 대조**: 앱의 CEF 코드 캐시에 남아 있던 이전 번들(2026-08-17 00:05 기록)에는
아직 `ws://localhost:5123`이 들어 있었습니다. 바뀐 시점을 그 사이로 좁힐 수 있었습니다.

**사이트 공지**: pilot 페이지 상단이 Pilot v2 배포를 알리며 옛 버전은 더 동작하지 않는다고
적고 있었습니다. 페이지 하단의 갱신 시각은 같은 날 09:39이었습니다.

정리하면 연동 구조가 이렇게 바뀌었습니다.

```
v1 (2026-08-17 이전)
  브라우저 --접속--> 로컬 앱의 WebSocket 서버 (포트 5123)

v2 (초기 조사 당시)
  브라우저 --접속--> tarkov-market 서버 <--접속-- 공식 앱
                     (계정에 묶인 중계, 로그인 필요)
```

앱은 v1의 서버 쪽을 맡고 있었으므로, 서버를 그대로 띄워도 접속하는 클라이언트가 영영
생기지 않는 상태가 됐습니다.

## 고를 수 있었던 세 가지 길

| 길 | 필요한 일 | 버린 이유 |
|----|-----------|-----------|
| v2 중계 규약 따라가기 | 계정 인증, 앱 등록, 서버 프로토콜 추적 | 사이트 계정 자격을 앱이 다루게 되고, 사이트가 규약을 바꿀 때마다 다시 깨짐 |
| 좌표를 앱이 직접 그리기 | 맵별 좌표 변환과 마커 렌더링을 앱이 구현 | 사이트가 이미 하는 일을 맵 개수만큼 다시 만들고, 맵이 갱신될 때마다 따라가야 함 |
| `window.pilot` 직접 호출 | 페이지에 호출 통로 등록, 파일명 전달 | 선택. 사이트가 스스로 쓰는 진입점이라 좌표 해석과 마커 표시가 전부 사이트 몫으로 남음 |

## 어떻게 그 진입점을 찾았는가

번들을 읽어 사이트가 자기 기능을 어디서 노출하는지 확인했습니다. 루트 컴포넌트가 마운트될 때
전역 객체에 네 함수를 등록합니다.

```js
window.pilot = {
  position,                 // 좌표를 직접 넘김
  positionFromScreenshot,   // 스크린샷 파일명을 넘김 (좌표 파싱은 사이트가 함)
  mapChange,                // 맵 전환
  questComplete             // 퀘스트 완료
}
```

세 가지가 중요했습니다.

- 등록은 로그인 여부와 무관하게, 모든 페이지에서 일어납니다.
- `positionFromScreenshot`은 파일명을 사이트가 직접 정규식으로 파싱해 마커를 옮깁니다.
  중계 서버를 거치지 않으므로 연결 상태와 무관합니다.
- 맵 전환은 앱이 주소를 직접 바꾸므로 `mapChange`를 쓸 이유가 없습니다.

## 검증 방법

앱을 고치기 전에 사이트에서 가정부터 확인했습니다. 일반 브라우저로 `tarkov-market.com/maps/lab`을
열고, 로그인하지 않은 상태에서 실제 로그에 남은 파일명을 그대로 넘겼습니다.

- `window.pilot`의 네 함수가 모두 존재했습니다.
- 호출 직후 Lab 맵에 위치 마커가 찍혔습니다.
- 그 마커 요소는 여전히 `class="marker"`에 `rotate(...)` 변환을 가지고 있어,
  기존 방향 표시기 스크립트(`map-markers.js`)가 그대로 붙습니다.

가정이 사실인 것을 확인한 뒤에 앱을 고쳤습니다. 퀘스트 완료 전달은 사이트에서 pro 계정으로
로그인해야 반영되므로, 통로만 같은 방식으로 연결하고 실제 반영은 확인하지 않았습니다.

## 지금 구조

<!-- INTENT
페이지의 일회성 로드 완료와 함수 호출 성공만으로는 지도 반영을 보장하지 못합니다.
최신 입력과 문서 수명은 호스트가 관리하고, 사이트의 진입점 및 좌표 변환 차이는 JS 어댑터에
모읍니다. 지도별 각도를 앱에 복제하지 않아 사본과 온라인 지도를 각각의 변환으로 표시합니다.
-->

```
스크린샷 감지
  -> 필요한 맵 전환을 먼저 요청
  -> WebBrowserViewModel이 대상 맵과 최신 파일명을 보관
  -> 페이지 로드 완료 / 주기 확인 / 스크린샷 수신
  -> 방향 스크립트와 Pilot 브리지 응답 확인 및 복구
  -> CefSharp EvaluateScriptAsPromiseAsync
  -> window.tanukiPilot -> 사용 가능한 Pilot 서비스
  -> 위치 마커와 방향 표시 준비 확인
  -> 성공하면 대기 해제, 실패하면 최신 입력 재시도
```

지원하는 진입점은 `Scripts/pilot-bridge.js`의 `getPilot()`에서 확인합니다. 전역 `window.pilot`이
없어도 Nuxt가 제공하는 Pilot 서비스를 찾으며, 사용할 때마다 함수가 있는지 확인합니다.
함수 호출이 끝났어도 지도의 플레이어 좌표가 입력과 다르거나 위치 마커 또는 방향 계산에 필요한
지도가 없으면 성공으로 처리하지 않습니다.

방향은 파일명의 quaternion으로 계산합니다. 렌더 중인 Vue 트리에서 좌표 변환 기능을 가진
지도 객체를 찾아 방향 벡터를 화면 좌표로 투영하므로 지도마다 다른 회전과 화면 회전을 함께
반영합니다. 사이트 마커의 위치와 CSS 변환은 보존하고, 앱이 붙인 화살표의 각도만 보정합니다.

같은 지도에서 새로고침하거나 스크립트를 복구하면 마지막 입력을 다시 사용합니다. Online/Local
전환으로 브라우저가 교체될 때도 마지막 입력을 보관하고, 준비용 `about:blank`는 맵 이동으로
처리하지 않습니다. 다른 지도로
이동하면 보관한 입력을 버려 지난 좌표가 새 지도에 나타나지 않게 합니다. 이전 문서에서 뒤늦게
돌아온 응답은 새 문서의 성공으로 처리하지 않습니다. 저장 공간을 공유해 사이트 초기화 자체가
실패한 경우에는 입력 재시도로 해결되지 않으므로, Local의 저장 공간도
[오프라인 맵 설계](20260818-offline-map.md)에 따라 분리합니다.

퀘스트 완료는 같은 어댑터로 전달하지만 위치 재시도 큐에는 넣지 않습니다. 사이트 계정에 따른
퀘스트 반영 여부는 별도 조건입니다.

파일명 인자는 `JsonSerializer`로 감싸 넘깁니다. 스크린샷 파일명에는 공백, 쉼표, 괄호가
들어가므로 따옴표로 직접 감싸면 호출문이 깨집니다.

## 함께 걷어낸 것

한 가지 경로를 바꾸면서 그 경로에만 쓰이던 것을 같이 정리했습니다.

- 포트 5123의 WebSocket 서버와 그 전용 메시지 타입. 접속하는 클라이언트가 없어졌습니다.
- `Microsoft.AspNetCore.App` 프레임워크 참조. Kestrel을 쓰던 곳이 그 서버뿐이었습니다.
- pilot 연결 감지 스크립트. v2에서 "Connected" 표시는 사이트가 자기 서버에 붙었다는 뜻이라
  앱과 무관하고, 로그인해야 뜹니다. 첫 실행 진입이 이 감지에 묶여 있었으므로 함께 풀었습니다.

## 사이트가 또 바꿀 때 알아차리는 방법

이 경로는 사이트 내부의 Pilot 서비스, Vue 트리와 위치 마커 구조에 의존합니다. 지원하는 경로가
사라지는 변경까지 자동으로 해석할 수는 없으므로, 대기 이유와 복구 결과를 로그로 남깁니다.

| 로그 | 뜻 |
|------|-----|
| `Direction script restored` / `Bridge restored` | 응답하지 않는 앱 스크립트 복구 |
| `Position rendered` | 플레이어 좌표 일치, 위치 마커 존재와 방향 계산 확인 후 대기 해제 |
| `Screenshot pending: pilot-unavailable` | 지원하는 Pilot 진입점 대기 |
| `Screenshot pending: position-not-rendered` | 함수 호출 후 위치 마커 대기 |
| `Screenshot pending: direction-not-ready` | 방향 계산에 필요한 지도 상태 대기 |
| `Screenshot pending: site-error: ...` | 사이트 함수 실행 중 오류 |

대기가 이어지면 `pilot-bridge.js`가 찾는 서비스와 지도의 좌표 변환 함수가 실제 페이지에 있는지
확인합니다. 페이지 로딩 실패는 `page-health.js` 로그와 함께 확인합니다. 재주입으로 복구되는
앱 스크립트 누락과 사이트 연동 규약 변경을 구분해 조사합니다.

페이지 후처리를 시작할 때 준비 판정을 `ChromiumWebBrowser`의
`IsBrowserInitialized`나 `Address`로 하면 안 됩니다. 둘 다 WPF DependencyProperty여서 CEF가
UI 스레드에 따로 게시해 갱신하고, 릴리즈 빌드에서는 첫 페이지 로드가 그 갱신을 앞질러
등록이 통째로 빠집니다(0.2.3에서 실제로 겪은 일). 주소는 이벤트가 준 값을 쓰고, 준비 상태는
`BrowserCore`로 봅니다.

## 다시 뒤집을 조건

아래 전제가 깨지면 그때 재검토합니다. 그 전에는 이 구조를 유지합니다.

- 어댑터가 지원하는 Pilot 서비스나 지도 좌표 변환 경로가 모두 사라지는 경우
- 사이트가 로컬 앱을 다시 직접 지원하고, 그 규약이 계정 자격을 요구하지 않는 경우
- 위치 표시 외에 사이트 계정과 묶인 기능(퀘스트 자동 완료, 스쿼드 공유)이 앱의 주된 목적이
  되는 경우. 그때는 중계 규약을 따라가는 비용이 정당해집니다
