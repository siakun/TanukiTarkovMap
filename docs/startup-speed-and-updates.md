## 결론

앱은 업데이트를 기다리지 않고 먼저 엽니다. 업데이트 확인과 다운로드는 창이 열린 뒤
백그라운드에서 하고, 적용은 앱을 닫을 때 합니다.

시작 속도가 이 앱의 다른 어떤 것보다 앞섭니다.

## 처음 구상과 버린 이유

원래는 `SplashWindow`가 업데이트를 관리하기로 했습니다. Discord처럼 "시작하는 중 ->
업데이트 확인 중 -> 다운로드 중 -> 열림" 순서로 진행하고, 최신 상태가 된 다음에
메인 창을 여는 방식입니다. `SplashWindow`의 `SetStatus`와 진행바는 그 목적으로
만들었습니다.

버린 이유는 셋입니다.

**이 앱은 목적지가 아닙니다.** 사용자가 앱을 켜는 순간은 대개 이미 레이드 안이고,
자기 위치를 몰라서 켭니다. 맵이 늦게 뜨면 그 사이에 죽습니다. 앱이 존재하는 이유가
"빨리 위치를 아는 것"인데 그 앞에 관문을 두면 스스로를 막는 셈입니다.

**받을 것이 작지 않습니다.** 버전 전환은 delta를 쓸 수 없어 언제나 전체 패키지를
받습니다. 실측으로 30초를 넘겼습니다. 이 시간을 시작 앞에 두는 선택은 없습니다.

**Discord 모델은 전제가 다릅니다.** Discord는 앱 자체가 목적지라 기다림이 목적의
일부로 받아들여집니다. 이 앱은 실시간으로 벌어지는 일의 보조 도구입니다. 같은 화면
구성을 빌려 와도 같은 결론이 나오지 않습니다.

## 지금 구조

```
앱 시작
  -> AppPaths.PrepareOnStartup      사용자 폴더 정돈
  -> InitializeCef                  브라우저 초기화
  -> 메인 창 표시                    여기까지가 사용자가 기다리는 시간
  -> CheckAndDownloadAsync          창이 열린 뒤에 시작한다 (fire-and-forget)

앱 종료
  -> Cef.Shutdown                   프로필 파일을 놓는다
  -> ApplyOnExit                    받아 둔 패키지를 적용한다
```

자동 업데이트를 끄면 확인 자체를 건너뜁니다. 받아 둔 패키지는 앱을 닫을 때 적용하므로
쓰는 도중에 끊기지 않습니다. 사용 중에 새 버전을 발견하면 타이틀 바의 다운로드 아이콘으로
알리고, 즉시 적용은 사용자가 그 아이콘을 누를 때만 합니다.

이 구조는 처음 구상의 두 축을 그대로 지킵니다. 첫 실행에서 자동으로 받는 것과, 사용
중에는 사용자 동의 없이 앱을 끊지 않는 것입니다. 바뀐 것은 창이 열리는 시점 하나뿐입니다.

## SplashWindow의 역할 변경

업데이트 관리자가 아니라 **시작이 오래 걸릴 때만 나타나는 표시**입니다.

시작이 빠르면 아예 뜨지 않습니다. 설치 직후 첫 실행이나 느린 디스크, 백신 검사처럼
실제로 몇 초 걸릴 때만 나타납니다.

0.2초 동안 떴다 사라지는 로딩 표시는 없느니만 못합니다. 사용자는 아무 정보도 얻지 못하고
화면만 튀어서 결함으로 읽습니다. 그래서 일정 시간이 지난 뒤에 띄우고, 한 번 뜬 뒤에는
최소 시간을 유지해 깜빡이지 않게 합니다.

**미관을 위해 최소 표시 시간을 강제하지 않습니다.** 아이콘을 보여주려고 시작을 늦추는
것은 이 문서가 정한 우선순위를 정면으로 어기는 일입니다. 앱 아이콘을 보여줄 자리는
트레이와 작업 표시줄에 따로 있습니다.

## 다시 뒤집을 조건

아래 전제가 깨지면 그때 재검토합니다. 그 전에는 이 구조를 유지합니다.

- 레이드 중에 앱을 켜는 것이 주된 사용 방식이 아니게 되는 경우
- 업데이트가 시작을 막지 않을 만큼 작아지는 경우

전제가 깨지지 않았는데 "스플래시가 있는데 왜 거기서 안 받지"라는 이유만으로
되돌리지 않습니다.
