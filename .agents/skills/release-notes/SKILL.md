# 릴리스 내역 작성

<!--

주요 업데이트의 기준은 변경 종류가 아니라 사용자에게 미치는 영향이다. 중요한 버그 수정도 그 중심이 될 수 있다.
고정된 분류나 한 줄 요약에 맞추면 원인과 선택 이유가 사라지므로, 근거와 독자의 궁금증에 따라 구성과 설명량을 정한다.

설치할 사용자가 달라지는 동작과 그 이유를 이해하는 업데이트 공지를 작성합니다. 아래 기준으로 내용을 먼저 고른 뒤 제목과 목록을 구성합니다.

## 버전과 배포 단위

- 버전을 따로 지정하지 않으면 현재 개발 계열의 패치 번호를 올려 정식 버전으로 이어갑니다. 베타 접미사는 시험 버전을 명시적으로 요청한 경우에 사용합니다.
- 한 번의 업데이트에서는 누적된 변경을 최종 목표 버전 하나로 배포합니다. 개발 중 거친 중간 버전의 태그와 릴리스를 함께 발행하지 않습니다.
- 중간 버전은 사용자가 해당 버전의 발행을 명시적으로 요청한 경우에만 배포합니다. 그 버전 시점의 코드와 내역을 사용하며, 같은 최종 코드를 여러 버전으로 나눠 발행하지 않습니다.
- 최종 버전의 내역은 실제로 공개된 비교 기준 버전 이후의 변경을 합쳐 작성합니다. 미배포 버전을 건너뛰어도 그 안의 변경을 누락하지 않으며, 대체된 미배포 초안은 최종 버전 파일로 옮깁니다. 이미 공개된 버전의 기록은 보존합니다.

## 변경 근거 확인

- 새 버전은 `src/TanukiTarkovMap/TanukiTarkovMap.csproj`의 `Version`, 기존 릴리스는 실제 태그를 기준으로 `docs/releases/<Version>.md`에 작성합니다. 파일명에서는 태그의 `v` 접두사를 뺍니다.
- 정식 버전은 직전 정식 버전, 시험 버전은 분기 기준이나 직전 시험 버전과 커밋 및 코드 차이를 비교합니다. 아직 태그가 없는 버전은 릴리스에 포함할 변경까지 확인합니다. 공개 날짜나 커밋 제목만으로 포함 범위를 정하지 않습니다.
- 설명할 변경의 이슈, PR, 코드와 검증 결과, 기존 INTENT, 사용자가 밝힌 필요와 의도를 읽습니다. 계획만 있는 기능과 실제 반영한 변경을 구분합니다.
- 버그 원인은 재현 결과와 코드에서 확인하고, 신규 기능의 개발 동기는 사용자 설명이나 당시 기록에서 확인합니다. 코드만 보고 개발자의 경험이나 감정을 역산하지 않습니다.
- 근거가 부족하면 확인한 동작까지만 설명합니다. 중요한 선택 이유가 빠져 글의 의미가 달라지는 경우에는 기존 자료부터 찾고, 사용자만 아는 배경은 질문하되 다른 항목의 작성은 계속합니다.

## 설명할 내용과 깊이

각 항목은 무엇이 달라졌는지 먼저 보여주고 필요한 배경을 이어 설명합니다. 아래 관점은 생각할 때 사용하며 본문에 매번 같은 라벨이나 순서로 찍어내지 않습니다.

- 버그 수정은 사용자가 겪은 증상과 발생 조건, 확인된 원인, 바꾼 처리 방식과 수정 후 동작을 연결합니다. `버그 수정`으로 끝내지 말고 왜 그 수정으로 문제가 해결되는지 이해되게 씁니다.
- 신규 기능이나 개선은 어떤 상황에서 필요했는지, 그 필요에 맞춰 어떤 방식을 골랐는지, 이제 어떻게 사용할 수 있는지 설명합니다. 개발자가 직접 밝힌 동기는 자연스럽게 살리되 `필요성을 느꼈습니다` 같은 문장을 임의로 만들지 않습니다.
- 여러 수정이 하나의 사용자 문제를 해결한다면 하나의 항목으로 묶습니다. 영향 범위나 사용 조건이 다른 변경은 각각 알아볼 수 있게 남깁니다.
- 자주 겪는 문제, 핵심 기능의 변화, 업데이트 후 행동이 필요한 변경에는 설명을 충분히 배정합니다. 작은 표시 변경은 짧게 끝내며 문장 수나 분량을 일률적으로 제한하지 않습니다. 길이가 아니라 독자가 이해와 사용에 필요한 정보를 얻었는지로 판단합니다.
- 원인과 구현 방식은 사용자의 말로 풉니다. 내부 함수명, 파일명과 조사 과정은 설명에 꼭 필요할 때만 넣고, 사용자가 찾아야 할 설정 이름과 사용 조건은 정확히 적습니다. 기술 분석의 상세 근거는 PR에 둡니다.
- 재발 방지 방법은 어떤 실패를 감지하거나 차단하는지 구체적으로 적습니다. 시험한 범위를 넘어 `완벽하게 해결`, `다시는 발생하지 않음`을 약속하지 않습니다. 실제 남은 제한은 해당 변경 가까이에 밝힙니다.

## 내용에 따른 구성

구획의 수, 이름과 순서는 고정하지 않습니다. `주요 업데이트 내용`에는 사용자에게 중요한 버그 수정, 신규 기능, 개선을 함께 담을 수 있습니다. 변경이 많으면 기능이나 사용 상황별로 묶고, 작은 패치라면 제목 하나와 목록만으로 끝냅니다. 빈 구획과 `해당 없음`은 만들지 않습니다.

제목은 `##`, 변경 항목은 `-`로 작성합니다. 중요한 항목은 짧은 제목 뒤에 설명 문단을 이어도 됩니다. 항목 제목은 명사형으로, 사용자에게 설명하는 문장은 합니다체로 씁니다. 같은 내용을 주요 업데이트와 버그 수정에 중복 기재하거나 모든 항목에 `[수정]` 같은 분류를 붙이지 않습니다.

설치 안내, 설정 초기화, 알려진 제한은 해당 항목에서 설명할지 별도 구획으로 묶을지 내용에 맞게 정합니다. 이미지나 변경 전후 비교는 말만으로 동작을 이해하기 어려울 때 사용합니다. 인사말, 목차, 개발자 코멘트는 설명에 도움이 될 때만 넣습니다.

## 유동형 템플릿

다음은 항목 안에 설명을 담는 예시 틀입니다. 중괄호 부분을 실제 근거로 채우고 제목과 항목은 내용에 맞게 추가하거나 생략합니다. 설명의 순서와 길이도 고정하지 않습니다.

```markdown
## {이번 버전에서 먼저 알릴 주제}

- **{해결된 문제 또는 달라진 기능}**

  {사용자가 겪던 상황과 확인된 원인 또는 필요를 설명하고, 선택한 방법과 달라진 동작을 자연스럽게 잇습니다.}

- {별도 배경 설명 없이도 이해되는 작은 변경}
```

## 작성 후 확인과 반영

독자가 `왜 필요했는지`, `어떻게 바뀌었는지`, `내가 무엇을 확인해야 하는지`를 이해하는지 읽어봅니다. 설명의 빈틈을 추측으로 메우지 않았는지, 중요한 배경을 지나치게 줄이거나 사소한 변경을 부풀리지 않았는지도 확인합니다.

변경 내역은 GitHub 릴리스와 설치 패키지에서 같은 파일을 사용합니다. 기존 릴리스 설명을 고칠 때는 다운로드 안내와 사용 조건, 해당 버전의 변경 범위를 보존합니다. 릴리스 제목, 태그, 공개 상태와 첨부 파일은 그대로 두며 이미 배포한 패키지 내부의 내역까지 바뀌었다고 안내하지 않습니다.

원격 반영을 요청받은 범위에서는 로컬 `gh`의 `siakun` 계정으로 수행하고, 반영 후 본문이 파일 내용과 일치하는지 확인합니다. 스킬이나 템플릿을 고치는 요청만으로 기존 릴리스 전체의 원격 설명까지 다시 쓰지는 않습니다.
